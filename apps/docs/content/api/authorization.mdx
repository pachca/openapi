# Авторизация

У каждого метода API есть требования для вызова:

- **Скоуп токена** — почти все методы требуют определённый скоуп. Указан в шапке страницы метода и в [OpenAPI-спецификации](/openapi.yaml) в поле `x-requirements.scope`.
- **Тарифный план** — часть методов доступна только на определённом тарифе (например, [экспорт](/guides/export) или [журнал аудита](/guides/audit-events)). Указан в шапке страницы метода рядом со скоупом и в [OpenAPI-спецификации](/openapi.yaml) в поле `x-requirements.plan`.
- **Права владельца токена** — скоуп открывает метод, но не расширяет видимость. Токен работает по тем же правилам, что и интерфейс Пачки: роль в пространстве, роль в чате и участие в нём. Подробнее — в разделе [Права и роли](/guides/permissions).

## Типы токенов

В Пачке есть два типа токенов. Тип определяет, от чьего имени работает интеграция и к какому кругу данных она имеет доступ.

### Персональный токен

Действует от имени пользователя. Подходит для скриптов, утилит и интеграций, которые работают от вашего имени: выгрузка данных, личная автоматизация, тестирование API.

**Доступ к данным** — те же чаты, треды и сообщения, что видит сам пользователь в интерфейсе Пачки. Никаких дополнительных ограничений или расширений у токена нет, он наследует видимость владельца.

Получить такой доступ можно двумя путями, и это не одно и то же:

| | Токен в интерфейсе | Вход через CLI |
|---|---|---|
| Как выдаётся | **Интеграции** > **API**, руками | `pachca auth login`, подтверждение в браузере |
| Кто выбирает права | вы, при выпуске | не выбираются: берётся весь каталог, урезанный вашей ролью на момент входа |
| Срок | бессрочный | час, продлевается автоматически |
| Значение токена | показывается один раз, копируется | в терминал не выводится |
| Как прекратить доступ | удалить токен на странице **Интеграции** > **API** | `pachca auth logout` или **Отозвать** в списке **Токены CLI** — токен гасится на сервере сразу |
| Когда подходит | унести в автоматизацию или CI, передать коллеге | работа руками и агентом на своей машине |

Разница не только в удобстве. Токен из интерфейса вы держите в руках: он бессрочный, его можно скопировать в чужую систему или передать другому сотруднику — вместе со своими правами. Токен входа через CLI короткоживущий и привязан к машине, где выполнен вход, поэтому переносить его бессмысленно.

Любой токен, с которым работает CLI, хранится в хранилище ключей операционной системы — и полученный входом через браузер, и переданный через `--token`. Там, где хранилища нет (headless-машина, контейнер), токен ложится в файл конфигурации открытым текстом, и CLI сообщает об этом при входе. Подробнее — в разделе [CLI: авторизация](/guides/cli/authentication#gde-hranitsya-token).

### Токен бота

Действует от имени бота. Подходит для сервисных интеграций независимо от конкретного пользователя: чат-боты, уведомления из внешних систем, обработка вебхуков, интерактивные формы.

**Доступ к данным** — все открытые каналы пространства плюс закрытые каналы, беседы и треды, в которые бот добавлен участником. Подробнее о правилах доступа бота к чатам, тредам и личным сообщениям — в разделе [Доступы к чатам и сообщениям](/guides/bots/access).

<Info>
  [Скоупы](#skoupy) определяют только **какие методы** можно вызывать — расширить круг данных за пределы границ типа токена они не могут.
</Info>

### Токен по авторизации

Персональный токен, который сотрудник выдал боту на экране согласия. Действует от имени сотрудника и видит то же, что он, а хранится в сервисе бота — по токену на каждого сотрудника. Права берутся из настроек бота и дополнительно ограничены ролью сотрудника, а отозвать доступ сотрудник может в любой момент. Подходит ботам, которым нужны данные самого сотрудника: его задачи, его чаты. Подробнее — в разделе [Авторизация от имени сотрудника](/guides/oauth/overview).

### Какой токен выбрать

Выберите тип по задаче, которую решает интеграция:

| Задача | Тип токена | С чего начать |
| --- | --- | --- |
| Работа с API руками или агентом на своей машине | Персональный | [CLI: авторизация](/guides/cli/authentication) |
| Скрипт или утилита от вашего имени, личная автоматизация, разовая выгрузка данных | Персональный | [Создание персонального токена](#sozdanie-personalnogo-tokena) |
| Чат-бот, уведомления из внешних систем, обработка вебхуков, интерактивные формы | Бот | [Боты](/guides/bots/overview) |
| Агент или headless-интеграция без участия сотрудника (CI, сервер, облачный воркер) | Бот | [Агенты и headless-интеграции](#agenty-i-headless-integratsii) |
| Бот, которому нужны данные сотрудника: его задачи, его чаты | По авторизации | [Авторизация от имени сотрудника](/guides/oauth/overview) |

## Кто может создавать токены

Владелец пространства может ограничить, кто может создавать токены и работать с API. Настройки находятся в разделе **Настройки пространства**:

- **Кто может создавать интеграции** *(боты и их токены)* — «Только администраторы» или «Администраторы и сотрудники»
- **Кто может работать с API** *(персональные токены)* — «Только администраторы» (сотрудники не смогут создавать персональные токены) или «Все сотрудники». При «Только администраторы» сотрудникам закрыты и вход в CLI, и выдача доступа ботам на экране согласия.

<ImageCard src="/images/authorization/token_access.webp" alt="Настройки доступа к API" caption="Настройки доступа к API" maxWidth={464} />

<Warning>Гости не могут создавать токены любого типа вне зависимости от настроек пространства. Мульти-гость создаёт персональные токены, входит в CLI и авторизует ботов на тех же условиях, что и сотрудник, а ботов и их токенов не создаёт. Что он видит через API — в разделе [Права и роли](/guides/permissions#multi-gost-v-api).</Warning>

## Создание персонального токена

Персональные токены создаются на странице **Интеграции** > **API**. На ней указан ваш `user_id` и собраны три списка: персональные токены, токены CLI и авторизации.

<ImageCard src="/images/authorization/user_tokens_list.webp" alt="Страница «API» в разделе «Интеграции»: user_id и список персональных токенов" caption="Страница «API»" maxWidth={998} />

Нажмите **Создать токен** — откроется диалог, в котором нужно задать название токена и выбрать разрешения (скоупы).

<ImageCard src="/images/authorization/create_user_token_modal.webp" alt="Создание API токена" caption="Создание API токена" maxWidth={418} />

<Warning>Токен показывается только один раз сразу после создания. Скопируйте и сохраните его в надёжном месте — после закрытия диалога восстановить его будет невозможно.</Warning>

В списке у каждого токена видны дата создания и последнего использования. Меню токена позволяет посмотреть выданные разрешения, изменить название и разрешения или удалить токен. Если токеном пользовались недавно, диалог удаления предупредит об этом: всё, что на нём работает, сломается сразу.

### Токены CLI и авторизации

Ниже на той же странице — доступы, которые вы выдали без ручного создания токена:

- **Токены CLI** — по строке на каждое устройство, где выполнен `pachca auth login`: имя устройства, время входа и последнего вызова. Токены продлеваются сами, а права ограничены вашей ролью. **Отозвать** завершает вход на выбранном устройстве, остальные входы продолжают работать. Подробнее — в разделе [CLI: авторизация](/guides/cli/authentication).
- **Авторизации** — боты, которым вы разрешили действовать от вашего имени на экране согласия. Для каждого видно, когда он подключён и когда использовался, и какие разрешения выданы. **Отозвать доступ** сразу отключает все токены этого бота, выданные вам.

## Получение токена бота

Бот виден в пространстве как отдельный участник со своим именем и аватаром. Получить его `access_token` можно двумя способами:

- **В интерфейсе** — на вкладке **API** в карточке бота: кнопка **Создать токен**, название и права. Токенов у бота может быть несколько, значение каждого показывается один раз.
- **Через API** — методом [Новый бот](POST /bots): он создаёт бота и сразу возвращает `access_token`. Сохраните токен из ответа: повторно значение не показывается, а перевыпустить токен можно методом [Ротация токена бота](POST /bots/{id}/recreate_token) или кнопкой **Перевыпустить** в карточке бота.

Несколько токенов у одного бота, их права, перевыпуск и что делать при утечке — в разделе [Токены бота](/guides/bots/tokens).

### Методы, требующие токен бота

Некоторые возможности API доступны исключительно с токеном бота:

- [Удаление события](DELETE /webhooks/events/{id}) — удаление события из истории событий бота
- [Саморегистрация вебхука бота](PUT /bot/webhook) — бот сам меняет `URL` своего исходящего вебхука
- [Unfurl (разворачивание ссылок)](POST /messages/{id}/link_previews) — создание предпросмотров ссылок в сообщениях
- [Открытие представления](POST /views/open) — открытие модального окна с формой для пользователя

Также при отправке сообщений ([Новое сообщение](POST /messages), [Новый тред](POST /messages/{id}/thread)) поля `icon_url` и `name` для кастомного аватара и имени отправителя работают только с токеном бота.

## Заголовок авторизации

Все запросы к API, кроме метода [Загрузка файла](POST /direct_url), должны содержать заголовок:

```http title="Заголовок авторизации"
Authorization: Bearer YOUR_ACCESS_TOKEN
```

## Агенты и headless-интеграции

Агенту или автоматизации без участия сотрудника (CI, сервер, облачный воркер) подходит токен бота — он работает как сервисная учётная запись, не привязанная к конкретному пользователю. Выдайте боту только нужные для задачи скоупы: принцип наименьших привилегий ограничивает круг доступных методов.

Как подключить агента (CLI, llms.txt, Skills) — в разделе [AI-агенты](/guides/ai-agents/overview). Передача токена в headless-режиме (`PACHCA_TOKEN` из секретов) — в разделе [CLI: авторизация](/guides/cli/authentication#ci-i-agenty-headless).

## Скоупы

Скоупы определяют, к каким методам API имеет доступ токен. Разные типы токенов получают скоупы по-разному:

- **Персональный токен** — вы выбираете скоупы вручную при создании и можете изменить их позже в настройках токена. Токен получит только запрошенные разрешения.
- **Токен бота** — права задаются на каждый токен при его создании и редактировании на вкладке **API** карточки бота. Через API — параметром `scopes` в методах [Новый бот](POST /bots) и [Редактирование бота](PUT /bots/{id}): он относится к тому токену, с которым работают методы API. Если скоупы не указаны, бот получает набор по умолчанию.

Боту доступны и собственные скоупы самоуправления, недоступные персональным токенам: `bot_self:webhook:write` — бот сам меняет `URL` своего исходящего вебхука методом [Саморегистрация вебхука бота](PUT /bot/webhook), и `bot_self:write` — самостоятельное управление настройками бота.

Бывает и наоборот: `bots:read` и `bots:write` для управления ботами, `drafts:read` и `drafts:write` для черновиков и отложенных сообщений выдаются только персональным токенам. Скоупы ботов есть у Владельца, Администраторов и Сотрудников, скоупы черновиков — ещё и у мульти-гостя, а токену бота их не получить: с ним метод отвечает `403`.

Проверить скоупы текущего токена можно методом [Информация о токене](GET /oauth/token/info).

### Доступные скоупы

При создании персонального токена в интерфейсе Пачки отображаются только те скоупы, которые доступны вашей роли. Токену бота права выбираются при создании в его карточке, а через API — параметром `scopes`, без которого бот получает набор по умолчанию.

## Ошибки авторизации

- `401 Unauthorized` — токен отсутствует, невалидный или отозван
- `403 Forbidden` — токен не имеет необходимого скоупа для данного метода (поле `error` содержит `insufficient_scope`)

<SchemaBlock name="OAuthError"/>

Ответ `403 insufficient_scope` дополнительно содержит заголовок `WWW-Authenticate` по [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750#section-3): в параметре `scope` — скоуп, которого не хватило токену. Это позволяет разобрать причину отказа, не разбирая тело ответа.

```http title="Заголовок ответа 403"
WWW-Authenticate: Bearer error="insufficient_scope", error_description="Insufficient scope. Required: profile:read", scope="profile:read"
```

Подробнее о кодах ошибок и структуре ответов — в руководстве [Ошибки](/api/errors).
