# Загрузка файлов

Загрузка файлов через API Пачки — трёхшаговый процесс с presigned URL (S3-совместимое хранилище).

## Процесс загрузки

<Steps>
  <Step title="Получение параметров загрузки">
    Сделайте запрос к методу [Получение подписи, ключа и других параметров](POST /uploads) без тела для получения подписи и параметров. Данный метод необходимо использовать для загрузки каждого файла.

    <ApiCodeExample operationId="UploadOperations_getUploadParams" title="Получение параметров загрузки" />

    В ответе вы получите параметры для следующего шага: `Content-Disposition`, `acl`, `policy`, `x-amz-credential`, `x-amz-algorithm`, `x-amz-date`, `x-amz-signature`, `key` и `direct_url`. В части пространств вместо `acl` приходит `bucket`.
  </Step>
  <Step title="Загрузка файла">
    Отправьте запрос к методу [Загрузка файла](POST /direct_url) с форматом `multipart/form-data` на адрес `direct_url`. Включите все полученные параметры, кроме самого `direct_url`, и файл: список полей — в разделе [Поля multipart-формы для S3](#polya-multipart-formy-dlya-s3). При успешной загрузке хранилище ответит `204` без тела.

    <ApiCodeExample operationId="DirectUploadOperations_uploadFile" title="Загрузка файла" />

    <Warning>Порядок полей в multipart-запросе важен: файл (`file`) должен быть **последним** полем.</Warning>
  </Step>
  <Step title="Прикрепление файла к сообщению или другой сущности">
    После загрузки файла, чтобы прикрепить его к сообщению или другой сущности API, необходимо сформировать путь файла. Для этого в поле `key`, полученном на этапе подписи, заменить шаблон `${filename}` на фактическое имя файла.

    Пример: если ваш файл называется `Логотип для сайта.png`, а в ответе на метод `/uploads` ключ был `attaches/files/93746/e354-...-5e6f/${filename}`, итоговый ключ будет `attaches/files/93746/e354-...-5e6f/Логотип для сайта.png`. Начало ключа бывает разным, поэтому меняйте в нём только `${filename}`.

    ```json title="Файл в сообщении"
    {
      "message": {
        "entity_type": "discussion",
        "entity_id": 12345,
        "content": "Документ прикреплён",
        "files": [
          {
            "key": "attaches/files/93746/e354fd79-.../document.pdf",
            "name": "document.pdf",
            "file_type": "file",
            "size": 102400
          }
        ]
      }
    }
    ```

    Поле `name` — это отображаемое имя файла, его базовую часть можно менять. А вот расширение в `name` должно совпадать с расширением файла в `key`: иначе запрос вернёт `422` с кодом `wrong_params`. Проверка не даёт замаскировать один тип файла под другой, когда в интерфейсе показано `photo.jpg`, а скачивается `photo.exe`.

    Поле `size` можно не передавать или передать `0`: тогда Пачка возьмёт размер из хранилища вскоре после сохранения.

    Кроме [Нового сообщения](POST /messages) тот же ключ в поле `files` принимают [Редактирование сообщения](PUT /messages/{id}), [Новый черновик](POST /drafts) и [Редактирование черновика](PUT /drafts/{id}). Формат записи файла везде одинаковый.

    При редактировании сообщения переданный набор файлов заменяет прежний. Чтобы оставить уже прикреплённый файл, передайте его снова с тем же `key`: он останется прежним вложением с тем же `id` и названием, а `name` и другие поля из запроса к нему не применятся. Чтобы показать файл под другим названием, загрузите его заново.
  </Step>
</Steps>

## Поля multipart-формы для S3

Все поля из ответа метода [Получение подписи, ключа и других параметров](POST /uploads), кроме `direct_url`, передаются на S3 **как есть** в multipart-форме. В `key` можно сразу заменить `${filename}` на имя файла:

| Поле | Описание |
|------|----------|
| `Content-Disposition` | Заголовок для скачивания |
| `acl` | Права доступа S3, приходит не во всех пространствах |
| `policy` | Base64-кодированная политика загрузки |
| `x-amz-credential` | AWS credential |
| `x-amz-algorithm` | Всегда `AWS4-HMAC-SHA256` |
| `x-amz-date` | Дата подписи |
| `x-amz-signature` | Подпись запроса |
| `key` | Путь файла на S3 (содержит `${filename}` — заменить на реальное имя) |
| `bucket` | Имя хранилища, приходит в части пространств вместо `acl` |
| `file` | Сам файл — **обязательно последнее поле** |

<Warning>`direct_url` — внешний presigned URL хранилища S3, его адрес отличается от адреса API Пачки. Запрос на него уходит без заголовка `Authorization`, а сама ссылка действует ограниченное время.</Warning>

## Через CLI

Команда `pachca upload` сама выполняет шаги 1 и 2 и возвращает готовый `key` для поля `files`. Как загрузить файл и отправить его в чат из терминала — в руководстве CLI [Файлы](/guides/cli/files).

## Типы файлов

| Тип | `file_type` | Дополнительные поля |
|-----|-------------|---------------------|
| Файл | `file` | — |
| Изображение | `image` | `width`, `height` — размеры в пикселях |
| Аудиофайл | `audio` | — |
| Голосовое сообщение | `voice` | `duration_ms` и `waveform` — оба обязательны |
| Видеофайл | `video` | `duration_ms` — длительность в миллисекундах |

Длительность `duration_ms` хранится у голосовых сообщений и видеофайлов, у остальных типов Пачка её отбрасывает.

Голосовое сообщение отправляют токеном сотрудника: с токеном бота файл с `file_type: "voice"` возвращает `403`. Голосовое длиннее 30 минут метод отклоняет с `422` и кодом `wrong_params`.

## Примеры полного цикла

### TypeScript SDK

```typescript
import { PachcaClient, FileUploadRequest, FileType } from "@pachca/sdk"
import fs from "fs"
import path from "path"

const client = new PachcaClient("YOUR_TOKEN")

const filePath = "./report.pdf"
const fileName = path.basename(filePath)
const fileBuffer = fs.readFileSync(filePath)

// Шаг 1: Получить параметры загрузки и подставить имя файла в ключ
const params = await client.files.getUploadParams()
const fileKey = params.key.replace("${filename}", fileName)

// Шаг 2: Загрузить файл на S3 (direct_url — внешний presigned URL)
await client.files.uploadFile(params.directUrl, {
  contentDisposition: params.contentDisposition,
  acl: params.acl,
  policy: params.policy,
  xAmzCredential: params.xAmzCredential,
  xAmzAlgorithm: params.xAmzAlgorithm,
  xAmzDate: params.xAmzDate,
  xAmzSignature: params.xAmzSignature,
  key: fileKey,
  bucket: params.bucket,
  file: new File([fileBuffer], fileName)
})

// Шаг 3: Отправить сообщение с файлом
await client.messages.createMessage({
  message: {
    entityType: "discussion",
    entityId: 12345,
    content: "Отчёт прикреплён",
    files: [{ key: fileKey, name: fileName, fileType: FileType.File, size: fileBuffer.length }]
  }
})
```

### Python SDK

```python
from pachca.client import PachcaClient
from pachca.models import FileUploadRequest, MessageCreateRequest, MessageCreateRequestMessage, MessageCreateRequestFile, FileType
import os

client = PachcaClient("YOUR_TOKEN")

file_path = "report.pdf"
file_name = os.path.basename(file_path)

# Шаг 1: Получить параметры загрузки и подставить имя файла в ключ
params = await client.files.get_upload_params()
file_key = params.key.replace("${filename}", file_name)

# Шаг 2: Загрузить файл на S3 (direct_url — внешний presigned URL)
with open(file_path, "rb") as f:
    await client.files.upload_file(
        direct_url=params.direct_url,
        request=FileUploadRequest(
            content_disposition=params.content_disposition,
            acl=params.acl,
            policy=params.policy,
            x_amz_credential=params.x_amz_credential,
            x_amz_algorithm=params.x_amz_algorithm,
            x_amz_date=params.x_amz_date,
            x_amz_signature=params.x_amz_signature,
            key=file_key,
            bucket=params.bucket,
            file=f.read()
        )
    )

# Шаг 3: Отправить сообщение с файлом
await client.messages.create_message(MessageCreateRequest(
    message=MessageCreateRequestMessage(
        entity_type="discussion",
        entity_id=12345,
        content="Отчёт прикреплён",
        files=[MessageCreateRequestFile(key=file_key, name=file_name, file_type=FileType.FILE, size=os.path.getsize(file_path))]
    )
))
```

## Частые ошибки

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `403 Forbidden` при загрузке | Поля формы не совпадают с подписью: поле пропущено или изменено, файл стоит не последним полем либо `key` выходит за выданный путь. Реже истекла сама подпись | Передайте все поля из ответа [Получение подписи, ключа и других параметров](POST /uploads) как есть, файл последним, и меняйте в `key` только `${filename}`. Если параметры получены давно, запросите новые. |
| `400 Bad Request` | Неправильный Content-Type. В пространствах, где в параметрах загрузки приходит `bucket`, причиной может быть и файл больше 4 ГБ | Убедитесь, что запрос отправляется как `multipart/form-data`, а не `application/json`. Файл больше 4 ГБ разделите на части или отправьте ссылкой |
| Файл не отображается | Имя в конце `key` не совпадает с именем, под которым файл загружен в хранилище | Подставьте вместо `${filename}` то же имя файла, с которым он ушёл на шаге 2 |
| `422` с кодом `wrong_params` | Расширение в `name` не совпадает с расширением файла в `key`. Сюда же попадает ключ, в котором остался `${filename}`: расширения у такого ключа нет | Замените `${filename}` в ключе на имя файла и приведите расширения к одному виду. Менять базовую часть имени можно, расширение — нет. |

## Ссылка на скачивание

Файлы сообщения приходят в поле `files` метода [Информация о сообщении](GET /messages/{id}). В каждом файле есть `url` — прямая ссылка на скачивание, заголовок `Authorization` для неё не нужен.

Ссылка действует до 7 дней с момента выдачи, и оставшийся срок бывает меньше: если её выдали раньше, вы получите ту же ссылку с остатком времени. Поэтому скачивайте файл сразу, а если ссылка ответила `403` — запросите сообщение заново и получите свежую.

Ссылка бывает и другой. Если в пространстве включено шифрование или задан безопасный контур, `url` ведёт не в хранилище, а на метод [Скачивание файла](GET /files/{id}). Такой файл забирается с заголовком `Authorization`, и токену нужен скоуп `files:read`. Отличить случай можно по самой ссылке, заранее знать настройки пространства не нужно.

Правило простое: защищённый файл, отправленный из безопасного контура, отдаётся только запросу с адреса из контура. Обычные и зашифрованные файлы метод отдаёт любому токену, который видит сообщение. Адрес проверяется тот, с которого пришёл запрос: для серверной интеграции это адрес вашего сервера, а не сотрудника, чьим токеном вы пользуетесь. Иначе ответ будет `403` с кодом `confidential_download_denied`.

В пространстве с безопасным контуром файлы после отправки проверяет антивирус. На файл, в котором нашли вирус, метод отвечает тем же `403` с любого адреса, даже если раньше этот файл скачивался.

Файл с прямой ссылкой метод тоже отдаёт, но такой проще скачать по самой ссылке. Откуда берутся ссылки обоих видов, рассказано в руководстве [Шифрование и безопасный контур](/guides/data-protection).

Узнать размер и имя файла, не скачивая его, можно запросом `HEAD` к методу [Скачивание файла](GET /files/{id}): в объекте файла размера нет. Запрос проходит те же проверки, что и скачивание, и отвечает только заголовками: `Content-Length` — размер файла или варианта из `target`, `Content-Disposition` — его имя. У зашифрованного файла `Content-Length` нет. Отказы приходят с теми же статусами, но без тела, а на отсутствующий файл или вариант — `404`.

<Info>В исходящем вебхуке о новом сообщении вложений нет. Чтобы получить файлы, запросите сообщение методом [Информация о сообщении](GET /messages/{id}) по полю `id` из вебхука.</Info>

## Удаление файлов

Файл живёт вместе с сообщением. Когда сообщение удаляют методом [Удаление сообщения](DELETE /messages/{id}), вложения стираются из хранилища без отложенного срока и корзины. Само сообщение остаётся в переписке помеченным как удалённое, но файлов в нём уже нет.

Так же работает правка: если убрать вложение методом [Редактирование сообщения](PUT /messages/{id}), файл удаляется из хранилища.

Исключение — пересылка. Пока на файл ссылается хотя бы одно сообщение, он остаётся в хранилище, поэтому удаление пересланной копии не трогает исходный файл.
