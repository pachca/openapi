# Лимиты

Мы следим за стабильностью API, поэтому есть лимиты на запросы (rate limiting). Они ориентировочные и могут меняться вместе с нагрузкой, но в обычной работе их хватает с запасом.

## API

Почти все лимиты API считаются по токену. Общий предел действует на все методы вместе, а у части методов есть свои, более строгие лимиты. Они действуют внутри общего предела: запрос к такому методу расходует оба счётчика.

Если запросов с одним токеном больше указанного, API вернёт `429 Too Many Requests`. В заголовке `Retry-After` мы укажем, через сколько секунд можно попробовать снова. В теле придёт обычный ответ об ошибке: код `rate_limit` в `errors[].code` и причина в `message`. Выждите этот срок и повторите запрос: правила повторов и готовый код — в разделе [Повторные запросы](#povtornye-zaprosy-retry). Срок дольше минуты приходит только у суточного предела сообщений и блокировки отправки, такой запрос не повторяйте.

Превышение суточного предела отвечает так же — `429` с кодом `rate_limit` в `errors[].code` и заголовком `Retry-After`. Отправка в этот чат приостанавливается на час. Каждая попытка во время паузы, пока квота за 24 часа ещё выбрана, удлиняет паузу на ступень: 1, 2, 4, 8, 16 и до 24 часов. Когда старые сообщения выпадают из окна и место освобождается, остаток паузы просто истекает и попытки его уже не удлиняют. Дождитесь срока из `Retry-After` — он учитывает и паузу, и момент, когда в окне освободится место. Отправка, прошедшая после паузы, возвращает шкалу к началу.

Лимит писем-приглашений отвечает иначе: `422` с кодом `daily_invites_limit`, а остаток и время, когда в окне освободится место, приходят в `payload`. Запрос при этом не применяется: сотрудник не создаётся, почта не меняется. В платном пространстве этого лимита нет.

В заголовке `Retry-After` мы укажем, через сколько секунд можно попробовать снова. В отличие от API, тело такого ответа — короткий текст с `Content-Type: text/plain`. Как уложиться в предел при потоке алертов — в разделе [Поток уведомлений](/guides/incoming-webhooks#potok-uvedomleniy).

## Длина текста

Текст сообщения, черновика и описание напоминания — до 40 000 байт в UTF-8. Символ кириллицы занимает два байта, поэтому это около 20 000 символов. Более длинный текст метод отклоняет.

## Защита от перегрузки

Если приложение продолжает отправлять сообщения выше лимитов даже после `429`, отправку с этого токена могут временно заблокировать — это защита от сбойных циклов и случайной перегрузки. Порог высокий, в обычной работе до него не доходит: около 22 000 запросов на отправку сообщений за час с одним токеном. Дальше отправка сообщений с этим токеном на час блокируется, а остальные методы продолжают работать. Ответ — тот же `429` с кодом `rate_limit`, а в `Retry-After` приходит, сколько секунд осталось до снятия блокировки: сразу после неё около часа, потом меньше. Чтобы этого избежать:

- Соблюдайте `Retry-After` — он указывает, через сколько секунд имеет смысл повторить
- Используйте экспоненциальный backoff с jitter — готовые примеры ниже в разделе [Повторные запросы](#povtornye-zaprosy-retry)
- Если ваш сервис не успевает обрабатывать ответы, приостановите запросы, а не ускоряйте retry

## Повторные запросы (Retry)

Наши клиенты повторяют запросы сами: все шесть [SDK](/guides/sdk/overview) ([TypeScript](/guides/sdk/typescript), [Python](/guides/sdk/python), [Go](/guides/sdk/go), [Kotlin](/guides/sdk/kotlin), [Swift](/guides/sdk/swift) и [C#](/guides/sdk/csharp)), [CLI](/guides/cli/overview) и [расширение для n8n](/guides/n8n/overview). Правила у них общие:

- До трёх повторов на каждый запрос
- `429` повторяется у любого метода: клиент ждёт не меньше срока из `Retry-After` и удлиняет паузу на случайную величину до 25%
- `429` с `Retry-After` дольше минуты сразу возвращается ошибкой вместе с этим заголовком
- `500`, `502`, `503` и `504` повторяются только у запросов GET, PUT и DELETE, а POST после них сразу возвращается ошибкой
- `504` с кодом `timeout` сразу возвращается ошибкой
- Остальные ошибки `4xx` возвращаются сразу

Паузы между повторами у клиентов разные, они указаны на странице каждого SDK. В CLI повторы отключает флаг `--no-retry`. Вызовы этих клиентов во второй цикл повторов не оборачивайте: каждая внешняя попытка снова запустит их собственные повторы. В n8n это касается и настройки узла [Retry On Fail](/guides/n8n/testing#retry-on-fail).

Если пишете свой клиент, соблюдайте три правила. Ниже — готовая реализация на TypeScript и Python.

**Не ждите меньше, чем сказано в `Retry-After`.** Это минимум ожидания, а не оценка: срок уже округлён вверх, чтобы клиент, выждавший его честно, не пришёл в ещё закрытое окно. Джиттер добавляйте вверх, а не вниз.

**Не повторяйте долгие паузы.** `Retry-After` дольше минуты приходит только там, где повтор не поможет: суточный предел сообщений в чат и блокировка отправки при перегрузке. Повтор внутри такой паузы бесполезен, а у суточного предела ещё и продлевает её, пока квота за 24 часа выбрана: каждая попытка поднимает срок на ступень, от часа до суток. Отдайте ошибку вызывающему коду вместе с `Retry-After`, и пусть он вернётся к работе позже.

**Повторяйте `5xx` только для идемпотентных методов.** Запросы GET, PUT и DELETE можно повторить без побочных эффектов. Запрос POST сервер мог выполнить до сбоя, и повтор `POST /messages` отправит сообщение дважды. Исключение — `504` с кодом `timeout`: так отвечают методы поиска и [Список сотрудников](GET /users) с параметром `query`, когда запрос не уложился по времени. Тот же запрос, скорее всего, снова не уложится, поэтому его не повторяют, а сужают: короче период, меньше чатов, точнее фраза.

### TypeScript

```typescript
const RETRYABLE_5XX = new Set([500, 502, 503, 504])
const IDEMPOTENT = new Set(["GET", "PUT", "DELETE"])
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms))
// Джиттер только вверх: ждать меньше Retry-After нельзя
const withJitter = (ms: number) => ms * (1 + Math.random() * 0.25)
// 504 с кодом timeout: поиск не уложился по времени, повтор не поможет
const isSearchTimeout = async (response: Response) =>
  response.status === 504 &&
  ((await response.clone().json().catch(() => null))?.errors ?? []).some(
    (e: { code?: string }) => e.code === "timeout"
  )

async function fetchWithRetry(
  url: string,
  init: RequestInit = {},
  maxRetries = 3
): Promise<Response> {
  const method = (init.method ?? "GET").toUpperCase()
  for (let attempt = 0; ; attempt++) {
    const response = await fetch(url, init)
    if (attempt >= maxRetries) return response

    if (response.status === 429) {
      const retryAfter = Number(response.headers.get("retry-after"))
      // Пауза дольше минуты: суточный предел или блокировка, повтор не поможет
      if (retryAfter > 60) return response
      await sleep(withJitter(retryAfter > 0 ? retryAfter * 1000 : 1000 * 2 ** attempt))
      continue
    }
    // 5xx повторяем только у идемпотентных методов: повтор POST может создать дубль
    if (RETRYABLE_5XX.has(response.status) && IDEMPOTENT.has(method) && !(await isSearchTimeout(response))) {
      await sleep(withJitter(1000 * 2 ** attempt))
      continue
    }
    return response
  }
}

// Использование
const response = await fetchWithRetry("https://api.pachca.com/api/shared/v1/users", {
  headers: { Authorization: `Bearer ${token}` },
})
```

### Python

```python
import random
import time

import httpx

RETRYABLE_5XX = {500, 502, 503, 504}
IDEMPOTENT = {"GET", "PUT", "DELETE"}


def with_jitter(seconds: float) -> float:
    # Джиттер только вверх: ждать меньше Retry-After нельзя
    return seconds * (1 + random.random() * 0.25)


def is_search_timeout(response: httpx.Response) -> bool:
    # 504 с кодом timeout: поиск не уложился по времени, повтор не поможет
    if response.status_code != 504:
        return False
    try:
        return any(e.get("code") == "timeout" for e in response.json().get("errors", []))
    except ValueError:
        return False


def request_with_retry(client: httpx.Client, method: str, url: str, max_retries: int = 3, **kwargs) -> httpx.Response:
    for attempt in range(max_retries + 1):
        response = client.request(method, url, **kwargs)
        if attempt == max_retries:
            return response

        if response.status_code == 429:
            retry_after = int(response.headers.get("Retry-After", 0))
            # Пауза дольше минуты: суточный предел или блокировка, повтор не поможет
            if retry_after > 60:
                return response
            time.sleep(with_jitter(retry_after or 2 ** attempt))
            continue
        # 5xx повторяем только у идемпотентных методов: повтор POST может создать дубль
        if response.status_code in RETRYABLE_5XX and method.upper() in IDEMPOTENT and not is_search_timeout(response):
            time.sleep(with_jitter(2 ** attempt))
            continue
        return response


# Использование
with httpx.Client(
    base_url="https://api.pachca.com/api/shared/v1",
    headers={"Authorization": f"Bearer {token}"},
) as client:
    users = request_with_retry(client, "GET", "/users").json()
```

### Стратегия повторов

| Код | Действие | Задержка |
| --- | --- | --- |
| `429` с `Retry-After` до минуты | Повторить | Не меньше `Retry-After`, без заголовка — 1 с, 2 с, 4 с |
| `429` с `Retry-After` дольше минуты | **Не повторять** | Отдать ошибку вызывающему коду вместе с `Retry-After` |
| `500`, `502`, `503` и `504` без кода `timeout` | Повторить только GET, PUT и DELETE | Exponential backoff: 1 с, 2 с, 4 с |
| `504` с кодом `timeout` | **Не повторять** | Сузить запрос: короче период, меньше чатов, точнее фраза |
| `400`, `401`, `403`, `404`, `422` | **Не повторять** | Ошибка клиента — нужно [исправить запрос](/api/errors) |

<Info>Максимум **3 повтора** на каждый запрос. Jitter (случайная добавка до 25% сверху к задержке) предотвращает «thundering herd» при массовых 429 и никогда не сокращает ожидание меньше `Retry-After`.</Info>
