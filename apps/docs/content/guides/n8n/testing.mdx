# Тестирование

В n8n тестирование узлов Пачки делится на две задачи:

- **Тестирование экшн-узлов** (узел **Pachca**) — отправка сообщений, создание напоминаний, работа с чатами. Тестируется как любой другой узел n8n: через **Execute step** и **Pin data**.
- **Тестирование триггера** (узел **Pachca Trigger**) — требует отдельного внимания, потому что у бота в Пачке только **один слот** для webhook URL, и неправильный тест может сломать живой workflow.

На этой странице — обе задачи, плюс приёмы отладки и локальной разработки.

## Инструменты n8n для тестирования

| Инструмент | Что делает | Для чего применять |
|-----------|-----------|---------------------|
| **Execute** (кнопка внизу холста) | Запуск всего workflow с триггера | Полный прогон цепочки с Manual Trigger |
| **Execute step** в окне узла | Запуск одного узла с данными предыдущего | Отладка конкретного узла без перезапуска всего |
| **Pin data** | Закрепление выходных данных узла | Мокирование входа для последующих узлов |
| **Execute step** в окне Pachca Trigger | Приём событий на Test URL, не дольше 120 секунд | Отладка триггера с реальным событием |
| **Publish** | Постоянная регистрация Production URL | Продакшен-запуск, ловит реальные события |

<Info>Execute step, Pin data и тестовый запуск триггера — стандартные возможности n8n, подробнее в [официальной документации n8n](https://docs.n8n.io/build/understand-workflows/understand-executions/). Ниже — как применять их к узлам Пачки.</Info>

## Тестирование экшн-узлов

Узел **Pachca** (действие) — это обычный n8n-узел, который вызывает REST API Пачки. Его можно тестировать без запуска всего workflow.

### Запуск одного узла через Execute step

Откройте узел Пачки (n8n называет его по операции, например **Create a message**), настройте параметры (Resource, Operation, поля) и нажмите **Execute step** в верхней части панели. n8n выполнит этот узел на данных предыдущего, а если предыдущие узлы ещё не запускались, сначала выполнит их. Весь workflow запускает кнопка **Execute** внизу холста.

<ImageCard src="/images/n8n/workflow-execute-success.avif" alt="Workflow «Первый workflow» после запуска кнопкой Execute: Manual Trigger и узел Пачки Create a message (create: message) подсвечены зелёным, на связях 1 item" caption="После запуска узлы подсвечиваются зелёным и показывают число элементов" maxWidth={960} />

При успехе:

- Узел подсвечивается зелёным и показывает количество обработанных элементов
- В панели **Output** появляется ответ API с данными операции

<ImageCard src="/images/n8n/workflow-output-data.avif" alt="Окно узла Create a message после запуска: в панели OUTPUT справа ответ API в виде JSON, 1 item с полями созданного сообщения в беседе 36942348 и текстом «Привет из n8n!»" caption="Ответ API в Output" maxWidth={960} />

<Warning>Перед тестом отправки сообщения убедитесь, что бот [добавлен в целевой чат](/guides/bots/access) и у токена есть нужный [скоуп](/api/authorization#skoupy). Иначе вы получите 403 Forbidden — симптомы и решения в разделе [Устранение ошибок](/guides/n8n/troubleshooting#nedostatochno-prav-403-forbidden).</Warning>

### Мокирование входных данных через Pin data

Функция **Pin data** позволяет закрепить выходные данные узла, чтобы последующие узлы при отладке использовали фиксированный вход вместо вызова API или ожидания события.

Типовой сценарий — отладка workflow с триггером без ожидания реального события:

<Steps>
  <Step title="Получите один пример события">
    Откройте узел **Pachca Trigger** и нажмите **Execute step**. Пока n8n показывает «Listening for test event», отправьте одно реальное событие, например сообщение в чат бота. n8n запишет тело события в **Output**. Как подготовить бота к такому тесту — в разделе [Тестирование триггера](#testirovanie-triggera).
  </Step>
  <Step title="Закрепите выход триггера">
    Нажмите на иконку булавки (**Pin data**) в правом верхнем углу панели **Output** узла **Pachca Trigger**. Теперь это тело зафиксировано — n8n будет подставлять его как вход для следующих узлов при отладке.
  </Step>
  <Step title="Отлаживайте цепочку">
    Меняйте настройки узлов IF, Switch, Pachca — при нажатии **Execute step** они будут получать зафиксированный вход триггера. Не нужно ждать новых событий от Пачки.
  </Step>
  <Step title="Снимите Pin перед публикацией">
    Закреплённые данные действуют только при запуске из редактора, продакшен-запуски после **Publish** их не используют. Когда отладка закончена, снимите закрепление той же иконкой (подсказка **Unpin data**), чтобы следующий тестовый запуск снова получил настоящее событие.
  </Step>
</Steps>

<Info>Pin data особенно полезен при разработке бота-эхо или логики с IF-ветками: вы отлаживаете маршрутизацию и ответ без ручной отправки сообщений в Пачку.</Info>

### Проверка Credentials

Перед первым запуском сохраните Credentials кнопкой **Save**: n8n вызовет [Информация о токене](GET /oauth/token/info) и покажет результат. Повторить проверку можно кнопкой **Retry** в баннере.

<ImageCard src="/images/n8n/credentials-test.avif" alt="Окно учётных данных Pachca Bot после сохранения: «Connection tested successfully» с кнопкой Retry, поля Base URL, Access Token, Webhook Signing Secret, Webhook Allowed IPs и поле n8n Allowed HTTP Request Domains" caption="Connection tested successfully" maxWidth={896} />

При ошибке 401 — токен неверный или просрочен. Симптомы и решения — в разделе [401 Unauthorized](/guides/n8n/troubleshooting#nevernyy-token-401-unauthorized).

## Тестирование триггера

Узел **Pachca Trigger** работает через исходящий вебхук Пачки, и здесь есть критичная особенность: **у бота в Пачке только один слот для webhook URL**. Любая перезапись этого слота ломает текущий workflow.

Поэтому тестирование триггера — это не просто «нажал Execute step», а осознанный выбор: какой бот задействовать и как не перезатереть продакшен.

### Test URL и Production URL

У триггерного узла n8n два webhook URL. Они в блоке **Webhook URLs** в верхней части панели узла: раскройте блок и выберите адрес переключателем **Test URL** / **Production URL**. Нажатие на адрес копирует его.

<ImageCard src="/images/n8n/trigger-webhook-urls.avif" alt="Раскрытый блок Webhook URLs в Pachca Trigger: переключатель Test URL и Production URL и адрес Production URL" caption="Test URL и Production URL в панели узла" maxWidth={419} />

| URL | Путь | Когда активен | Использование |
|-----|------|---------------|---------------|
| **Test URL** | `/webhook-test/...` | Пока n8n слушает после нажатия **Execute step**, но не дольше 120 секунд | Отладка — данные видны прямо в редакторе |
| **Production URL** | `/webhook/...` | Пока workflow опубликован (**Publish**) | Продакшен — данные видны только во вкладке **Executions** |

<Info>Test URL удобен тем, что n8n сразу показывает тело входящего события в редакторе — это лучший способ изучить структуру webhook-payload от Пачки.</Info>

### Как работает тестовый запуск триггера

У **Pachca Trigger** тестовый запуск начинается кнопкой **Execute step**. Она есть над параметрами узла и слева, под надписью «Pull in events from Pachca». Пока n8n ждёт событие, слева написано «Listening for test event» и есть кнопка **Stop Listening**. Когда вы нажимаете **Execute step** на узле **Pachca Trigger** в автоматическом режиме:

1. Узел прописывает боту Test URL в поле `outgoing_url`: с токеном бота методом [Саморегистрация вебхука бота](PUT /bot/webhook), с персональным токеном методом [Редактирование бота](PUT /bots/{id})
2. Пачка записывает Test URL в единственный слот вебхука бота
3. Пока n8n слушает, но не дольше 120 секунд, бот отправляет события на Test URL
4. n8n перехватывает событие и показывает его в редакторе
5. Когда n8n перестаёт слушать, узел очищает слот: адрес вебхука бота остаётся **пустым**, пока workflow не опубликуют снова

Именно шаги 1 и 5 — источник проблем. Если до теста в слоте был другой адрес, например Production URL, прописанный вручную, или адрес другого workflow, тест его перезапишет, а после теста слот окажется пустым. Пачка перестанет отправлять события, и живой сценарий молча остановится.

### Защита от перезаписи webhook-слота

Чтобы эта ситуация не происходила по ошибке, в **автоматическом** режиме Pachca Trigger блокирует тестовый запуск кнопкой **Execute step**, если на боте уже зарегистрирован Production URL этого же workflow. Узел выдаёт ошибку:

> Cannot listen for test events while the workflow is published — Pachca bots support only one webhook URL per bot, and a test run would overwrite the production webhook.

Это значит, что автоматический режим защищён от самого частого сценария — «забыл, что workflow опубликован, нажал Execute step на триггере и уронил продакшен».

<Warning>В **ручном** режиме (значение по умолчанию) узел не управляет слотом и не может его защитить — ответственность за то, какой URL прописан в настройках бота, полностью на вас. **Execute step** в ручном режиме всё равно начнёт слушать Test URL в n8n, но Пачка ничего об этом не узнает, пока вы сами не пропишете Test URL в настройках бота.</Warning>

### Три способа тестировать правильно

<Steps>
  <Step title="Отдельный бот для тестов (рекомендуется)">
    Создайте в Пачке второго бота специально для разработки. Сделайте отдельные Credentials с его токеном и используйте в тестовом workflow. На продакшене остаётся основной бот, на тестах — тестовый. Они никогда не конфликтуют, и тестовый запуск триггера можно повторять сколько угодно раз.

    Этот способ подходит для регулярной отладки и для команды: каждый разработчик может завести свой тестовый бот.
  </Step>
  <Step title="Временное снятие с публикации">
    Если второго бота нет, перед тестом снимите продакшен-workflow с публикации: откройте меню стрелкой рядом с кнопкой **Published** в правом верхнем углу и выберите **Unpublish**. В автоматическом режиме узел **Pachca Trigger** освободит слот: запишет пустой `outgoing_url` методом [Саморегистрация вебхука бота](PUT /bot/webhook) или [Редактирование бота](PUT /bots/{id}), в зависимости от токена.

    После этого нажмите **Execute step** на **Pachca Trigger**, проведите тест и снова опубликуйте workflow кнопкой **Publish**. На время теста продакшен будет выключен — учитывайте это, если на workflow приходит критичный трафик.
  </Step>
  <Step title="Подмена URL в ручном режиме">
    Оставьте **Webhook Setup** = **Manual** (значение по умолчанию) — в [ручном режиме](/guides/n8n/trigger#ruchnoy-rezhim) узел не управляет `outgoing_url`, и вы сами решаете, какой URL прописан в настройках бота в Пачке. Можно временно вручную заменить Production URL на Test URL в настройках бота, провести тест, затем вернуть Production URL обратно.

    Этот способ даёт максимальный контроль, но требует аккуратности — легко забыть вернуть Production URL.
  </Step>
</Steps>

## Отладка

### Просмотр Execution Data

Данные продакшен-запусков опубликованного workflow не показываются в редакторе — их нужно смотреть во вкладке **Executions**:

1. Откройте workflow и перейдите на вкладку **Executions**
2. Выберите нужное выполнение по времени и статусу (успех / ошибка)
3. n8n покажет цепочку узлов с данными входа и выхода каждого узла в формате JSON

Этот же режим работает и для неудачных выполнений — полезно, если workflow молча не срабатывает в продакшене. Там же видно тело webhook-события от Пачки и ответ API.

### Retry On Fail

Узел **Pachca** сам повторяет запросы после `429` и временных ошибок сервера, правила — в разделе [Повторные запросы](/api/limits#povtornye-zaprosy-retry). Настройка **Retry On Fail** на вкладке **Settings** узла запускает второй цикл повторов поверх встроенного и повторяет и отправку, поэтому на узлах, которые отправляют сообщения или создают объекты, она может дать дубли. Если она нужна, включайте её на узлах, которые читают данные.

### Error Trigger workflow

Чтобы получать алерты о сбоях в продакшене, сделайте отдельный workflow с узлом **Error Trigger** — он запускается при любой ошибке в основных workflow:

<Steps>
  <Step title="Создайте workflow с Error Trigger">
    Новый workflow → добавьте узел **Error Trigger**. Он автоматически подхватит ошибки всех workflow, в настройках которых этот workflow выбран как **Error Workflow**.
  </Step>
  <Step title="Отправьте алерт в чат Пачки">
    Добавьте после Error Trigger узел **Pachca** с операцией **Message → Create**. В поле **Content** используйте выражение с деталями ошибки из Error Trigger — например, `{{ $json.execution.error.message }}`.
  </Step>
  <Step title="Подключите Error Workflow к основным workflow">
    В каждом боевом workflow откройте меню **…** рядом с названием workflow и выберите **Settings**. В поле **Error Workflow (to notify when this one errors)** выберите созданный workflow с Error Trigger и нажмите **Save**. Теперь любая ошибка в этом workflow будет отправлять сообщение в Пачку.
  </Step>
</Steps>

## Локальная разработка

<Info>В **n8n Cloud** Production URL и Test URL триггера публичные «из коробки» — туннель не нужен. Этот раздел касается только self-hosted-инсталляций на локальной машине.</Info>

Если вы запускаете n8n на своей машине (`npx n8n` или Docker без публичного домена), Пачка не сможет доставить вебхуки на `localhost` — сервера Пачки находятся в публичной сети.

Решение — туннель с публичным HTTPS-адресом до порта n8n, по умолчанию `5678`:

| Инструмент | Как работает |
|-----------|--------------|
| **Cloudflare Tunnel** | Быстрый туннель `cloudflared tunnel --url http://localhost:5678` работает без аккаунта и домена, но адрес меняется при каждом запуске. Постоянный адрес даёт именованный туннель на своём домене, подключённом к Cloudflare. |
| **ngrok** | Отдельный сервис, пробрасывает любой локальный порт. Нужен аккаунт ngrok. Бесплатный тариф даёт один постоянный адрес на домене ngrok, свой домен — на платных тарифах. |

Адрес туннеля n8n сам не узнаёт: укажите его в переменной окружения `N8N_WEBHOOK_URL` (в версиях n8n до 2.30 — `WEBHOOK_URL`) и перезапустите n8n. После этого Test URL и Production URL узла **Pachca Trigger** покажут публичный адрес. Если адрес туннеля сменился, обновите переменную, перезапустите n8n и заново пропишите Production URL в настройках бота: в автоматическом режиме для этого снимите workflow с публикации и опубликуйте заново, в ручном вставьте новый адрес на вкладке **Исходящий вебхук**.

Подробнее о переменной — в [документации n8n](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-webhook-urls-with-reverse-proxy/). Что проверить перед запуском в работу — в разделе [Разработка и запуск обработчика](/guides/webhook/deploy).

## Если что-то пошло не так

- **Вебхук не приходит** — проверьте, что бот в чате, событие отмечено на вкладке **Исходящий вебхук** и workflow опубликован. Симптомы и решения: [Вебхук не приходит](/guides/n8n/troubleshooting#vebhuk-ne-prihodit).
- **403 при публикации Pachca Trigger** — токену не хватает прав: для токена бота `profile:read` и `bot_self:webhook:write`, для персонального `bots:write` плюс доступ редактора к боту. Решение: [403 Forbidden при публикации Pachca Trigger](/guides/n8n/troubleshooting#403-forbidden-pri-publikatsii-pachca-trigger).
- **Ошибка подписи** — узел молча отклоняет событие, и в **Executions** нет запуска, если Webhook Signing Secret в Credentials не совпадает с секретом бота. Решение: [Событие отклонено проверкой подписи или IP](/guides/n8n/troubleshooting#sobytie-otkloneno-proverkoy-podpisi-ili-ip).
- **401 Unauthorized** — неверный или просроченный токен. Решение: [401 Unauthorized](/guides/n8n/troubleshooting#nevernyy-token-401-unauthorized).

Полный список типовых ошибок — в разделе [Устранение ошибок](/guides/n8n/troubleshooting).
