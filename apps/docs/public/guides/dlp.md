# DLP-система

> **Внимание:** Доступно только на тарифе **Корпорация**


Встроенная в Пачку DLP-система (Data Loss Prevention) позволяет вам построить защиту от утечек конфиденциальной информации без интеграции сторонних сервисов.

Правила DLP-системы настраиваются в разделе **Настройки пространства** > **DLP**: здесь их создают, изменяют, включают и выключают. Раздел видит только владелец пространства.

![Список правил DLP-системы](/images/dlp/dlp-page.webp)

*Список правил DLP-системы*


## Создание правила

Чтобы внести новое правило, нажмите кнопку «Создать новое правило» и укажите название правила, его приоритет и `JSON`-объект условия.

![Новое правило](/images/dlp/new-rule.webp)

*Создание нового правила*


Название должно быть уникальным в пространстве: при создании из него получается идентификатор правила, который приходит в журнале аудита в поле `dlp_rule_id`. Названия, которые отличаются только регистром, пробелами или знаками препинания, считаются одинаковыми. При переименовании идентификатор не меняется, поэтому название, с которым правило создано, остаётся занятым.

Приоритет — целое число от `1`. Как он влияет на проверку, описано в разделе [Порядок обработки](#poryadok-obrabotki).

`JSON`-условие состоит из трёх полей: контекст применения правила (необязательное), условие срабатывания и действие при срабатывании. Параметры и примеры — в разделе [Структура правила](#struktura-pravila).

> В настройках правило редактируется как обычный текст в поле «JSON условия», визуального конструктора нет. Пишите JSON вручную или копируйте готовые примеры из этого гайда и подставляйте свои значения.


## Порядок обработки

Правила проверяются по приоритету: **чем больше число, тем раньше проверяется правило**. Правило с приоритетом `10` проверяется раньше правила с приоритетом `5`. Если приоритет у нескольких правил совпадает, раньше проверяется правило, созданное первым. Выключенные правила не проверяются.

**Первое сработавшее правило останавливает обработку**: остальные правила к сообщению уже не применяются. Если ни одно правило не сработало, сообщение остаётся без изменений и DLP-система ничего не пишет в журнал аудита.

Например, в пространстве заведены два правила:

- **Правило A** (`priority: 10`, `BLOCK`) блокирует номера телефонов
- **Правило B** (`priority: 5`, `AUDIT_LOG`) записывает в журнал упоминания слова «паспорт»

Сотрудник пишет в чат: «паспорт +7 999 123-45-67». Сообщение подходит под оба правила, но первым проверяется A с более высоким приоритетом: оно срабатывает, и текст заменяется на `action.message`. Правило B к этому сообщению **не применяется**, и события `dlp_violation_detected` о нём в журнале не будет.

## Когда проходит проверка

DLP-система не задерживает отправку. Сообщение сразу появляется в чате, а проверка идёт следом, в фоне. Пока она не закончилась, исходный текст могут увидеть участники чата, он может прийти в уведомлениях и в событии о новом сообщении, которое получают боты с исходящим вебхуком. Когда срабатывает правило с блокировкой, текст заменяется так же, как при правке сообщения: участники видят изменённое сообщение, а боты получают событие об изменении.

Каждая правка текста запускает проверку заново. Проверяется только текст сообщения: вложения, их названия и содержимое не проверяются, и при замене текста вложения остаются в сообщении.

Проверяются сообщения сотрудников и гостей, в том числе отправленные от их имени программой или ботом по токену сотрудника. Сообщения ботов и системные сообщения не проверяются.

## Структура правила

- `scope: object` — Объект контекста применения правила
  - `to_external: boolean` — Ограничение по наличию внешних контактов в чате. При значении true правило работает только в чатах, где есть гости или мульти-гости. Со значением false правило сохраняется, но не срабатывает ни в одном чате. Если поле не указано, по этому признаку правило не ограничивается.
  - `channel_type: string` — Тип чата, в котором работает правило. Указывается одним значением.
    Значения: `personal` — личные сообщения, `discussion` — беседы, `channel` — каналы, `thread` — треды
  - `user_role: string` — Роль автора сообщения в чате, при которой работает правило. Указывается одним значением.
    Значения: `owner` — создатель, `admin` — админ, `editor` — редактор, `member` — участник (для бесед), `subscriber` — подписчик (для каналов), `not_member` — не состоит в чате
- `conditions: object` (required) — Объект условия срабатывания правила. Можно указать all, any или оба, и тогда должны выполниться оба.
  - `all: array of object` — Массив условий (все должны совпасть)
    - `type: string` (required) — Тип условия
      Значения: `regex` — регулярное выражение, `keyword` — ключевое слово
    - `max_hits: integer` — Максимальное количество совпадений
    - `min_hits: integer` (default: 1) — Минимальное количество совпадений
    - `pattern: string` — Регулярное выражение для поиска в тексте, в синтаксисе Ruby, до 2000 символов. Обязательно, если type указано как regex.
    - `value: string` — Ключевое слово для поиска в тексте. Обязательно, если type указано как keyword.
  - `any: array of object` — Массив условий (хотя бы одно должно совпасть)
    - `type: string` (required) — Тип условия
      Значения: `regex` — регулярное выражение, `keyword` — ключевое слово
    - `max_hits: integer` — Максимальное количество совпадений
    - `min_hits: integer` (default: 1) — Минимальное количество совпадений
    - `pattern: string` — Регулярное выражение для поиска в тексте, в синтаксисе Ruby, до 2000 символов. Обязательно, если type указано как regex.
    - `value: string` — Ключевое слово для поиска в тексте. Обязательно, если type указано как keyword.
- `action: object` (required) — Объект действия при срабатывании правила
  - `type: string` (required) — Тип действия
    Значения: `BLOCK` — удалить текст сообщения, `AUDIT_LOG` — добавить запись в журнал событий, `BLOCK_AND_AUDIT_LOG` — удалить текст сообщения и добавить запись в журнал событий
  - `message: string` — Текст сообщения для пользователя. Пример: `"Сообщение заблокировано политикой безопасности"`


```json title="Пример правила #1"
{
    "conditions": {
        "any": [
            {
                "type": "regex",
                "pattern": "\\b(?:\\+7|7|8)\\s*\\(?\\d{3}\\)?\\s*\\d{3}[\\s-]*\\d{2}[\\s-]*\\d{2}\\b"
            }
        ]
    },
    "action": {
        "type": "AUDIT_LOG",
        "message": "Обнаружен номер телефона в сообщении"
    }
}
```

```json title="Пример правила #2"
{
    "conditions": {
        "all": [
            {
                "type": "keyword",
                "value": "паспорт"
            },
            {
                "type": "regex",
                "pattern": "\\b\\d{4}\\s?\\d{6}\\b"
            }
        ]
    },
    "action": {
        "type": "BLOCK",
        "message": "Нельзя отправлять паспортные данные"
    }
}
```

## Условия

В одном правиле можно скомбинировать любое число условий через массивы `all` (логическое И — должны сработать все) и `any` (логическое ИЛИ — хотя бы одно). Если заданы оба массива, должны выполниться оба. В массивах допускаются только простые условия `regex` и `keyword`: правило с вложенной группой `all` или `any` не сохранится.

### Регулярные выражения

Условия `type: "regex"` проверяются движком регулярных выражений [Ruby](https://docs.ruby-lang.org/en/master/Regexp.html). Правило с паттерном, который этот движок не разбирает, не сохранится: например, с именованной группой `(?P<name>…)` вместо `(?<name>…)` или с флагами `(?s)` и `(?U)`.

При проверке действуют правила этого движка:

- `.` совпадает и с переводом строки, а `^` и `$` — с началом и концом каждой строки сообщения.
- Регистр учитывается. Чтобы его не учитывать, начните паттерн с `(?i)`.
- `\w`, `\d` и `\s` совпадают только с символами ASCII, поэтому для русских букв используйте `\p{L}` или `\p{Cyrillic}`. Граница слова `\b` работает и рядом с кириллицей.

Максимальная длина паттерна — 2000 символов. На каждую проверку регулярного выражения отводится 200 мс: если проверка не уложилась, условие считается несработавшим, и ошибки при этом нет.

### Ключевые слова

Условия `type: "keyword"` ищут целое слово (с учётом границ слова `\b`) **без учёта регистра**, плюс одну распространённую морфологическую форму с суффиксом на «н»:

- `"секрет"` найдёт «секрет» и «секретная», «секретный», «секретное», но **не** «секреты» или «секрета»
- для остальных форм используйте `regex`

### Подсчёт совпадений

Поля `min_hits` и `max_hits` позволяют требовать определённое число совпадений в одном сообщении. По умолчанию `min_hits = 1` и `max_hits` не задан.

```json title="Минимум два упоминания ключевого слова"
{
    "conditions": {
        "all": [
            { "type": "keyword", "value": "пароль", "min_hits": 2 }
        ]
    },
    "action": {
        "type": "AUDIT_LOG",
        "message": "В одном сообщении упомянуто несколько паролей"
    }
}
```

## Действия

| Тип | Что происходит |
|---|---|
| `AUDIT_LOG` | Сообщение остаётся без изменений, в [журнал аудита](#zhurnal-audita) пишется событие `dlp_violation_detected` |
| `BLOCK` | Текст сообщения **заменяется** на `action.message`, а если поле не задано, на «Удалено DLP». Сообщение остаётся в чате и помечается как изменённое, а в журнал аудита замена попадает как правка автора. |
| `BLOCK_AND_AUDIT_LOG` | Текст заменяется, как при `BLOCK`, и в журнал аудита пишется событие `dlp_violation_detected` |

> Поле `action.message` показывается **в самом чате** вместо исходного текста, и его видят все участники. Пишите туда нейтральную формулировку о политике безопасности без подробностей правила.


## Контекст применения

Необязательный объект `scope` ограничивает, к каким сообщениям применять правило. Все указанные параметры комбинируются через И. Если `scope` не задан, правило применяется ко всем сообщениям, которые [проверяет](#kogda-prohodit-proverka) DLP-система.

- `to_external` — значение `true` ограничивает правило чатами, где состоят гости или мульти-гости. Без этого поля правило действует во всех чатах.
- `channel_type` — тип чата, одно значение строкой: `personal`, `discussion`, `channel` или `thread`.
- `user_role` — роль автора сообщения в чате, одно значение строкой: `owner`, `admin`, `editor`, `member`, `subscriber` или `not_member`.

> **Внимание:** Правило с `to_external: false` сохраняется, но не срабатывает ни в одном чате, поэтому ограничить правило чатами без гостей нельзя.

  Массив в `channel_type` и `user_role` при сохранении отбрасывается без ошибки, и правило начинает действовать на чаты всех типов или авторов всех ролей. Для нескольких значений заведите по правилу на каждое и после сохранения откройте правило, чтобы проверить `scope`.


```json title="Блокировать конфиденциальные данные в беседах с гостями"
{
    "scope": {
        "to_external": true,
        "channel_type": "discussion"
    },
    "conditions": {
        "any": [
            { "type": "keyword", "value": "конфиденциально" }
        ]
    },
    "action": {
        "type": "BLOCK_AND_AUDIT_LOG",
        "message": "Конфиденциальные сведения нельзя отправлять во внешние чаты"
    }
}
```

## Журнал аудита

DLP-система оставляет в журнале аудита два вида записей:

- `dlp_violation_detected` — при срабатывании правила с действием `AUDIT_LOG` или `BLOCK_AND_AUDIT_LOG`. Актор — автор сообщения, объект — само сообщение.
- `message_updated` — при каждой замене текста действием `BLOCK` или `BLOCK_AND_AUDIT_LOG`. В `actor_id` приходит автор, а в `ip_address` и `user_agent` — адрес и клиент из его запроса на отправку или правку сообщения, поэтому такую запись не отличить от правки самого автора.

Чтобы блокировки было видно в журнале, задавайте правилам действие `BLOCK_AND_AUDIT_LOG`.

Создание, изменение и удаление правил в журнал не пишутся.

Для события `dlp_violation_detected` в `details` приходит:

- `dlp_rule_id: string` (required) — Идентификатор правила DLP: строка из названия правила, например `pasport-rf`. При переименовании правила не меняется.
- `dlp_rule_name: string` (required) — Название правила DLP
- `message_id: integer, int32` (required) — Идентификатор сообщения
- `chat_id: integer, int32` (required) — Идентификатор чата
- `user_id: integer, int32` (required) — Идентификатор пользователя
- `action_message: string` (required, nullable) — Описание действия. `null`, если у действия правила текст не задан.
- `conditions_matched: boolean` (required) — Результат проверки условий правила (true — условия сработали)


Получить такие события можно методом [Журнал аудита событий](/api/security/list) с фильтром `event_key=dlp_violation_detected`. Подробнее — в [гайде по журналу аудита](/guides/audit-events).
