# Входящие вебхуки

Входящий вебхук публикует сообщения в чаты Пачки от имени бота. Внешний сервис отправляет один HTTP POST-запрос на адрес вебхука, и сообщение появляется во всех беседах и каналах, где состоит бот. Токен и работа с API не нужны, а текст сообщения из полей запроса собирает шаблон.

Вебхук работает в одну сторону: он только публикует сообщения. Чтобы бот отвечал сотрудникам, выполнял команды и обрабатывал нажатия кнопок, нужны токен бота и исходящий вебхук, с них начинается раздел [Первый бот](/guides/bots/first-bot). Один бот публикует в один набор чатов: чтобы уведомления разных сервисов шли в разные чаты, заведите по боту на каждый чат или используйте [n8n](#vhodyaschiy-vebhuk-ili-n8n).


## Входящий вебхук или n8n

Оба способа доставляют в Пачку уведомления из внешних сервисов без программирования. Входящему вебхуку достаточно бота и адреса. n8n сложнее в настройке, зато сценарий сам выбирает чат, дополняет данные и умеет кнопки.

| | Входящий вебхук | n8n |
| --- | --- | --- |
| Что нужно | Бот и адрес его вебхука | n8n Cloud или свой сервер n8n, токен бота или персональный токен |
| Куда приходят сообщения | Во все беседы и каналы бота | В любой чат, тред или личные сообщения, доступные токену |
| Разные уведомления в разные чаты | По боту на каждый чат | Выбор чата в узле Pachca по содержимому запроса |
| Обработка данных | Шаблон Liquid или Mustache | Узлы n8n: фильтры, запросы в другие сервисы, AI-агент |
| Кнопки, формы и ответы сотрудников | Недоступны | Узлы Pachca и Pachca Trigger |

Входящего вебхука хватает, когда сервис шлёт уведомления в одни и те же чаты: алерты мониторинга, сборки, заявки из CRM. n8n нужен, когда уведомление надо направить в чат по его содержимому, дополнить данными из других сервисов или дать сотрудникам кнопки для ответа. Тогда внешний сервис шлёт запрос на узел Webhook в n8n, а узел Pachca публикует сообщение в нужный чат. Готовый workflow — в примере [Уведомления из внешнего сервиса](/guides/n8n/workflows#uvedomleniya-iz-vneshnego-servisa), с чего начать — в разделе [n8n](/guides/n8n/overview).

## Как это работает


  ### Шаг 1. Создайте бота

Откройте **Интеграции** > **Боты** в боковой панели слева (если пункт скрыт, он в меню **Ещё**) и нажмите **Создать бота**. Ботов создают в веб-версии и десктопном приложении Пачки. Кто может создавать ботов и как это сделать — в разделе [Создание бота](/guides/bots/setup).


  ### Шаг 2. Включите вебхук и выберите источник

В карточке бота на вкладке **Входящий вебхук** нажмите **Включить** и выберите, что будет присылать данные: GitLab, Grafana или **Свой формат** для любого другого сервиса. Источник можно поменять позже.


  ### Шаг 3. Скопируйте адрес вебхука

После включения на вкладке появится адрес, на который сервис будет отправлять запросы. Скопируйте его. Адрес работает как пароль: кто его знает, тот публикует сообщения от имени бота. Подробнее — в разделе [Безопасность адреса](#bezopasnost-adresa).


  ### Шаг 4. Добавьте бота в нужные чаты

Вебхук публикует сообщение во все беседы и каналы, где состоит бот, кроме архивных. В треды и личные сообщения он не пишет. Добавьте бота в чаты, в которые хотите получать уведомления. Как это сделать — в разделе [Доступы к чатам и сообщениям](/guides/bots/access#besedy-i-kanaly).


  ### Шаг 5. Отправьте пробный запрос

Проверьте адрес до настройки сервиса. Подставьте адрес вебхука вместо `WEBHOOK_URL` и выполните команду:

```bash
curl -X POST "WEBHOOK_URL" \
  -H "Content-Type: application/json" \
  -d '{"message": "Проверка вебхука"}'
```

В ответ придёт `OK`, а сообщение «Проверка вебхука» появится во всех чатах бота, поэтому проверяйте, пока бот состоит в одном тестовом чате. Пока шаблон пустой, Пачка публикует поле `message`. Другие ответы разобраны в разделе [Ответ вебхука](#otvet-vebhuka).

Без командной строки подойдёт Postman: метод **POST**, адрес вебхука, на вкладке **Body** режим **raw** и тип **JSON**. Чтобы проверить свой шаблон, сохраните пример запроса из документации сервиса в файл, например `alert.json`, и замените в команде `-d '…'` на `--data-binary @alert.json`. Для источника GitLab пробный запрос отправляют кнопкой **Test** в настройках вебхука GitLab: свой JSON такой источник отклоняет с кодом `422`.


  ### Шаг 6. Вставьте адрес в настройки сервиса

Укажите адрес как адрес для уведомлений (webhook URL) в CRM, CI/CD, мониторинге или другом сервисе. При каждом событии сервис отправит `POST`-запрос, и бот опубликует сообщение. Запросы GitLab и Grafana Пачка разбирает сама, для остальных сервисов сообщение собирает [шаблон](#shablon-soobscheniya). Настройки и шаблоны для Alertmanager, Zabbix, Sentry, Uptime Kuma, GitHub, amoCRM и Битрикс24 — в разделе [Шаблоны для популярных сервисов](#shablony-dlya-populyarnyh-servisov).


## Настройки

Настройки входящего вебхука находятся на вкладке **Входящий вебхук** в карточке бота и появляются после включения. ### Источник

- **GitLab** — пуши, пайплайны и их задания (jobs), merge request, задачи (issues), комментарии, релизы и вехи (milestones)
- **Grafana** — алерты со скриншотами графиков
- **Свой формат** — любой сервис: JSON и шаблон сообщения

Для GitLab и Grafana Пачка сама разбирает запрос и собирает сообщение, поэтому шаблон нужен только своему формату.

Из событий GitLab в чат попадают не все. Пайплайн и задание публикуются, когда завершились: успешно, с ошибкой, пропущены или отменены. Задача публикуется, когда её открыли, открыли снова или закрыли. На остальные события, например на пуш тега или запущенный пайплайн, вебхук отвечает `422`. GitLab считает такой ответ ошибкой доставки и после нескольких ошибок подряд временно отключает вебхук. Поэтому отмечайте в GitLab только нужные события, а события заданий (Job events) лучше не отмечать: у каждого задания несколько промежуточных статусов, и ошибки быстро копятся подряд.

### Шаблон сообщения

Пока шаблон пустой, Пачка публикует содержимое поля `message` из входящего JSON. Чтобы собирать сообщение из полей произвольной структуры, выберите **формат шаблона** и заполните **шаблон сообщения**.

Какие поля присылает сервис, видно по настоящему запросу. Отправьте один запрос из сервиса или [пробный](#kak-eto-rabotaet) и нажмите ссылку **Показать последний полученный объект** под адресом вебхука: откроется окно с телом последнего запроса и временем получения. Окно показывает тело как есть, даже если сообщение из него не собралось. Тело формы (`application/x-www-form-urlencoded`) показывается строкой, а в шаблоне его поля становятся вложенными: `leads[add][0][name]` читается как `leads.add["0"].name`.

Пачка поддерживает два шаблонизатора:

- [**Liquid**](https://shopify.github.io/liquid/) — условия, циклы, фильтры (Shopify, open source)
- [**Mustache**](https://mustache.github.io/) — простая подстановка без логики (open source)

У бота, созданного в интерфейсе, формат шаблона по умолчанию Mustache. Mustache ставится и после удаления и повторного включения вебхука. Шаблоны для популярных сервисов на этой странице написаны на Liquid, поэтому перед вставкой шаблона выберите **Liquid** в поле **Формат шаблона**. Как это устроено у бота, созданного через API, описано в разделе [Через API](#cherez-api).

> Ссылки выше ведут на полную документацию шаблонизаторов, а ниже — общая информация по форматированию текста и получению данных из JSON-полей.


Шаблонизатор разбирает входящий JSON и подставляет значения полей в шаблон. Для форматирования текста (жирность, курсив, ссылки, блоки кода и пр.) используйте markdown — полный список поддерживаемых конструкций в разделе [Форматирование текста](/guides/markdown).

```json title="Входящий JSON"
{
  "client": "Иван Петров",
  "amount": 15000,
  "status": "оплачен",
  "project": { "name": "Pachca" }
}
```

```text title="Шаблон Liquid (точечная нотация для вложенных объектов)"
Заказ от {{ client }} на сумму {{ amount }} ₽ — {{ status }}
Проект: {{ project.name }}
```

```text title="Шаблон Mustache (секции для вложенных объектов)"
Заказ от {{ client }} на сумму {{ amount }} ₽ — {{ status }}
{{#project}}Проект: {{ name }}{{/project}}
```

> Mustache также поддерживает точечную нотацию для вложенных объектов `{{ project.name }}`.


```text title="Результат в чате"
Заказ от Иван Петров на сумму 15000 ₽ — оплачен
Проект: Pachca
```

Mustache экранирует HTML в двойных скобках: символы `<`, `>` и `'` попадают в текст сообщения как `&lt;`, `&gt;` и `&#39;`. Пустой шаблон при формате Mustache подставляет поле `message` так же, с экранированием. Чтобы вставить значение как есть, используйте тройные скобки: `{{{ client }}}`. Liquid значения не экранирует.

Liquid также поддерживает:

- **Условия** — `if`, `elsif`, `else`, `unless`, `case`/`when`, операторы `and`, `or`, `contains`
- **Циклы** — `for` с параметрами `limit`, `offset`, `reversed` и переменной `forloop`
- **Переменные** — `assign`, `capture`
- **Фильтры строк** — `default`, `append`, `prepend`, `downcase`, `upcase`, `capitalize`, `truncate`, `replace`, `remove`, `remove_first`, `split`, `slice`, `strip`, `newline_to_br`, `escape`, `url_encode`
- **Фильтры чисел** — `plus`, `minus`, `times`, `divided_by`, `modulo`, `round`, `ceil`, `floor`, `abs`
- **Фильтры массивов** — `join`, `first`, `last`, `size`, `sort`, `uniq`, `where`, `map`, `sum`, `compact`, `reverse`
- **Фильтры дат** — `date` с форматированием (`%d.%m.%Y`, `%H:%M` и пр.)

Поле, которого нет в запросе, подставляется пустой строкой. Дефис в тегах `{%-` и `-%}` убирает пустые строки и отступы вокруг тега, это пригодится в циклах и условиях. Фильтр `date` выводит время в том часовом поясе, в котором его прислал сервис: для `2026-10-30T07:00:00Z` это UTC.

### Показывать превью ссылок

Если включено, Пачка разворачивает ссылки из сообщений вебхука в превью — так же, как в обычных сообщениях.

### Поле для верификации

Некоторые сервисы (например, [monday.com](https://monday.com)) при настройке вебхука отправляют проверочный запрос и ожидают получить в ответе определённое поле. Укажите название поля проверки — Пачка ответит JSON-объектом с этим полем и его значением. Для monday.com это слово `challenge`.

## Шаблоны для популярных сервисов

Шаблоны ниже написаны на Liquid для источника **Свой формат**: выберите формат шаблона **Liquid** и вставьте шаблон в поле **Шаблон сообщения**. Вместо `WEBHOOK_URL` в настройках сервиса укажите адрес вебхука.

Заголовки запроса в шаблон не попадают, поэтому шаблон различает события по полям тела. Если для события шаблон ничего не выводит, вебхук отвечает `empty_message` и сообщение не публикуется: так шаблон заодно отсекает лишние события. Какие поля присылает ваш сервис, видно в окне **Показать последний полученный объект**.

### Prometheus Alertmanager

Alertmanager присылает группу алертов одним запросом, в массиве `alerts`. Добавьте получателя с адресом вебхука в `alertmanager.yml`:

```text title="alertmanager.yml"
route:
  receiver: pachca
  group_by: ['alertname']
receivers:
  - name: pachca
    webhook_configs:
      - url: 'WEBHOOK_URL'
        send_resolved: true
        max_alerts: 20
```

`max_alerts` ограничивает число алертов в одном запросе, чтобы сообщение уложилось в [предел длины](#otvet-vebhuka). Сколько алертов не вошло, Alertmanager передаёт в поле `truncatedAlerts`. Текст алерта шаблон берёт из аннотации `summary`, а если её нет, из `description`.

```text title="Шаблон Liquid"
{%- for alert in alerts %}
{% if alert.status == "firing" %}**Сработал:**{% else %}**Решено:**{% endif %} {{ alert.labels.alertname }}
{%- if alert.annotations.summary or alert.annotations.description %}
{{ alert.annotations.summary | default: alert.annotations.description }}
{%- endif %}
{%- if alert.labels.instance %}
Узел: {{ alert.labels.instance }}
{%- endif %}
[Источник]({{ alert.generatorURL }})
{% endfor -%}
{%- if truncatedAlerts > 0 %}
Не вошли в сообщение: {{ truncatedAlerts }}
{%- endif %}
```

### Zabbix

Создайте в Zabbix способ оповещения типа **Webhook**: **Alerts** > **Media types** > **Create media type**. В **Parameters** задайте параметры из таблицы, остальные можно удалить:

| Параметр | Значение |
| --- | --- |
| `URL` | `{ALERT.SENDTO}` |
| `event_value` | `{EVENT.VALUE}` |
| `event_name` | `{EVENT.NAME}` |
| `severity` | `{EVENT.SEVERITY}` |
| `host` | `{HOST.NAME}` |

В поле **Script** вставьте код. Он отправляет поля события в Пачку и считает ошибкой любой ответ, кроме `OK`, поэтому ошибки шаблона видны в журнале Zabbix.

```javascript title="Script"
var params = JSON.parse(value),
    request = new HttpRequest(),
    response;

request.addHeader('Content-Type: application/json');
response = request.post(params.URL, JSON.stringify({
    event_value: params.event_value,
    event_name: params.event_name,
    severity: params.severity,
    host: params.host
}));

if (request.getStatus() !== 200 || response !== 'OK') {
    throw 'Пачка ответила ' + request.getStatus() + ': ' + response;
}
return 'OK';
```

Пользователю, который получает оповещения, добавьте этот способ на вкладке **Media** и укажите адрес вебхука в поле **Send to**. В действии (action) добавьте операцию с этим способом, а для сообщений о решении проблемы — операцию восстановления (Recovery operations). Если разным пользователям указать адреса разных ботов, уведомления разойдутся по разным чатам.

```text title="Шаблон Liquid"
{% if event_value == "0" %}**Решено:**{% else %}**Проблема:**{% endif %} {{ event_name }}
Узел: {{ host }}, важность: {{ severity }}
```

### Sentry

В Sentry откройте **Settings** > **Developer Settings** и создайте внутреннюю интеграцию (Internal Integration). Укажите адрес вебхука как Webhook URL и включите **Alert Action**. Затем в правиле алерта (alert rule) добавьте действие **Send a notification via** с этой интеграцией. Другие вебхуки интеграции, например об установке, шаблон пропускает.

```text title="Шаблон Liquid"
{%- if data.event -%}
**{{ data.event.title }}**
Уровень: {{ data.event.level }}, правило: {{ data.triggered_rule }}
[Открыть в Sentry]({{ data.event.web_url }})
{%- endif -%}
```

### Uptime Kuma

Добавьте в Uptime Kuma уведомление типа **Webhook**: вставьте адрес вебхука в **Post URL**, а в **Request Body** оставьте **Preset - application/json**. Затем включите это уведомление у нужных мониторов. Пробное уведомление и предупреждение об истекающем сертификате приходят без данных монитора, их шаблон публикует общим текстом из поля `msg`.

```text title="Шаблон Liquid"
{%- if heartbeat -%}
{% case heartbeat.status %}{% when 0 %}**Недоступен:**{% when 1 %}**Снова работает:**{% else %}**Статус изменился:**{% endcase %} {{ monitor.name }}
{{ heartbeat.msg }}
Время: {{ heartbeat.localDateTime }}
{%- else -%}
{{ msg }}
{%- endif -%}
```

### GitHub

В репозитории откройте **Settings** > **Webhooks** > **Add webhook** и вставьте адрес вебхука в **Payload URL**. В **Content type** выберите `application/json`: в формате формы GitHub присылает JSON строкой в одном поле `payload`, и шаблон не прочитает его поля. В списке событий выберите **Let me select individual events** и отметьте **Pushes**, **Pull requests** и **Issues**. Сразу после создания GitHub присылает проверочное событие `ping`, и шаблон публикует сообщение о подключении.

```text title="Шаблон Liquid"
{%- if zen -%}
Вебхук GitHub подключён к репозиторию {{ repository.full_name }}
{%- elsif pull_request -%}
{%- if action == "opened" or action == "closed" or action == "reopened" -%}
Pull request [#{{ number }} {{ pull_request.title }}]({{ pull_request.html_url }}) в {{ repository.full_name }}
{%- case action %}{% when "opened" %} открыт{% when "reopened" %} открыт снова{% else %}{% if pull_request.merged %} влит{% else %} закрыт{% endif %}{% endcase %}, автор события: {{ sender.login }}
{%- endif -%}
{%- elsif issue -%}
{%- if action == "opened" or action == "closed" or action == "reopened" -%}
Задача [#{{ issue.number }} {{ issue.title }}]({{ issue.html_url }}) в {{ repository.full_name }}
{%- case action %}{% when "opened" %} открыта{% when "reopened" %} открыта снова{% else %} закрыта{% endcase %}, автор события: {{ sender.login }}
{%- endif -%}
{%- elsif pusher and commits.size > 0 -%}
**{{ pusher.name }}** отправил(а) коммиты в ветку `{{ ref | remove_first: "refs/heads/" }}` репозитория {{ repository.full_name }} ([изменения]({{ compare }}))
{%- for commit in commits limit: 5 %}
- [{{ commit.id | slice: 0, 7 }}]({{ commit.url }}) {{ commit.message | newline_to_br | split: "<br />" | first }}
{%- endfor -%}
{%- endif -%}
```

### amoCRM

В amoCRM откройте **амоМаркет**, нажмите **WEB HOOKS** в правом верхнем углу, вставьте адрес вебхука и отметьте для сделок добавление и смену статуса. amoCRM присылает форму (`application/x-www-form-urlencoded`), и Пачка разбирает её во вложенные объекты: сделки лежат в `leads.add` и `leads.status` под ключами `"0"`, `"1"` и так далее, поэтому шаблон перебирает их циклом. Этап воронки приходит числом в поле `status_id`, названий этапов в запросе нет.

```text title="Шаблон Liquid"
{%- for item in leads.add %}
Новая сделка №{{ item[1].id }}: **{{ item[1].name }}**
{%- endfor -%}
{%- for item in leads.status %}
Сделка №{{ item[1].id }} **{{ item[1].name }}** перешла на другой этап
{%- endfor -%}
```

amoCRM отключает вебхук, если тот часто отвечает ошибкой, например `429` при массовом изменении сделок. Включить его снова можно в тех же настройках, а как не упираться в предел — в разделе [Поток уведомлений](#potok-uvedomleniy).

### Битрикс24

В Битрикс24 откройте **Разработчикам** > **Готовые сценарии** > **Другое** > **Исходящий вебхук**, укажите адрес вебхука как URL обработчика и выберите событие, например `ONCRMDEALADD` (создание сделки). Битрикс24 присылает форму с названием события и идентификатором сделки, а название и сумму сделки в запрос не кладёт. Поэтому шаблон публикует ссылку на сделку. Чтобы показать в сообщении поля сделки, нужен отдельный запрос к REST API Битрикс24: это задача для [n8n](/guides/n8n/overview) или своего обработчика.

```text title="Шаблон Liquid"
{%- case event -%}
{%- when "ONCRMDEALADD" -%}
Новая сделка: [№{{ data.FIELDS.ID }}](https://{{ auth.domain }}/crm/deal/details/{{ data.FIELDS.ID }}/)
{%- when "ONCRMDEALUPDATE" -%}
Сделка изменена: [№{{ data.FIELDS.ID }}](https://{{ auth.domain }}/crm/deal/details/{{ data.FIELDS.ID }}/)
{%- endcase -%}
```

## Ответ вебхука

На принятый запрос вебхук отвечает `200` с коротким текстом в теле, по которому видно, что стало с сообщением (у [проверочного запроса](#pole-dlya-verifikatsii) ответ свой):

| Тело ответа | Что произошло |
| --- | --- |
| `OK` | Сообщение принято и поставлено в очередь на публикацию |
| `empty_message` | Результат шаблона пустой или длиннее 40 000 символов, сообщение не публикуется |
| `syntax_error` | В шаблоне Liquid синтаксическая ошибка, и вместо сообщения в чаты публикуется текст `Ошибка в шаблоне: …` |

Ответ `OK` ещё не гарантирует публикацию. Сообщение не появится, если результат шаблона укладывается в 40 000 символов, но длиннее [предела длины текста](/api/limits#dlina-teksta) в байтах, как бывает с длинным текстом на кириллице. Не появится оно и тогда, когда бот не состоит ни в одной беседе или канале. Ошибка в шаблоне Mustache тоже публикуется в чаты текстом ошибки, но вебхук отвечает на неё `OK`.

Запрос, который вебхук не принял, получает код ошибки:

| Код | Причина |
| --- | --- |
| `400` | Тело запроса не удалось разобрать |
| `403` | Вебхук заблокирован, обратитесь в поддержку Пачки |
| `404` | Адрес вебхука неизвестен или вебхук выключен |
| `415` | Формат тела не поддерживается, подробнее в разделе [Ограничения](#ogranicheniya) |
| `422` | Запрос не подходит выбранному источнику, например событие GitLab, по которому Пачка не публикует сообщение |
| `429` | Превышен предел запросов к адресу, подробнее в разделе [Поток уведомлений](#potok-uvedomleniy) |

## Ограничения

> **Внимание:** Входящий вебхук публикует сообщение во **все беседы и каналы**, где состоит бот, кроме архивных.
  Выбрать один чат, написать в тред или в личные сообщения он не может.


Разослать уведомления по разным чатам можно без программирования:

- **Бот на каждый чат.** Заведите отдельного бота для каждого чата и укажите адрес его вебхука в нужном правиле сервиса. Alertmanager и Zabbix умеют сами разводить уведомления по адресам: через маршруты и через разных получателей. Чтобы такого бота не добавили в другой чат, включите у него настройку [Ограничить одним чатом](/guides/bots/settings#ogranichit-odnim-chatom).
- **n8n.** Один сценарий принимает запрос и выбирает чат по содержимому, как в примере [Уведомления из внешнего сервиса](/guides/n8n/workflows#uvedomleniya-iz-vneshnego-servisa). Сравнение со входящим вебхуком — в разделе [Входящий вебхук или n8n](#vhodyaschiy-vebhuk-ili-n8n).

Из своего кода сообщение в конкретный чат, тред или личные сообщения отправляют методом [Новое сообщение](/api/messages/create) с токеном бота.

Сам запрос ограничен форматом и длиной:

- **Формат запроса** — Пачка принимает тело в форматах `application/json`, `application/x-www-form-urlencoded` и `multipart/form-data`. Передавайте формат в заголовке `Content-Type`: на запрос с другим форматом вебхук отвечает `415` и перечисляет допустимые форматы в тексте ответа, сообщение не публикуется.
- **Длина сообщения** — та же, что у обычного сообщения: предел указан в разделе [Длина текста](/api/limits#dlina-teksta). Что вебхук отвечает на слишком длинный результат шаблона — в разделе [Ответ вебхука](#otvet-vebhuka).

### Поток уведомлений

У каждого адреса вебхука свой предел запросов в секунду, число указано на странице [Лимиты](/api/limits#vhodyaschie-vebhuki). Запросы сверх предела получают `429` с заголовком `Retry-After`, и сообщения из них не публикуются. Повторит ли отклонённый запрос сам сервис, зависит от него: Alertmanager, например, повторяет только ответы `5xx`, и такое уведомление теряется.

Чтобы уложиться в предел при потоке алертов:

- **Собирайте уведомления в один запрос.** Группируйте алерты на стороне сервиса, например через `group_by` в Alertmanager, и выводите их в одном сообщении циклом по массиву, как в [шаблоне для Alertmanager](#prometheus-alertmanager).
- **Разносите сервисы по разным ботам.** Предел считается для каждого адреса отдельно, поэтому у каждого бота он свой.

## Безопасность адреса

Запрос на адрес вебхука не требует токена или подписи: кто знает адрес, тот публикует сообщения от имени бота во все его чаты. Храните адрес как пароль: в настройках сервиса и секретах CI. Не публикуйте его в репозиториях, задачах трекера, на скриншотах и в коде, который выполняется в браузере.

Если адрес утёк, получите новый:

1. Скопируйте шаблон и запишите остальные настройки вкладки **Входящий вебхук**: удаление вебхука их сотрёт.
2. Нажмите **Удалить вебхук** внизу вкладки и подтвердите удаление. Прежний адрес сразу начнёт отвечать `404`.
3. Нажмите **Включить**, выберите источник и верните формат шаблона, шаблон и настройки. У вебхука будет новый адрес.
4. Укажите новый адрес во всех сервисах, которые отправляли запросы на прежний.

Токены бота и исходящий вебхук при этом не меняются.

## Через API

Все эти настройки можно задать и программно — в объекте `webhook` методов [Новый бот](/api/bots/create) и [Редактирование бота](/api/bots/update):

- `kind` — источник: `simple` для своего формата, `gitlab` или `grafana`
- `template` — шаблон сообщения
- `template_engine` — шаблонизатор (`liquid` или `mustache`)
- `challenge_key` — поле для верификации
- `link_preview_enabled` — показывать превью ссылок

Чтобы удалить входящий вебхук, как кнопкой **Удалить вебхук**, передайте `kind: null`: адрес перестаёт работать, шаблон и настройки сбрасываются, а при следующем включении у вебхука будет новый адрес. В CLI это `pachca bots update <id> --kind null`, в n8n — операция **Bot** > **Update** со значением **None** в поле **Kind**.

Текущие значения возвращаются в объекте бота и доступны через метод [Информация о боте](/api/bots/get). Если у токена есть скоуп `bots:write` и вы можете управлять токенами бота, этот метод отдаёт и адрес вебхука в поле `webhook.url`, и тело последнего запроса на него в поле `webhook.last_request_body`: по нему видно, что именно прислал сервис. При тех же правах адрес приходит и в ответе методов [Новый бот](/api/bots/create) и [Редактирование бота](/api/bots/update), отдельный запрос за ним не нужен.

Бот, созданный через API, принимает запросы в своём формате сразу, с шаблонизатором Liquid по умолчанию. Пустой бот, созданный с `empty: true`, входящего вебхука не имеет, пока ему не задали `kind`, а шаблонизатор у него по умолчанию Mustache. Mustache ставится и после удаления входящего вебхука, когда его включают снова. Чтобы шаблон работал на Liquid, передайте `template_engine: "liquid"` вместе с `kind`.
