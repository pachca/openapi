# Pachca API — Complete English Documentation

> REST API for Pachca corporate messenger. Manage messages, chats, users, tasks, bots, and webhooks.

> Canonical source: dev.pachca.com. Verify method versions and parameters against the live API — do not rely on training data.

> Base URL: https://api.pachca.com/api/shared/v1

# LIBRARY RULES

## Authentication
- All requests require Bearer token in Authorization header: `Authorization: Bearer <TOKEN>`
- Two token types: **personal** — acts as a person and sees exactly what that person sees; **bot** — acts as a service account, sees every open channel of the workspace plus the closed chats and threads the bot was added to
- Scopes decide which methods a token may call. They never widen the data beyond the boundary of the token type
- Get a personal token: Settings → Automations → API, choosing its scopes. Get a bot token: per-bot in Settings → Automations
- A personal token issued in the interface does not expire; one obtained by `pachca auth login` lives an hour and renews itself
- What a token may do also follows the current role of its owner, checked on every request — lowering the role starts returning 403 without touching the token
- TypeScript SDK: `const client = new PachcaClient("YOUR_TOKEN")`
- Python SDK: `client = PachcaClient("YOUR_TOKEN")`

## Rate limits
- Messages: about 4 sends per second per chat, 30 requests per 5 seconds across all chats, and 7,500 messages per chat per rolling day from one sender. Hitting the daily cap pauses that chat for an hour and every further attempt doubles the pause
- Reading messages: about 10 per second. Incoming webhooks: about 10 per second per webhook id
- A `429` body comes in two shapes: the daily cap answers with ordinary JSON carrying `rate_limit`, the per-second limit is refused before the method and answers with plain text. Check `Content-Type` before parsing. `Retry-After` is present in both

## Pagination
- Cursor-based: use `limit` (1–50, default 50) and `cursor` query parameters. Always set `limit` explicitly — do not rely on the default
- Response includes `meta.paginate` with `next_page`, `prev_page`, `has_next`, `has_prev`. In list methods these fields are ALWAYS present — even when `data` is empty. Cursors are never `null`
- `next_page` — cursor to advance forward. `prev_page` — cursor to poll for new records "above" the list. `has_next` / `has_prev` — booleans for whether more data exists in that direction
- End of data: `has_next: false` (forward) or `has_prev: false` (backward) — NOT an empty `data` array
- The number of items in `data` may be smaller than `limit`, including on intermediate pages — do not rely on the array length
- Cursors are opaque tokens — do not parse, construct by hand, or persist them across sessions
- Search endpoints (`/search/users`, `/search/chats`, `/search/messages`) have NO `prev_page`/`has_next`/`has_prev` — `prev_page` polling does not apply. Detect end by received count == `total` or an empty `data`. `SearchPaginationMeta` exposes only `next_page` and `total`
- TypeScript auto-pagination: `client.users.listUsersAll()` returns flat array of all results
- Python auto-pagination: `await client.users.list_users_all()` returns list of all results
- Available for: users, chats, messages, members, tags, reactions, tasks, audit events, webhook events

## Rate Limiting
- Messages (POST/PUT/DELETE /messages): ~4 req/sec per chat (burst: 30/sec for 5s)
- Message read (GET /messages): ~10 req/sec per token
- Other endpoints: ~50 req/sec per token
- Webhook events read (GET /webhooks/events): ~5 req / 2 sec per token
- Incoming webhooks: ~10 req/sec per webhook id (counted by the identifier in the path, e.g. `/webhooks/user123`)
- On `429 Too Many Requests`: respect `Retry-After` header value (seconds)
- Recommended retry strategy: exponential backoff with jitter — base delay × 2^attempt × random(0.5–1.5)
- SDK (@pachca/sdk, pachca-sdk) handles retry automatically: 3 retries, respects Retry-After, exponential backoff for 5xx

## Webhooks (Real-time Events)
- Create a bot in Pachca: Automations → Integrations → Bots
- Set webhook URL in bot settings → Outgoing Webhook tab
- Events: `new_message`, `edit_message`, `delete_message`, `new_reaction`, `delete_reaction`, `button_pressed`, `view_submit`, `chat_member_changed`, `company_member_changed`, `link_shared`
- Verify: HMAC-SHA256 of raw body with bot's Signing Secret
- Header: `Pachca-Signature` contains hex digest
- Replay protection: check `webhook_timestamp` within ±60 seconds of current time
- Alternative to webhooks: polling via GET /webhooks/events (enable "Save event history" in bot settings)
- IP whitelist: Pachca webhook IP is `37.200.70.177`

## File Uploads (3-step process)
- Step 1: POST /uploads → get S3 presigned params (`direct_url`, `key`, `policy`, `x-amz-signature`, etc.)
- Step 2: POST to `direct_url` (external S3 URL, NOT a Pachca API endpoint) with multipart/form-data — all params + `file` as LAST field
- Step 3: Replace `${filename}` in `key` with actual filename, include in message `files` array
- Note: `direct_url` is an external S3 presigned URL and does not require Authorization header

## User Status
- Get any user's status: GET /users/{id}/status → `{ emoji, title, expires_at, is_away, away_message }`
- Set own status: PUT /profile/status `{ status: { emoji, title, expires_at, is_away, away_message } }`
- Clear own status: DELETE /profile/status
- Admin can manage any user: PUT /users/{id}/status, DELETE /users/{id}/status
- No real-time presence webhooks — use polling with ≥60s interval for monitoring status changes

## Error Handling
- `400`: validation errors — `{ errors: [{ key, value, message, code }] }` with codes: `blank`, `invalid`, `taken`, `too_short`, `too_long`, `not_a_number`
- `401`: unauthorized — `{ error, error_description }` (OAuthError)
- `403`: forbidden — insufficient permissions. May return ApiError (business logic) or OAuthError (`insufficient_scope`). On `insufficient_scope` the missing scope is in the `WWW-Authenticate` response header (`scope="…"`, RFC 6750) — read it from there instead of parsing the message text
- `404`: not found
- `409`: conflict (duplicate)
- `422`: unprocessable — `{ errors: [{ key, value, message, code }] }`
- `429`: rate limited — respect `Retry-After` header, use exponential backoff with jitter
- SDK auto-retries `429` and `5xx` errors (3 attempts with exponential backoff)

## Idempotency and Reliability
- Pachca API operations are NOT idempotent by default — duplicate POST requests create duplicate resources
- Client-side deduplication: track request IDs, check before sending, store results with TTL
- Webhooks use at-least-once delivery — handlers MUST be idempotent (dedup by event fields: id + type + event)
- For multi-step operations: implement compensating actions (saga pattern) for failure recovery
- Separate critical operations (create chat) from non-critical (send welcome message) with independent error handling

## SDK (Typed Clients for 6 Languages)
- Unified pattern: `PachcaClient(token)` → `client.service.method(request)`
- **Input**: path params and body fields (≤2) expand to method arguments; otherwise a single request object
- **Output**: if API response has a single `data` field, SDK returns its contents directly
- Service, method, and field names match operationId and parameters from OpenAPI

## CLI (Command-Line Interface)
- Zero-install: `npx -y @pachca/cli <command> --token <TOKEN>` (always latest). Or `npm install -g @pachca/cli`
- Every API endpoint is a typed command: `pachca <section> <action> --flags` (e.g. `pachca messages create --entity-id=123 --content="Hi"`)
- Non-interactive by default in pipes/CI: emits JSON, no prompts or spinner; a missing required flag returns an error instead of prompting
- Token via `PACHCA_TOKEN` env or `--token` flag — nothing is written to disk
- Branch on exit codes (`0` success, `3` forbidden, `4` not found); JSON errors carry a `type` field (`PACHCA_AUTH_ERROR`, `PACHCA_VALIDATION_ERROR`, …)
- **Per-endpoint docs on demand — you do not need to load this whole file.** To get just the endpoint you need:
  - `npx -y @pachca/cli api ls` — list every endpoint (`METHOD PATH SUMMARY SCOPE`; add `--json` for machine-readable)
  - `npx -y @pachca/cli api <METHOD> <path> --describe` — parameters, body, scope, equivalent typed command
  - `npx -y @pachca/cli api <METHOD> <path> --spec` — OpenAPI fragment (request/response schemas)
  - `npx -y @pachca/cli api <METHOD> <path> --docs` — full Markdown reference for that one endpoint
- Arbitrary request to any endpoint: `npx -y @pachca/cli api <METHOD> <path> -f field=value` (or `-F` typed, `--input body.json`, `--data '{...}'`)
- Any documentation page is also available as Markdown — append `.md` to its URL (e.g. `https://dev.pachca.com/guides/webhook/overview.md`)

## How to paginate through results

### TypeScript SDK — auto-pagination
```typescript
// Returns all results as a flat array (handles cursors automatically)
const allUsers = await client.users.listUsersAll()
console.log(`Total: ${allUsers.length}`)

// Manual pagination with cursor control using has_next
let cursor: string | undefined
let hasNext = true
while (hasNext) {
  const response = await client.users.listUsers({ limit: 50, cursor })
  for (const user of response.data) {
    console.log(user.firstName, user.lastName)
  }
  cursor = response.meta.paginate.nextPage
  hasNext = response.meta.paginate.hasNext
}
```

### Python SDK — auto-pagination
```python
# Returns all results as a list (handles cursors automatically)
all_users = await client.users.list_users_all()
print(f"Total: {len(all_users)}")

# Manual pagination with cursor control using has_next
from pachca.models import ListUsersParams

cursor = None
has_next = True
while has_next:
    response = await client.users.list_users(ListUsersParams(limit=50, cursor=cursor))
    for user in response.data:
        print(user.first_name, user.last_name)
    cursor = response.meta.paginate.next_page
    has_next = response.meta.paginate.has_next
```

Auto-pagination methods: `listUsersAll()`, `listChatsAll()`, `listChatMessagesAll()`, `listMembersAll()`, `listTagsAll()`, `listTasksAll()`, `searchMessagesAll()`, `searchChatsAll()`, `searchUsersAll()`, `listReactionsAll()`, `getAuditEventsAll()`, `getWebhookEventsAll()`.

### Polling new data with prev_page

Use the `prev_page` cursor to efficiently poll for new records that appear "above" the list (newer than your first page) without refetching everything:

```typescript
// Initial fetch — save prev_page
const initial = await client.chats.listChats({ limit: 50 })
let prevCursor = initial.meta.paginate.prevPage
const chats = new Map(initial.data.map(c => [c.id, c]))

// Poll periodically — drain newer records via prev_page until has_prev is false
setInterval(async () => {
  let hasPrev = true
  while (hasPrev) {
    const response = await client.chats.listChats({ limit: 50, cursor: prevCursor })
    // Deduplicate by id — records may reappear if their sort field changed
    for (const chat of response.data) {
      chats.set(chat.id, chat)
    }
    prevCursor = response.meta.paginate.prevPage
    hasPrev = response.meta.paginate.hasPrev
  }
}, 5000)
```

## How to create chats and manage members

### TypeScript SDK
```typescript
import { PachcaClient, MessageEntityType } from "@pachca/sdk"

const client = new PachcaClient("YOUR_TOKEN")

// Create a group chat with initial members
const chat = await client.chats.createChat({
  chat: { name: "Project Discussion", memberIds: [1, 2, 3], channel: false, public: false }
})
console.log("Created chat:", chat.id, chat.name)

// Add more members later
await client.members.addMembers(chat.id, { memberIds: [4, 5] })

// Remove a member
await client.members.removeMember(chat.id, 5)

// List current members
const members = await client.members.listMembersAll(chat.id)
console.log("Members:", members.map(m => m.firstName))

// Send a message to the chat
await client.messages.createMessage({
  message: { entityType: MessageEntityType.Discussion, entityId: chat.id, content: "Welcome everyone!" }
})
```

### Python SDK
```python
from pachca.client import PachcaClient
from pachca.models import ChatCreateRequest, ChatCreateRequestChat, MessageCreateRequest, MessageCreateRequestMessage, AddMembersRequest

client = PachcaClient("YOUR_TOKEN")

# Create a group chat with initial members
chat = await client.chats.create_chat(ChatCreateRequest(
    chat=ChatCreateRequestChat(name="Project Discussion", member_ids=[1, 2, 3], channel=False, public=False)
))
print("Created chat:", chat.id, chat.name)

# Add more members later
await client.members.add_members(chat.id, AddMembersRequest(member_ids=[4, 5]))

# List current members
members = await client.members.list_members_all(chat.id)

# Send a message to the chat
await client.messages.create_message(MessageCreateRequest(
    message=MessageCreateRequestMessage(entity_type="discussion", entity_id=chat.id, content="Welcome everyone!")
))
```

Chat types: `channel: true` creates a channel (one-way announcements), `channel: false` creates a group chat (everyone can write). `public: true` makes it visible to all workspace members.

## How to set up webhooks for real-time updates

### Step-by-step setup
1. Create a bot in Pachca: **Automations** → **Integrations** → **Bots**
2. In bot settings, go to **Outgoing Webhook** tab and set your HTTPS URL
3. Copy the **Signing Secret** for signature verification
4. Select event types: new messages, reactions, button presses, form submissions, etc.
5. Add the bot to chats where you want to receive events (global events like company member changes work without adding to chat)

### TypeScript webhook handler (Express.js)
```typescript
import express from "express"
import crypto from "crypto"

const SIGNING_SECRET = "your_signing_secret" // From bot settings → Outgoing Webhook
const app = express()

app.post("/webhook", express.raw({ type: "application/json" }), (req, res) => {
  // Step 1: Verify HMAC-SHA256 signature
  const signature = crypto.createHmac("sha256", SIGNING_SECRET)
    .update(req.body).digest("hex")
  if (signature !== req.headers["pachca-signature"]) {
    return res.status(401).send("Invalid signature")
  }

  // Step 2: Check timestamp for replay protection (±60 seconds)
  const event = JSON.parse(req.body.toString())
  if (Math.abs(Date.now() / 1000 - event.webhook_timestamp) > 60) {
    return res.status(401).send("Expired event")
  }

  // Step 3: Process event by type
  switch (event.type) {
    case "message":
      if (event.event === "new") console.log("New message:", event.content, "from user:", event.user_id)
      if (event.event === "update") console.log("Message edited:", event.id)
      if (event.event === "delete") console.log("Message deleted:", event.id)
      break
    case "reaction":
      console.log(event.event === "new" ? "Reaction added:" : "Reaction removed:", event.emoji)
      break
    case "button":
      console.log("Button pressed:", event.data, "by user:", event.user_id)
      // Use event.trigger_id within 3 seconds to open a form
      break
    case "view_submit":
      console.log("Form submitted:", event.payload)
      break
  }

  res.status(200).send("OK")
})
app.listen(3000)
```

### Python webhook handler (Flask)
```python
import hmac, hashlib, json, time
from flask import Flask, request, abort

SIGNING_SECRET = "your_signing_secret"  # From bot settings → Outgoing Webhook
app = Flask(__name__)

@app.route("/webhook", methods=["POST"])
def webhook():
    raw_body = request.get_data()

    # Step 1: Verify HMAC-SHA256 signature
    expected = hmac.new(SIGNING_SECRET.encode(), raw_body, hashlib.sha256).hexdigest()
    if expected != request.headers.get("Pachca-Signature"):
        abort(401)

    # Step 2: Check timestamp for replay protection
    event = json.loads(raw_body)
    if abs(time.time() - event["webhook_timestamp"]) > 60:
        abort(401)

    # Step 3: Process event by type
    if event["type"] == "message" and event["event"] == "new":
        print("New message:", event["content"], "from user:", event["user_id"])
    elif event["type"] == "button":
        print("Button pressed:", event["data"])

    return "OK", 200
```

### Webhook event types
| Event type | Description | Fields |
|-----------|-------------|--------|
| message (new) | New message in chat | id, content, user_id, chat_id, entity_type, entity_id, created_at, url |
| message (update) | Message edited | id, content, user_id, chat_id |
| message (delete) | Message deleted | id, user_id, chat_id |
| reaction (new/delete) | Reaction added/removed | message_id, user_id, emoji, chat_id |
| button | Button pressed | message_id, user_id, data, trigger_id, chat_id |
| view_submit | Form submitted | payload (form field values), user_id, trigger_id |
| chat_member (new/delete) | Member added/removed from chat | chat_id, user_id, event |
| company_member (new/update/delete) | Workspace member changes | user_id, event (no chat needed) |
| link_shared | URL shared (unfurl bots) | url, message_id, chat_id |

### Alternative: Polling (when webhook URL is not available)
Enable "Save event history" in bot settings, then poll:
```typescript
// Poll for events periodically
const events = await client.bots.getWebhookEvents()
for (const event of events.data) {
  processEvent(event)
  await client.bots.deleteWebhookEvent(event.id) // Remove processed event
}
```

## How to handle rate limits and implement retry logic

Both SDKs handle retry automatically — 3 retries with exponential backoff for `429` and `5xx` errors. No extra code needed:

### TypeScript SDK
```typescript
import { PachcaClient, ApiError } from "@pachca/sdk"

const client = new PachcaClient("YOUR_TOKEN")

// SDK retries 429 and 5xx automatically (3 attempts, exponential backoff)
// Just call methods normally — retries are transparent
const users = await client.users.listUsersAll()

// If all retries are exhausted, ApiError is thrown
try {
  await client.messages.createMessage({
    message: { entityId: 12345, content: "Hello" }
  })
} catch (error) {
  if (error instanceof ApiError) {
    // After 3 retries, the error is surfaced — check error.errors for details
    for (const e of error.errors ?? []) {
      console.error(e.key, e.message)
    }
  }
}
```

### Python SDK
```python
from pachca.client import PachcaClient
from pachca.models import ApiError

client = PachcaClient("YOUR_TOKEN")

# SDK retries 429 and 5xx automatically (3 attempts, exponential backoff)
# Just call methods normally — retries are transparent
users = await client.users.list_users_all()

# If all retries are exhausted, ApiError is raised
try:
    await client.messages.create_message(request)
except ApiError as e:
    # After 3 retries, the error is surfaced — check e.errors for details
    for err in e.errors:
        print(err.key, err.message)
```

Rate limits by endpoint category:
- Messages send/edit/delete: ~4 req/sec per chat (burst: 30/sec for 5s)
- Messages read: ~10 req/sec per token
- All other endpoints: ~50 req/sec per token
- Webhook events read (GET /webhooks/events): ~5 req / 2 sec per token
- Incoming webhooks: ~10 req/sec per webhook id (counted by path identifier)
- On 429: SDK respects `Retry-After` header automatically

## How to upload files and attach to messages

File upload is a 3-step process: get presigned params → upload to S3 → attach to message.

### TypeScript SDK
```typescript
import { PachcaClient, FileType } from "@pachca/sdk"
import fs from "fs"
import path from "path"

const client = new PachcaClient("YOUR_TOKEN")

const filePath = "./report.pdf"
const fileName = path.basename(filePath)
const fileBuffer = fs.readFileSync(filePath)

// Step 1: Get S3 presigned upload parameters
const params = await client.files.getUploadParams()

// Step 2: Upload file to S3 (direct_url is an external presigned URL, not Pachca API)
await client.files.uploadFile(params.directUrl, {
  contentDisposition: params.contentDisposition,
  acl: params.acl,
  policy: params.policy,
  xAmzCredential: params.xAmzCredential,
  xAmzAlgorithm: params.xAmzAlgorithm,
  xAmzDate: params.xAmzDate,
  xAmzSignature: params.xAmzSignature,
  key: params.key,
  file: new File([fileBuffer], fileName)
})

// Step 3: Attach file to message (replace ${filename} in key with actual name)
const fileKey = params.key.replace("${filename}", fileName)
await client.messages.createMessage({
  message: {
    entityId: 12345,
    content: "Report attached",
    files: [{ key: fileKey, name: fileName, fileType: FileType.File, size: fileBuffer.length }]
  }
})
```

### Python SDK
```python
from pachca.client import PachcaClient
from pachca.models import (
    FileUploadRequest, MessageCreateRequest, MessageCreateRequestMessage,
    MessageCreateRequestFile, FileType
)
import os

client = PachcaClient("YOUR_TOKEN")

file_path = "report.pdf"
file_name = os.path.basename(file_path)

# Step 1: Get S3 presigned upload parameters
params = await client.files.get_upload_params()

# Step 2: Upload file to S3 (direct_url is an external presigned URL, not Pachca API)
with open(file_path, "rb") as f:
    await client.files.upload_file(
        direct_url=params.direct_url,
        request=FileUploadRequest(
            content_disposition=params.content_disposition,
            acl=params.acl,
            policy=params.policy,
            x_amz_credential=params.x_amz_credential,
            x_amz_algorithm=params.x_amz_algorithm,
            x_amz_date=params.x_amz_date,
            x_amz_signature=params.x_amz_signature,
            key=params.key,
            file=f.read()
        )
    )

# Step 3: Attach file to message (replace ${filename} in key with actual name)
file_key = params.key.replace("${filename}", file_name)
await client.messages.create_message(MessageCreateRequest(
    message=MessageCreateRequestMessage(
        entity_id=12345,
        content="Report attached",
        files=[MessageCreateRequestFile(key=file_key, name=file_name, file_type=FileType.FILE, size=os.path.getsize(file_path))]
    )
))
```

File types: `FileType.File` / `FileType.FILE` (any file), `FileType.Image` / `FileType.IMAGE` (add `width` and `height`).

### Polling pattern for monitoring status changes
Pachca does not provide real-time webhooks for status/presence changes. Use polling with caching:

```typescript
const cache = new Map<number, { status: any; fetchedAt: number }>()
const CACHE_TTL = 60_000 // Minimum 60 seconds between polls per user

async function getUserPresence(userId: number) {
  const cached = cache.get(userId)
  if (cached && Date.now() - cached.fetchedAt < CACHE_TTL) return cached.status
  const status = await client.users.getUserStatus(userId)
  cache.set(userId, { status, fetchedAt: Date.now() })
  return status
}

// Batch refresh for a team
async function refreshTeamPresences(userIds: number[]) {
  const results = []
  for (const id of userIds) {
    cache.delete(id)
    results.push(await getUserPresence(id))
  }
  return results
}
```

Status fields: `emoji` (string), `title` (string), `expires_at` (ISO datetime or null), `is_away` (boolean), `away_message` (string). Admin can manage any user's status via PUT/DELETE /users/{id}/status.

## How to handle idempotency and partial failures in multi-service workflows

Pachca API is **NOT idempotent** — duplicate POST requests create duplicate resources. Webhooks use **at-least-once** delivery. Both require explicit handling in distributed systems.

### 1. Client-side request deduplication

```typescript
import { PachcaClient, ApiError } from "@pachca/sdk"

const client = new PachcaClient("YOUR_TOKEN")

// Idempotency layer: track requests to prevent duplicates
const requestLog = new Map<string, { result: any; expiresAt: number }>()
const DEDUP_TTL = 300_000 // 5 minutes

async function idempotentCreateMessage(idempotencyKey: string, entityId: number, content: string) {
  // Check if this request was already processed
  const existing = requestLog.get(idempotencyKey)
  if (existing && Date.now() < existing.expiresAt) {
    return existing.result // Return cached result, no duplicate created
  }

  const result = await client.messages.createMessage({
    message: { entityId, content }
  })

  // Cache result with TTL for deduplication window
  requestLog.set(idempotencyKey, { result, expiresAt: Date.now() + DEDUP_TTL })
  return result
}

// Usage: same key = same result, no duplicate message
await idempotentCreateMessage("onboard-user-42", chatId, "Welcome!")
await idempotentCreateMessage("onboard-user-42", chatId, "Welcome!") // returns cached, no duplicate
```

### 2. Webhook event deduplication

```typescript
// Webhooks deliver at-least-once — same event may arrive multiple times
const processedEvents = new Set<string>()

function handleWebhookEvent(event: any) {
  // Build unique key from event fields: type + event + id
  const eventKey = `${event.type}:${event.event}:${event.id}:${event.webhook_timestamp}`

  if (processedEvents.has(eventKey)) {
    return // Already processed, skip duplicate
  }
  processedEvents.add(eventKey)

  // Process event (idempotent handler)
  switch (event.type) {
    case "message":
      syncMessageToExternalSystem(event)
      break
    case "button":
      handleButtonPress(event)
      break
  }
}
```

### 3. Saga pattern for multi-step operations

```typescript
import { PachcaClient, MessageEntityType } from "@pachca/sdk"

const client = new PachcaClient("YOUR_TOKEN")

// Saga: create project workspace (chat + members + welcome message + task)
// Each step has a compensating action for rollback on failure

interface SagaStep {
  name: string
  execute: () => Promise<any>
  compensate: (result: any) => Promise<void>
}

async function executeSaga(steps: SagaStep[]) {
  const completed: { step: SagaStep; result: any }[] = []

  for (const step of steps) {
    try {
      const result = await step.execute()
      completed.push({ step, result })
    } catch (error) {
      console.error(`Saga failed at step "${step.name}":`, error)

      // Compensate in reverse order (undo completed steps)
      for (const { step: completedStep, result } of completed.reverse()) {
        try {
          await completedStep.compensate(result)
          console.log(`Compensated: ${completedStep.name}`)
        } catch (compensateError) {
          // Log for manual intervention — compensation itself failed
          console.error(`CRITICAL: Failed to compensate "${completedStep.name}":`, compensateError)
        }
      }
      throw new Error(`Saga rolled back at step "${step.name}"`)
    }
  }

  return completed.map(c => c.result)
}

// Define saga steps with compensating actions
async function createProjectWorkspace(projectName: string, memberIds: number[]) {
  let chatId: number

  const steps: SagaStep[] = [
    {
      name: "create-chat",
      execute: async () => {
        const chat = await client.chats.createChat({
          chat: { name: projectName, memberIds, channel: false, public: false }
        })
        chatId = chat.id
        return chat
      },
      compensate: async (chat) => {
        // No delete chat API — archive instead
        await client.chats.archiveChat(chat.id)
      },
    },
    {
      name: "send-welcome",
      execute: async () => {
        return await client.messages.createMessage({
          message: {
            entityType: MessageEntityType.Discussion,
            entityId: chatId,
            content: `Project **${projectName}** workspace created!`
          }
        })
      },
      compensate: async (message) => {
        await client.messages.deleteMessage(message.id)
      },
    },
    {
      name: "create-task",
      execute: async () => {
        return await client.tasks.createTask({
          task: { kind: "reminder", content: `Set up ${projectName}`, performerIds: memberIds }
        })
      },
      compensate: async (task) => {
        await client.tasks.deleteTask(task.id)
      },
    },
  ]

  return executeSaga(steps)
}
```

### 4. State reconciliation across microservices

```typescript
// Periodic reconciliation: ensure external system matches Pachca state
async function reconcileUsers(externalDb: Map<number, any>) {
  const pachcaUsers = await client.users.listUsersAll()

  for (const user of pachcaUsers) {
    const external = externalDb.get(user.id)
    if (!external) {
      // User exists in Pachca but not in external system — sync
      await syncUserToExternal(user)
    } else if (external.lastActivityAt < user.lastActivityAt) {
      // Pachca has newer activity — update external
      await updateExternalUser(user)
    }
  }

  // Check for users in external system that no longer exist in Pachca
  for (const [id, external] of externalDb) {
    if (!pachcaUsers.find(u => u.id === id)) {
      await markExternalUserDeleted(id)
    }
  }
}

// Schedule reconciliation as fallback for missed webhooks
setInterval(() => reconcileUsers(externalDb), 15 * 60 * 1000) // Every 15 minutes
```

### Key principles for Pachca API distributed systems
- **All POST endpoints create new resources** — never assume idempotency, always deduplicate on client side
- **Webhooks are at-least-once** — handlers MUST be idempotent (dedup by event id + type + timestamp)
- **Separate critical from non-critical operations** — chat creation (critical) vs welcome message (non-critical) should fail independently
- **Use saga pattern with compensating actions** — for multi-step workflows where partial completion is worse than full rollback
- **Implement periodic reconciliation** — webhooks can be missed; polling + reconciliation ensures eventual consistency
- **Track operation state externally** — store saga progress in your database, not in memory, for crash recovery
- **SDK auto-retry handles transient failures** — 429 and 5xx are retried 3 times automatically, so sagas should only compensate on permanent failures (4xx)

# API Reference

Base URL: `https://api.pachca.com/api/shared/v1`

All endpoints require `Authorization: Bearer <TOKEN>` header.

## OAuth

### GET /api/shared/v1/oauth/token/info
Information about the token the request itself was made with: its scopes, its owner, and the dates it was created and last used. The token itself comes back masked — only the first 8 and the last 4 characters are visible. The method requires no scope and answers any valid token, personal or bot. That makes it convenient for checking a token before work: a live one answers `200`, a revoked or expired one `401`, and the list of scopes immediately shows which methods are available to this token. Whose token it is can be seen from `user_id`. The owner's full profile is returned by [Own profile](/api/profile/get).

## Chats

### GET /api/shared/v1/chats
By default — the conversations, channels, and direct messages the token owner belongs to. With `availability=public` the method returns instead all public chats of the workspace, including the ones the caller has not joined. Threads never come in this list; for them there is [List threads](/api/threads/list). `archived=true` does not switch the results to the archive, it adds archived chats to the active ones.
Parameters: sort?, order?, availability?, archived?, last_message_at_after?, last_message_at_before?, personal?, limit?, cursor?

### POST /api/shared/v1/chats
Creates a conversation or a channel. The token owner becomes the chat owner, and this role is not transferred later on. To create a one-on-one direct message with a user, use the [New message](/api/messages/create) method. To discuss a particular message there is no need to create a chat — a thread is started under it with the [New thread](/api/threads/add) method. A conversation on a single topic needs no permanent place either: there is the [New standalone thread](/api/threads/create) method for it. Members can be passed right away: `member_ids` adds them one by one, `group_tag_ids` brings in everyone who belongs to the tag and keeps the membership up to date afterwards. IDs that do not exist in the workspace, as well as suspended and deleted employees, are silently dropped — the response is successful but the employee is not in the chat, so check the membership in the response.
Body: { chat: { name*, member_ids, group_tag_ids, channel, public } }

### POST /api/shared/v1/chats/exports
Order an export of the workspace messages for a period. The archive is prepared in the background, so the response comes back empty and contains no export identifier. The number of the finished export arrives in the `export_id` field of the webhook sent to the address from `webhook_url`. The employee who ordered it also receives an email and a notification in Pachca with a link of the form `/full_exports/{id}` — the number in it is the identifier. The webhook address is optional, but without it a program has nowhere to take the number from: only the email and the notification to whoever ordered it are left. With that identifier the archive is fetched by the [Download export archive](/api/chats/download-export) method.
Body: { start_at*, end_at*, webhook_url, chat_ids, skip_chats_file }

### GET /api/shared/v1/chats/exports/{id}
In response to the request the server returns `302 Found` with a `Location` header containing a temporary download link for the file. Most HTTP clients automatically follow the redirect and download the file. The link is valid for 5 minutes, so download the archive right after the request. The archive itself is stored for 7 days, and only the employee who ordered the export can download it — the method refuses another employee holding the same permission.
Parameters: id

### GET /api/shared/v1/chats/{id}
The chat's details together with the list of members and the linked tags. What is written in the chat is returned by the [List chat messages](/api/messages/list) method. A private conversation the caller does not belong to responds `403`, not `404`: this method does not hide the existence of a chat. A public channel of your own workspace is returned even to someone who has not joined it. The method does not open other people's private chats to the workspace owner either — the full list of those is returned by [List workspace chats](/api/chats/list-company). Only active members come in `member_ids`: suspended ones do not make it into the list, although their membership is kept.
Parameters: id

### PUT /api/shared/v1/chats/{id}
Changes the name of a conversation or a channel and its availability. Both changes are visible to the members as a system message in the chat feed. A direct chat cannot be renamed, and neither can an archived one: [Unarchive chat](/api/chats/unarchive) it first. In a private chat the method is available to the chat owner and a chat administrator, in a public one to any employee of the workspace, even a non-member. The membership is not changed by this method; for that there are [Add users](/api/members/add) and [Remove user](/api/members/remove).
Parameters: id
Body: { chat: { name, public } }

### PUT /api/shared/v1/chats/{id}/archive
Sends a conversation or a channel to the archive: the chat disappears from the lists of all members, new messages are not accepted into it, and the history is kept. Archiving does not merely freeze the chat. All guests are removed from it and all tags are unlinked from it. The employees a tag brought in stay as ordinary members, but the membership is no longer maintained by itself. The [Unarchive chat](/api/chats/unarchive) method brings back neither the guests nor the tag links. Threads created in the chat stay open: they can still be written to after archiving. A direct chat and a thread are not sent to the archive. Archiving a chat that is already archived responds `403`.
Parameters: id

### PUT /api/shared/v1/chats/{id}/unarchive
Brings a conversation or a channel back from the archive: the chat appears in the lists again, and it becomes possible to write into it again. On a chat that is not in the archive anyway the method responds with success.
Parameters: id

### GET /api/shared/v1/company/chats
The conversations and channels of the whole workspace, including private ones you are not a member of. Direct messages and threads are not returned. Both active and archived chats are returned by default. The `activity` parameter keeps only one of the states in the selection. The method is available to the workspace owner. Every request is written to the [audit log](/guides/audit-events) with the `company_chats_accessed` key.
Parameters: activity?, limit?, cursor?

## Profile

### GET /api/shared/v1/profile
The profile of the token owner. For a bot token this is the bot's own profile. The time zone from here is needed by anyone who turns human deadlines into dates: "by 3 p.m." and "by Friday" are counted in the employee's time zone, not in UTC. An empty value means the workspace time zone. Someone else's profile is returned by [Employee info](/api/users/get).

### PUT /api/shared/v1/profile/avatar
Sets or replaces the avatar of the token owner. The file is sent in `multipart/form-data` format, and the response contains only a link to the new image. `jpg`, `jpeg`, `png`, and `gif` are accepted, and an animated `gif` must be no larger than 2 MB. The image is scaled down to 1024 by 1024 pixels, and an opaque `png` is stored as `jpg`. Another employee's avatar is set by [Upload employee avatar](/api/users/update-avatar), and that is available only to the workspace owner and an administrator.
Body: { image* }

### DELETE /api/shared/v1/profile/avatar
Removes the avatar of the token owner; the interface then shows initials. If there was no avatar, the response is still `204`.

### GET /api/shared/v1/profile/status
The status of the token owner: the emoji, the title, the expiry, and away mode. If no status is set, the method returns `200` and `null` in the response body — with no wrapper object. A status whose `expires_at` has passed may still be returned for a short time until it is cleared, so check `expires_at` on the client side.

### PUT /api/shared/v1/profile/status
Sets a status for the token owner: an emoji, a caption, and, if needed, an expiry. It is available to a bot as well — the status will be visible on the bot. Away mode is turned on by this same method, with the `is_away` flag. `away_message` holds the text shown in the profile and to anyone trying to write to them or mention them. When the `expires_at` moment passes, the whole status is cleared, the mode and that text along with it. Only the fields you pass are overwritten. To extend the current status it is enough to send `expires_at` alone. An expiry that an employee names in words — "until three", "until the end of the day" — is exactly `expires_at`, not a part of the caption. It is counted in the employee's time zone, and the zone arrives in [Own profile](/api/profile/get). The emoji is required, and there must be exactly one, with no text around it. The caption is required and no longer than 50 characters.
Body: { status: { emoji*, title*, expires_at, is_away, away_message } }

### DELETE /api/shared/v1/profile/status
Removes the status from the token owner, along with away mode and its text. If there was no status, the response is still `204`, so a repeated call is safe.

## Users

### GET /api/shared/v1/users
Every employee of the workspace except the deleted ones. Suspended employees come together with the rest and are distinguished by the `suspended` field. Bots in the workspace are employees too and come in the common list with `bot: true`. But they are excluded from the results for `query`: to find a bot by name, page through the list without a search query or use [List bots](/api/bots/list). Email and phone come back as `null` if the display of personal data is turned off in the workspace and the caller is not an administrator. The profile of a single employee is returned by [Employee info](/api/users/get), and your own by [Own profile](/api/profile/get).
Parameters: query?, limit?, cursor?

### POST /api/shared/v1/users
Creates an employee in the workspace and sends them an invitation by email. Available to the workspace owner and an administrator; the method is not available to a bot. If an employee with this email address already exists in the workspace, the response is `409`. A nickname that is already taken is not treated as an error: random characters are silently appended to it, and the response comes back with the modified one. You can fill in custom properties for the employee that have been created in your workspace. You can get the current list of employee custom property IDs using the [List custom properties](/api/custom-properties/list) method. The `list_tags` field puts the employee into tags right away, and together with the tags into the chats those tags are linked to. For a guest no tags are assigned at all: the response is successful and `list_tags` in it is empty. Through the `chat_ids` parameter the employee can be added to the specified chats right at creation. To create a guest, pass `role: "guest"` — for this role `chat_ids` is required and must contain exactly one active chat the token has permission to add members to. Violating the guest access rules returns `400` with an error on the `chat_ids` field.
Body: { user*, skip_email_notify }

### GET /api/shared/v1/users/{id}
The employee's profile. A suspended employee is returned with `suspended: true`, a deleted one as `404`, like a non-existent one. A bot also comes here as an employee, with `bot: true`. Email and phone come back as `null` if the display of personal data is turned off in the workspace and the caller is not an administrator. An employee sees their own profile in full — the same one is returned by the [Own profile](/api/profile/get) method, and without the `users:read` scope.
Parameters: id

### PUT /api/shared/v1/users/{id}
Changes the employee's profile: only the fields you pass are overwritten. Custom property IDs are returned by [List custom properties](/api/custom-properties/list). The `list_tags` field replaces the whole set of tags, so send the tags that are being kept along with the new one. A removed tag takes the employee out of the chats this tag brought them into, and a name that does not exist in the workspace yet creates a new tag together with the assignment. `suspended: true` suspends the employee: they lose access but remain in chats, tags, and tasks, while `suspended: false` brings them back. An employee is removed for good by [Delete employee](/api/users/delete). The workspace owner can be edited only by themselves, and their role can be changed only to administrator. Turning a regular employee into a guest is impossible — in both cases the response is `403`. An unknown role value is silently ignored by the method: the response is successful and the role stays as it was.
Parameters: id
Body: { user: { first_name, last_name, email, phone_number, nickname, department, title, role, suspended, list_tags, custom_properties } }

### DELETE /api/shared/v1/users/{id}
Removes an employee from the workspace. This cannot be undone: they can be brought back only with a new invitation, and that will already be a different employee. What happens: they leave all conversations and channels except direct messages, all tags are taken off them, the tasks where they were the only assignee are deleted, and they are removed from the remaining ones. The messages and files they wrote stay in place. The workspace owner cannot be deleted — the method responds `403`. A repeated call responds `404`: the method no longer finds a deleted employee. If the employee is going on vacation or the dismissal is not final yet, use [Edit employee](/api/users/update) with `suspended: true`. Suspension is reversible and keeps chats, tags, and tasks.
Parameters: id

### PUT /api/shared/v1/users/{user_id}/avatar
Sets or replaces the avatar of another employee. Available to the workspace owner and an administrator; not to a bot. The workspace owner's avatar can be changed only by themselves. The file is sent in `multipart/form-data` format, and the response contains only a link to the new image. `jpg`, `jpeg`, `png`, and `gif` are accepted, an animated `gif` must be no larger than 2 MB, and the image is scaled down to 1024 by 1024 pixels. Your own avatar is set by the [Upload own avatar](/api/profile/update-avatar) method — it is available to all roles and to bots.
Parameters: user_id
Body: { image* }

### DELETE /api/shared/v1/users/{user_id}/avatar
Removes the avatar of another employee; the interface then shows initials. Available to the workspace owner and an administrator; not to a bot, and the workspace owner's avatar can be removed only by themselves. If there was no avatar, the response is still `204`.
Parameters: user_id

### GET /api/shared/v1/users/{user_id}/status
The status of another employee: the emoji, the title, the expiry, and away mode. If no status is set, the method returns `200` and `null` in the response body — with no wrapper object. A status whose `expires_at` has passed may still be returned for a short time until it is cleared, so check `expires_at` on the client side.
Parameters: user_id

### PUT /api/shared/v1/users/{user_id}/status
Sets a status for another employee — for example, "on vacation" for the time of their absence. Available to the workspace owner and an administrator; not to a bot, even with the scope. This same method turns on away mode for that employee with the `is_away` flag and sets the `away_message` text that anyone reaching out to them will see. The status is seen by everyone who sees the employee in the workspace. Only the fields you pass are overwritten, so someone else's status can be extended with `expires_at` alone. An expiry named in words is `expires_at`, not a part of the caption, and it is counted in the time zone of the employee the status is set for. The emoji is required and there must be exactly one; the caption is required and no longer than 50 characters. Your own status is set by the [New own status](/api/profile/update-status) method — it is available to all roles and to bots.
Parameters: user_id
Body: { status: { emoji*, title*, expires_at, is_away, away_message } }

### DELETE /api/shared/v1/users/{user_id}/status
Removes the status from another employee, along with away mode and its text. Available to the workspace owner and an administrator; not to a bot. If there was no status, the response is still `204`. Your own status is removed by [Delete own status](/api/profile/delete-status).
Parameters: user_id

All tags of the workspace with the number of employees in each. They are visible the same way to all roles, regardless of which chats they are linked to. ### POST /api/shared/v1/group_tags
Creates a tag. A tag is a way to keep chat membership up to date by itself: it is linked to a conversation or a channel, and everyone who has this tag ends up there automatically. Employees are added to a tag not here but in each employee's profile — [Edit employee](/api/users/update) with the `list_tags` field. A fresh tag is created empty, with `users_count: 0`. Tags can be created by the workspace owner and an administrator; the method is not available to a bot.

### GET /api/shared/v1/group_tags/{id}
The tag name and the number of employees in it. Only active employees are counted in `users_count`: suspended ones do not make it into the counter, although they remain in [List tag employees](/api/group-tags/list-users).

### PUT /api/shared/v1/group_tags/{id}
Renames a tag. The set of employees and the links to chats do not change: everyone who was in the tag stays in it, only under the new name. The name is unique within the workspace, case-insensitively, and cannot contain `@`. Tags can be renamed by the workspace owner and an administrator; the method is not available to a bot.

### DELETE /api/shared/v1/group_tags/{id}
Removes a tag from the workspace: it is taken off every employee and unlinked from every chat. Nobody leaves the chats because of this. The employees the tag brought into a conversation or a channel stay there as ordinary members, and their membership is no longer maintained by the tag. ### GET /api/shared/v1/group_tags/{id}/users
Who belongs to the tag. Suspended employees come in the list, although they are not counted in the tag's own `users_count`; deleted ones do not come. ## Members

### POST /api/shared/v1/chats/{id}/group_tags
Links tags to a conversation or a channel so that the chat membership keeps itself up to date. After adding a tag, all its members automatically become members of the chat. The tag and chat member lists are synchronized automatically: when a new member is added to the tag, they immediately appear in the chat; when removed from the tag, they are removed from the chat. If at least one of the tags passed is not found, the method responds `404` and links none of them. A tag already linked to the chat is not linked again, but its members are still pulled into the chat. A tag can be linked by a member of a private conversation and by any employee of the workspace in an open chat, while taking it off is available only to the chat owner or a chat administrator through the [Remove tag](/api/members/remove-group-tag) method.
Parameters: id
Body: { group_tag_ids* }

### DELETE /api/shared/v1/chats/{id}/group_tags/{tag_id}
Unlinks a tag from a conversation or a channel and takes out the employees who were held there by it alone. The removal happens in the background, after the response: the method responds `204` immediately, and the chat membership changes a few moments later. The chat owner, those brought in by another tag of the same chat, and those added to the chat by hand will stay. A tag can be taken off a chat by the chat owner or a chat administrator. It can be linked back with the [Add tags](/api/members/add-group-tags) method.
Parameters: id, tag_id

### DELETE /api/shared/v1/chats/{id}/leave
The token owner leaves a conversation, a channel, or a thread on their own. A thread is addressed by its `chat_id`. In a private conversation the others see a system message about the departure; in a public chat and in a channel they do not. You cannot leave if an employee is held in the chat by a linked tag: the method responds `403` until the tag is taken off the employee or off the chat. You cannot leave a direct message either, but you can leave an archived chat. You can come back to a public chat on your own, and to a private one only if one of the members adds you back. Another employee is taken out by [Remove user](/api/members/remove).
Parameters: id

### GET /api/shared/v1/chats/{id}/members
Who belongs to a conversation, a channel, or a thread. Bots come on equal terms with employees, with `bot: true`. The workspace owner can retrieve the member list of any chat in the workspace. Admins and bots can only retrieve the member list of chats they belong to (or that are public). Only active employees make it into the results: suspended ones do not come, although their membership is kept. The method does not return a member's role in the chat — the `role` parameter works only as a filter.
Parameters: id, role?, limit?, cursor?

### POST /api/shared/v1/chats/{id}/members
Adds employees and bots to a conversation, a channel, or a thread. A bot is added the same way as an employee: its `id` in `member_ids`. In a channel it receives the editor role, and in a conversation it becomes an ordinary member — and only after that can it write there. The role in the chat is assigned at the moment of adding: the workspace owner and an administrator become chat administrators, everyone else becomes an ordinary member. After that it is not recalculated by itself, and promoting an employee in the workspace changes nothing where they already belong. To change a role, use the [Edit role](/api/members/update) method. Those who already belong to the chat are silently skipped by the method, and this is not treated as an error. An unknown or inactive ID, however, stops the whole request: the method responds `404` and lists such values, and nobody is added. Adding a whole department at once is more convenient with a tag — [Add tags](/api/members/add-group-tags): then the chat membership is maintained by itself.
Parameters: id
Body: { member_ids*, silent }

### PUT /api/shared/v1/chats/{id}/members/{user_id}
Changes the role of a member of a conversation or a channel. A role in a chat is not tied to a role in the workspace: a regular employee can be a chat administrator, and a promotion in the workspace does not change roles in chats. The `editor` role exists only in channels. You cannot change your own role, nor the role of someone who is not in the chat: the method responds with an error. Setting the same role again is treated as an error, not as a repeat. The chat owner's role cannot be changed. They always have Admin privileges in the chat.
Parameters: id, user_id
Body: { role* }

### DELETE /api/shared/v1/chats/{id}/members/{user_id}
Removes an employee or a bot from a conversation, a channel, or a thread. A thread is addressed by its `chat_id`. In a private conversation the removed member loses access to the chat but stays in the threads they belonged to. An employee held in the chat by a linked tag cannot be removed with this method: the response will be successful, but the employee will stay in the chat. Take the tag off them with [Edit employee](/api/users/update) or unlink the tag from the chat with the [Remove tag](/api/members/remove-group-tag) method. If the user is the chat owner, they cannot be removed. They can only leave the chat on their own using the [Leave chat](/api/members/leave) method.
Parameters: id, user_id

## Threads

### POST /api/shared/v1/messages/{id}/thread
Creates a thread under a message — a place to discuss what has been said without cluttering the chat feed. A thread is a separate access: an employee can be invited into it without opening the chat itself to them, and they will see only the thread and the parent message. If a topic rather than a message needs discussing, start a thread with the [New standalone thread](/api/threads/create) method. A new thread immediately includes the employee who created it, the author of the message, everyone who added reactions to the message, and the chat members who turned on thread notifications. Anyone mentioned in the parent message — by name or by tag — is added by a background job right after creation, so the first response may not list them yet. Blanket mentions such as `@all` bring nobody into the thread, and a mentioned employee who is not in the chat itself is not picked up either. An empty thread is not a conversation yet: send the first message into it right away with the [New message](/api/messages/create) method and `entity_type: "thread"`. A thread has no name, and it cannot be deleted either through the API or in the app. If a thread has already been created for the message, the response will return information about the previously created thread. But to simply read a thread, the method is not needed: the ID of an existing thread arrives in the `thread` field of the message itself. A thread cannot be created under a message that itself lies in a thread: there are no nested threads in Pachca.
Parameters: id

### GET /api/shared/v1/threads
Threads available to the token owner. Returns threads where you belong either to the thread itself or to the chat it was started in. Belonging to the thread is enough: you do not have to join the chat with the parent message, and standalone threads come as well. Threads from open chats of the workspace you have not joined, however, do not make it into the list, even though those chats are available to you. Sorted by the time of the last message in the thread, descending. A list item carries neither a title nor any text: only the identifiers of the thread, its chat, and the parent message. To find out what a thread is about, read its messages with [List chat messages](/api/messages/list) by `chat_id`, and a thread known by its topic is found with [Search messages](/api/search/list-messages).
Parameters: last_message_at_after?, last_message_at_before?, limit?, cursor?

### POST /api/shared/v1/threads
Creates a thread that is not linked to anything: a place for a conversation, a dialogue with an agent, or a call that needs no chat of its own. Any employees can be gathered in it. No request body is required. The thread creator becomes its only member, and the `message_id` and `message_chat_id` fields in the response are returned as `null`. The easiest way to add members to the thread is a mention: `@nickname` or `@tag` at the start or the end of the message text. The [Add users](/api/members/add) method by the `chat_id` of the thread works too. A thread has no name, so send the first message into it right away — that is how employees will understand what it is about. A thread cannot be deleted. If what needs discussing is a particular message in a chat, start a thread under it with the [New thread](/api/threads/add) method, and if a permanent place with a name is needed, use the [New chat](/api/chats/create) method.

### GET /api/shared/v1/threads/{id}
The thread's identifiers: its own `id`, the `chat_id` for reading and sending messages, and the message it hangs under. For a standalone thread `message_id` and `message_chat_id` come back as `null`. The response carries identifiers only: a thread has no name and no message counter, and what it is about can be seen from the conversation inside. The messages of a thread are read with the [List chat messages](/api/messages/list) method, and its members with the [List chat members](/api/members/list) method, both by the `chat_id` of the thread. Access to a thread is broader than the results of [List threads](/api/threads/list): a thread that opens by `id` may well not appear in the list.
Parameters: id

## Messages

### GET /api/shared/v1/messages
The message feed of a conversation, a channel, a thread, or a direct message — by the `chat_id` of the chat in question. Messages come newest first, that is, the most recent messages of the chat come first. For earlier ones, use the `limit` and `cursor` parameters. Deleted messages do not make it into the list. The messages of a thread are returned by the `chat_id` of the thread itself, not by the chat where the parent message hangs. The thread identifier arrives in the `thread` field of the parent message.
Parameters: chat_id, sort?, order?, limit?, cursor?

### POST /api/shared/v1/messages
Sends a message to a conversation or a channel, a direct message to a user, or a comment to a thread. With `entity_type: "discussion"` — the default — `entity_id` takes the `chat_id` of any chat, so knowing the chat ID is enough to send. A message can also be addressed to a thread by the thread's own ID, and a direct message by the user's ID, but then the matching `entity_type` is needed: `thread` or `user`. There is no need to create the direct chat for this: it appears by itself if there has been no prior conversation between you. Only one direct chat can exist between two users. Your own ID writes to the chat with yourself, where notes to oneself go. Unlike a direct chat, a thread does not appear by itself: if a message has no thread yet, it is first created with the [New thread](/api/threads/add) method. The text in the `content` field is parsed as markdown: bold, italic, strikethrough, inline code, code block, and links. Lists and tables are not parsed — `-`, `1.`, and `|` stay as they are, a quote loses its `>`, and a line with a hash and a space becomes bold. Attach a table, a checklist, or a diagram as an `.md` file: Pachca shows such a file formatted, and if it is the only document in the message, its beginning is visible right in the chat. The details are in the [Text formatting](/guides/markdown) section. `@all` mentions all members of the chat, `@here` those who are currently online, and `@` with a tag name without spaces the employees of that tag. In a thread a mention also works as an invitation: a mentioned employee who is not in the thread is added to it by Pachca and gains access to the thread and its parent message. To prevent that, pass `skip_invite_mentions: true`. In a conversation or a channel a mention adds nobody, and the parameter changes nothing there. A name without `@`, and a mention inside inline code or a code block, are not mentions. Buttons can be shown under the message text — the `buttons` array, where each nested array is a row. They only work on messages sent with a bot token: a click on a button with `data` arrives as a `button_click` event to that same bot, carrying a `trigger_id` — there are 3 seconds to open a form with it, the [Open view](/api/views/open) method. A button with `url` simply follows the link and creates no event. Details are in the [Buttons](/guides/buttons) section. A bot can sign a message with someone else's name and avatar: `display_name` and `display_avatar_url` change the sender for this message only. The **Bot** badge stays, and the sender's profile still shows the real bot. This is how the original author is shown when a conversation is carried over from another system. With a personal token these fields are not available and the response is `403`. Details are in the [Bots](/guides/bots/overview) section. No more than 10 files can be attached to a message. A link preview is built only if `link_preview` is passed at the root of the request body. A daily limit applies to the number of messages into one chat from one sender. When it is exceeded the method responds `429`, and the `Retry-After` header carries the pause before the next attempt. The limit values are in the [Limits](/api/limits) section.
Body: { message*, link_preview }

### GET /api/shared/v1/messages/{id}
The message together with its author, attachments, and buttons. A deleted message is returned by the method all the same — with empty `content` and a filled-in `deleted_at`, without files and reactions. The file links in the response are temporary. An ordinary file is returned as a direct link to the storage, while a protected or an encrypted one comes as an API address that requires a token with the `files:read` scope.
Parameters: id

### PUT /api/shared/v1/messages/{id}
Changes the text, files, and buttons of a message that has already been sent. In the interface it gets an edited mark. The text follows the same formatting rules as in the [New message](/api/messages/create) method. You can edit only your own messages, and only ordinary ones: a system, a forwarded, and a voice message are not changed by the method. There are no restrictions on how long ago the message was sent. Files and buttons are replaced as a whole: an empty array removes all of them, while the absence of the field in the body leaves them as they were. Any edit removes the link previews, and they are not built again.
Parameters: id
Body: { message: { content, files, buttons, display_avatar_url, display_name } }

### DELETE /api/shared/v1/messages/{id}
Message deletion is available to the sender, admins, and editors in the chat. In direct messages, both users are editors. There are no time restrictions on message deletion. The text, files, and reactions disappear for everyone and are not restored, the pin is removed, and a "Message deleted" note stays in place of the message in the conversation. The thread created under this message stays, together with the whole conversation inside it. A repeated deletion responds `204` and no longer changes anything.
Parameters: id

### POST /api/shared/v1/messages/{id}/link_previews
Inserts into a message a link preview assembled by the bot itself: a title, a description, and an image. This way the company's internal addresses, which Pachca cannot open on its own, are shown in the conversation as a card. The method is available only to a bot whose outgoing webhook is configured for link previews. Such a bot receives the `message_link_shared` event and answers it with this method, and it does not need to belong to the chat with the message — it is enough that the chat is in its workspace. The domain of the link must be in the bot's list of allowed ones, and the link itself must be present in the message text, otherwise the method responds with an error. The response comes back empty even when no preview has been applied: the result is checked by reading the message again.
Parameters: id
Body: { link_previews* }

### POST /api/shared/v1/messages/{id}/pin
Pins a message in the header of a conversation or a channel, where all members see it. There is no limit on the number of pinned messages. In threads the method does not work. A message that is already pinned responds `409`, and a deleted one `422`.
Parameters: id

### DELETE /api/shared/v1/messages/{id}/pin
Removes the pin from a message. If the message was not pinned, the response is still `204`, so a repeated call is safe.
Parameters: id

## Read members

### GET /api/shared/v1/messages/{id}/read_member_ids
Which of the chat members have read the feed up to this message. A flat array of IDs is returned. The caller themselves and the author of the message will never be in the list — only the other members are counted. For a message in a thread these are the members of the thread, not of the parent chat. The method does not return names. They are fetched with the [Employee info](/api/users/get) method for each ID.
Parameters: id, limit?, cursor?

## Reactions

### GET /api/shared/v1/messages/{id}/reactions
All reactions on a message and who left them: each record carries a `user_id` and the character itself. For a deleted message the list is empty — reactions disappear along with the text and the files.
Parameters: id, limit?, cursor?

### POST /api/shared/v1/messages/{id}/reactions
Adds an emoji reaction to a message on behalf of the token owner. The `code` field carries the emoji character itself: text notations such as `+1` or `:+1:` are not accepted by the method. If the user has already added the same reaction, it will not be duplicated. To remove a reaction, use the [Delete reaction](/api/reactions/remove) method. If there is a thread under the message, the employee who reacted is subscribed to it as well and starts receiving the new messages of the thread. **Reaction limits:** - Each user can add no more than **20 unique** reactions to a message - A message can have no more than **30 unique** reactions - The total number of reactions on a message cannot exceed **1000**
Parameters: id
Body: { code*, name }

### DELETE /api/shared/v1/messages/{id}/reactions
Removes your own reaction from a message. Someone else's reaction and a reaction that does not exist respond `404`. Removing a reaction does not cancel the thread subscription, if it appeared together with the reaction.
Parameters: id, code, name?

## Search

### GET /api/shared/v1/search/chats
Searches for conversations and channels by name, forgiving typos. It also finds the public chats of the workspace the caller has not joined, and of the private ones only those they belong to. Direct messages are not searched by default. Pass `personal=true` and the search will go by the name of the other party rather than by the chat name. The method searches names, not content. To find where something was discussed or agreed, use [Search messages](/api/search/list-messages).
Parameters: query?, limit?, cursor?, order?, created_from?, created_to?, active?, chat_subtype?, personal?

### GET /api/shared/v1/search/messages
Searches by message text and by the names of attachments, but only in the chats the token owner belongs to. A public channel they have not joined does not make it into the search, even though its feed can be read. Thread messages are included in the results. The words of the query are matched by their forms and by part of a word, and typos are not corrected. A query in quotation marks is searched as an exact phrase, and matching on part of a word does not apply to it. By default messages come from newest to oldest. `sort=relevance` switches the results to how well they match the query, where recent messages are still valued higher.
Parameters: query?, limit?, cursor?, order?, sort?, created_from?, created_to?, chat_ids?, user_ids?, active?

### GET /api/shared/v1/search/users
Searches for employees by first and last name, nickname, position, and department. Typos are forgiven only in the first and last name; the other fields need an exact word. The method searches by email only for those who can see personal data in the workspace. It does not search by phone at all — for that there is [List employees](/api/users/list) with the `query` parameter. Deleted employees are never found; suspended ones only when a text query is given, and they stand below the rest in the results. Of the bots, only public ones are found.
Parameters: query?, limit?, cursor?, sort?, order?, created_from?, created_to?, company_roles?

## Tasks

### GET /api/shared/v1/tasks
The tasks available to the token owner. Without the `chat_ids` parameter only your own tasks are returned: those from conversations and channels you are a member of, plus tasks with no chat that you created or that are assigned to you. The `chat_ids` parameter changes the selection — all tasks of the listed chats are returned, including those of other employees.
Parameters: status?, chat_ids?, performer_ids?, author_id?, limit?, cursor?

### POST /api/shared/v1/tasks
Creates a task and assigns the employees responsible for it. Specifying the task type is required when creating a task: call, meeting, simple reminder, event, or email. A description is not required — without it the task takes the name of its type as the text. If a description is passed, it is what becomes the task's text. A task must have assignees; if none are specified, you are assigned as the responsible one. Any workspace employee can be assigned to a task that is not linked to any entity. You can get the current employee list using the [List employees](/api/users/list) method. Assignees the caller cannot see are silently dropped: the response is successful but they are not in `performer_ids`, so check the list in the response. A task can be linked to a conversation with the `chat_id` field — then, besides the author and the assignees, the members of that conversation see it. Whoever links it must belong to that conversation. Tasks are not created in a channel, in a thread, or in an archived chat. Handing a task to somebody else means changing the assignee with [Edit task](/api/tasks/update). If a calendar is connected to the workspace or to the profile, the task also appears there as an event.
Body: { task: { kind*, content, due_at, priority, performer_ids, chat_id, all_day, custom_properties } }

### GET /api/shared/v1/tasks/{id}
The task together with its author, assignees, and the chat it is linked to. A task is seen by its author, its assignees, and the members of the chat it is linked to. But membership in the chat is enough only to read it: a task can be changed and deleted only by the author or one of the assignees.
Parameters: id

### PUT /api/shared/v1/tasks/{id}
Changes a task: only the fields you pass are overwritten. Handing a task over to another employee is an edit too: add them to `performer_ids` in place of the previous one. A completed task is closed with this same method: `status: "done"` ticks it off and keeps it in the list, `status: "undone"` puts it back to work. Available to the author and the assignees. A member of the chat where the task hangs sees it but cannot change it. The link to a chat cannot be changed: to move a task to another chat, delete it and create it again with the `chat_id` you need.
Parameters: id
Body: { task: { kind, content, due_at, priority, performer_ids, status, all_day, done_at, custom_properties } }

### DELETE /api/shared/v1/tasks/{id}
Removes a task for good: it cannot be restored, and it disappears for the assignees as well. If the task went into a connected calendar, the event is deleted there too. Available to the author and the assignees. A repeated call responds `404`. A completed task can be closed while keeping it in the list with [Edit task](/api/tasks/update) and `status: "done"`.
Parameters: id

## Drafts

### GET /api/shared/v1/drafts
Your own drafts, newest first. By default only ordinary drafts are returned: scheduled ones have to be asked for with the `type` parameter. In the response they are told apart by the `schedule` field. The pair `entity_type` and `entity_id` narrows the results down to a single chat, thread, or direct message. If there is no such chat or it is not accessible, the method responds with an empty list rather than an error.
Parameters: type?, entity_type?, entity_id?, limit?, cursor?

### POST /api/shared/v1/drafts
Puts a draft into a conversation, a thread, or a direct message. In the Pachca interface it shows up in that chat's input box, where an employee finishes it and sends it. A scheduled message is created by this same method: with the `schedule` field the draft goes out by itself at the appointed time, without it the draft simply lies there. The method itself sends nothing — sending is [New message](/api/messages/create). Sending a message does not remove the draft: the Pachca app clears it by itself, while through the API it is removed with the [Delete draft](/api/drafts/delete) method — otherwise the text stays in the input box. A draft is visible only to its author — neither the other party nor a workspace administrator sees it. A chat can hold only one ordinary draft. A repeated call responds `409` with the `already_exists` code and the ID of the existing one in `payload.draft_id`. That one is finished with the [Edit draft](/api/drafts/update) method. A chat holds no more than 50 scheduled messages. For a thread, `entity_id` takes the ID of the thread itself, not of the message it hangs under. A direct message with an employee may not exist yet — then it is created by itself, the same way as when an ordinary message is sent. An empty draft cannot be created: either text or attachments are needed. The method is not available to bot tokens.
Body: { draft: { entity_type*, entity_id*, content, parent_message_id, files, schedule } }

### GET /api/shared/v1/drafts/{id}
The draft. For a scheduled message its schedule comes here too.
Parameters: id

### PUT /api/shared/v1/drafts/{id}
Changes your own draft: the text, the attachments, the schedule, and the message it will reply to (`parent_message_id`). Only the fields you pass are overwritten, so the text can be finished with `content` alone, without touching the attachments. An ordinary draft turns into a scheduled message if `schedule` is passed. The reverse transition is forbidden: `schedule: null` on a scheduled message responds `422` with the `draft_type_change_forbidden` code. To cancel the sending, the draft is removed with the [Delete draft](/api/drafts/delete) method. Editing works only while writing into the chat is allowed. If access to the chat has been lost, editing responds `403`, while deletion works all the same. The draft's chat is not changed by this method, it does not accept `entity_type` and `entity_id`. To move a draft to another chat, create a new one and delete the old one.
Parameters: id
Body: { draft: { content, parent_message_id, files, schedule } }

### DELETE /api/shared/v1/drafts/{id}
Removes your own draft for good: it cannot be restored, and the attachments are deleted along with it. For a scheduled message deleting is the cancellation of the sending. It works even if writing into the chat is no longer possible. A repeated call responds `404`.
Parameters: id

## Views

### POST /api/shared/v1/views/open
Shows a user a modal window with a form in response to their action. The method is called with a bot token: button click events reach bots only, and the window is opened on behalf of the bot. There is only one way to open the window — by the `trigger_id` from the button click event. One `trigger_id` opens one window and lives for 3 seconds: for a bot with a webhook, from the moment Pachca delivered the click, and for a bot with the [Event history](/api/bots/list-events), from the moment the click was written to it. That is why the window is opened first of all, and everything else for the event is done afterwards. The filled-in form comes back as a `view_submit` event: to the outgoing webhook, and if no address is set, to the event history. A webhook is answered in the response to it, and Pachca waits 3 seconds for that. An event from the history is closed with [Respond to a form submission](/api/views/submit-response), and there are 5 seconds for that. Miss the window and the user sees a submission error.
Body: { type*, trigger_id*, private_metadata, callback_id, view* }

### POST /api/shared/v1/views/{view_id}/submit_response
Closes the form for the employee or shows them errors under the fields. The method is needed by a bot that has no outgoing webhook address set: such a bot has nowhere to answer the webhook, and it receives the `view_submit` event from the [Event history](/api/bots/list-events). If the webhook address is set, answer the webhook directly — that is simpler and does not require polling the history. The `view_id` and `submit_id` identifiers arrive in the event payload. You must respond within 5 seconds of the form submission, otherwise the employee sees a submission error and the field values are kept for another attempt. A body without the `errors` field closes the form as successfully submitted; with the `errors` field it shows the error text under each named field. The response is accepted once. A repeated call with the same `view_id` and `submit_id` pair, as well as a late one, receives `410` with the `submit_expired` code.
Parameters: view_id
Body: { submit_id*, errors }

## Bots

### POST /api/shared/v1/bot/recreate_token
Allows a bot to generate a new `access_token` for itself using its own token — without an administrator and without knowing its own `id`. The very token the request was made with is rotated, and it is invalidated immediately. The new token is returned in the response once — be sure to save it, otherwise the bot loses access to the API. The scopes are carried over from the previous token.

### PUT /api/shared/v1/bot/webhook
Allows a bot to change its own outgoing webhook `URL` using its own token — without an administrator and without knowing its own `id`. The webhook of the bot that owns the token is changed. To disable the webhook, send an empty string in `outgoing_url`.
Body: { webhook: { outgoing_url* } }

### GET /api/shared/v1/bots
The bots the caller is entitled to configure: those they created themselves and those whose settings grant them edit access. The `query` parameter selects bots by part of the name, without typos. Bot tokens do not come in the list — they are shown once at creation and at rotation. The list of all bots in the workspace, including other people's, is available to the owner on the "Corporation" plan — [List workspace bots](/api/bots/list-company). There other people's bots come with only a name and a nickname, and the rest of the settings are hidden.
Parameters: query?, limit?, cursor?

### POST /api/shared/v1/bots
Creates a bot in the workspace and immediately returns its `access_token`. Save the token at creation: the same one is not shown again, and what remains is to reissue it with [Bot token rotation](/api/bots/recreate-token). A newly created bot does not write anywhere yet. It writes into a conversation and a channel only as a member, and it is added like an employee — with the [Add users](/api/members/add) method, passing the bot's `id`. In a channel the bot receives the editor role. Direct messages and threads in public chats do not require membership. The bot's incoming webhook sends a message at once to every conversation and channel the bot belongs to, so it is the set of its chats that decides where it lands. No token is needed for that, the webhook address is enough. To write into one particular chat, take the [New message](/api/messages/create) method — that one does need a token. The nickname must end with `_bot` and be free in the workspace. The `single_chat` restriction is set only here: when editing a bot it can no longer be changed.
Body: { webhook: { name*, nickname, outgoing_url, events, trigger_on, commands, scopes, template, template_engine, challenge_key, link_preview_enabled, ignore_self_messages, events_history_enabled, who_can_add, can_edit, single_chat } }

### GET /api/shared/v1/bots/{id}
The bot's settings. The token does not come in the response — it is shown once at the bot's creation and at [Bot token rotation](/api/bots/recreate-token). The method returns only the bots the caller is entitled to configure: their own, and, if the bot's settings allow it, also as a workspace administrator or as the owner of a chat the bot belongs to. For someone else's bot the method responds `403`. The list of all bots in the workspace, including other people's, is available to the owner on the "Corporation" plan — [List workspace bots](/api/bots/list-company).
Parameters: id

### PUT /api/shared/v1/bots/{id}
Changes a bot's settings: only the fields you pass are overwritten. The `single_chat` field is accepted only when a bot is created. In this method it is silently ignored: the response is successful and the bot's mode does not change. The nickname must end with `_bot` and be free in the workspace, otherwise the method responds with a validation error. Commands and scopes are replaced by the passed list as a whole, and the new set of scopes is applied to the bot's current token right away — there is no need to reissue it. You cannot edit a bot whose settings are not accessible to you (the "Who can edit bot settings" field is located on the "General" tab in the bot settings).
Parameters: id
Body: { webhook: { name, nickname, outgoing_url, events, trigger_on, commands, scopes, template, template_engine, challenge_key, link_preview_enabled, ignore_self_messages, events_history_enabled, who_can_add, can_edit } }

### DELETE /api/shared/v1/bots/{id}
Delete a bot. The bot's previous `access_token` is invalidated immediately, the bot is removed from all chats, and its outgoing webhook is deleted. Deletion is available to the bot creator, and to a workspace administrator if the bot's settings grant administrators edit access. Chat owners and admins cannot delete a bot, even if they are allowed to edit it.
Parameters: id

### POST /api/shared/v1/bots/{id}/recreate_token
Generates a new `access_token` for the bot and immediately invalidates the previous one. Use it when a token is compromised or for scheduled secret rotation in `CI`. The new token is returned in the response only once — save it right away. Its permissions are the same: the scopes are carried over from the previous token. Rotation is available to the bot creator, and also to a workspace administrator if the bot's settings grant administrators edit access. The owner of a chat the bot belongs to cannot rotate the token, even when the rest of the bot's settings are open to them.
Parameters: id

### GET /api/shared/v1/company/bots
Every bot in the workspace, including the ones you cannot edit. For those, only the name and the nickname are returned, the rest of the settings come as `null`. The method is available to the workspace owner. Every request is written to the [audit log](/guides/audit-events) with the `company_bots_accessed` key.
Parameters: query?, limit?, cursor?

### GET /api/shared/v1/webhooks/events
The bot's event history: the same thing that goes to the outgoing webhook, but fetched with a request. The method is needed when webhooks cannot be received at your own address — the handler is not reachable from the internet, is not always up, or is being written right now. The history is kept only when the "Save event history" option is enabled in the "Outgoing webhook" tab of the bot settings. The webhook address does not have to be specified at all, and if it is specified, the event both goes to it and lands in the history. The method works only with a bot token: a personal token has no history of its own. Events are returned from newest to oldest, and an event identifier is a string, not a number. The history does not clear itself: delete the events you have read with the [Delete event](/api/bots/remove-event) method, otherwise they come again on a repeat request.
Parameters: limit?, cursor?

### DELETE /api/shared/v1/webhooks/events/{id}
Removes an event from the bot's event history. When working through the history, delete an event right after processing it: the history does not clear itself, and everything left in it comes again on a repeat request. The method works only with the token of the bot the event belongs to.
Parameters: id

## Security

### GET /api/shared/v1/audit_events
What has been happening in the workspace: sign-ins and sign-outs, changes of roles and settings, actions on chats, employees, and bots. The records are read-only — they cannot be changed or deleted either through the API or from the interface. The method is available to the workspace owner on the "Corporation" plan; other employees receive `403`. Accessing the audit log is itself written to the audit log — as the `audit_events_accessed` event. Events come from newest to oldest and are selected with filters: the period by `start_time` and `end_time`, the kind of event by `event_key`, and the actor by `actor_id` and `actor_type`. Without filters the method returns all events of the workspace page by page.
Parameters: start_time?, end_time?, event_key?, actor_id?, actor_type?, entity_id?, entity_type?, limit?, cursor?

## Custom Properties

### GET /api/shared/v1/custom_properties
The schema of the workspace's custom properties: the ID, the name, and the type of each. Only employees and tasks have such properties, their sets are independent, and the `entity_type` parameter picks the one you need. The values come with the entity itself — in the employee's profile or in the task. The IDs from here are needed in order to set those values. Properties of the "File" and "Multiple choice" types are not available through the API and do not make it into the results. The basic profile fields — name, phone, email, department, tags — do not either: these are not custom properties. The set of properties is defined by the workspace administrator, who also renames and deletes them. That is why the list is worth re-reading before work: addressing a property that no longer exists returns an error.
Parameters: entity_type

## Files

### POST /api/shared/v1/direct_url
The second step of the upload: the file itself goes to the storage as a `multipart/form-data` form. The form fields and the address are taken from the response of the [Get signature, key and other parameters](/api/files/uploads) method and passed as they are, in the same order, with the file as the last field. The request goes not to the Pachca API but straight to the storage, and `204` with no body comes back in response. After that the file is attached by passing its `key` in the `files` field — to [New message](/api/messages/create) or [New draft](/api/drafts/create), and when editing either of them. The file name in `name` must have the same extension as the `key`, otherwise the message will be rejected.
Body: { Content-Disposition*, acl*, policy*, x-amz-credential*, x-amz-algorithm*, x-amz-date*, x-amz-signature*, key*, file* }

### GET /api/shared/v1/files/{id}
Returns the file itself, not a link to it. It is needed for attachments that have no direct storage link: their `url` field holds the address of this method, and it can only be opened with a token. Encrypted files and files sent from the workspace secure perimeter are served this way — both settings are covered in [Encryption and the secure perimeter](/guides/data-protection). A refusal comes as `403` with the `confidential_download_denied` code. The address being checked is the one the request came from, that is the address of your server, not of the employee whose token you use: for a server integration that is the most common reason to be refused. The response is the body of the file and a `Content-Disposition` header with its name, not `JSON`. An encrypted file is decrypted on the fly and comes as a whole attachment: `target` does not apply to it. If it could not be decrypted, the answer is `400` with the `decryption_failed` code. An attachment of a message is available to whoever sees the message itself, and an attachment of a draft only to its author.
Parameters: id, target?

### POST /api/shared/v1/uploads
The first step of a file upload: the method issues the storage address and the signed form fields with which the file is uploaded by the next request. Nothing is created in Pachca at this point yet: the uploaded file is visible to nobody and linked to nothing. It becomes an attachment when its `key` is passed in the `files` field — to [New message](/api/messages/create) or [New draft](/api/drafts/create), and when editing either of them. The parameters are issued for one file: request them again for each next one. The signature is valid for 14 days, and the `key` is tied to the token owner, so someone else's key cannot be attached to your own message.
