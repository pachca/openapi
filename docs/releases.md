# Публикация пакетов и версии

Как выходят в реестры публикуемые пакеты репозитория и какие проверки это
гарантируют. Цель — никаких «молчаливых» релизов: всё, что попадает в `main`
и triggers публикацию, обязано нести запись в changelog, которую увидят
пользователи, и корректную версию.

Публикуемые пакеты:

| Пакет                                        | Реестр             | Версионирование                   | Свой changelog                         |
| -------------------------------------------- | ------------------ | --------------------------------- | -------------------------------------- |
| `@pachca/cli`                                | npm                | CalVer `ГГГГ.М.патч` (`2026.5.6`) | `packages/cli/src/data/changelog.json` |
| `n8n-nodes-pachca`                           | npm                | semver                            | `integrations/n8n/CHANGELOG.md`        |
| `@pachca/generator`                          | npm                | semver                            | — (только портал)                      |
| `@pachca/sdk` (TS/Python/Go/Kotlin/C#/Swift) | npm/PyPI/NuGet/git | semver, из `releases.json`        | — (только портал)                      |
| `@pachca/mcp-manifest`                       | npm                | semver, из `package.json`         | `packages/mcp-manifest/CHANGELOG.md`   |

«Портал» — `apps/docs/data/releases.json`: единый список релизов всех
продуктов, он же лента `/updates` на сайте. Формат записей — в
`docs/updates-format.md`.

MCP-манифест на портал не выходит, записи в `releases.json` у него нет. Версия
пакета записана в `packages/mcp-manifest/package.json`, а история — в
`packages/mcp-manifest/CHANGELOG.md` на английском, который едет в архиве
пакета.

Плагин `plugins/pachca` в реестры не публикуется, записи в `releases.json` и
своего changelog у него нет. Его версию руками не меняют: её ставит сборка
документации, когда меняются файлы плагина. Правило описано в `CONTRIBUTING.md`,
раздел «Agent skills and the plugin».

## Единый источник версии

Версия пакета объявляется **вручную** в `releases.json` (запись с нужным
`product` и `version`) и, для CLI/n8n, продублирована в собственном changelog
пакета. Никакого авто-инкремента из npm — раньше он молча переиздавал
идентичный код под новым номером (так появились лишние `cli 2026.5.5/5.6` и
`generator 1.1.3/1.1.4`).

Версия в `releases.json` и в собственном changelog **обязаны совпадать** —
это проверяется на сборке (см. ниже).

У MCP-манифеста источник версии — поле `version` в его `package.json`. Та же
версия заголовком `## X.Y.Z (дата)` открывает его `CHANGELOG.md`, и это тоже
проверяется на сборке.

SDK как и все: версия из `releases.json` (product `sdk`), валидируется тем же
`check-release`. Особенность только в публикации — одна версия едет сразу во
все 6 языков (npm/PyPI/NuGet + git-теги для Go/Swift/Kotlin), `typespec.tsp`
остаётся источником _спеки_, но не версии SDK.

> **В `@pachca/sdk` на npm есть лишние `2.0.0`/`3.0.0`** (ошибочные мажоры из
> марта), но `latest = 1.0.19`. Шаг считается от **latest dist-tag**, поэтому
> следующий релиз SDK — `1.0.20` (а не прыжок на `3.0.x`). Номера `2.0.0`/`3.0.0`
> переиздать нельзя (заняты), но как база шага они не используются.

## Две проверки

### 1. Сборка PR — `scripts/check-changelog-sync.mjs`

Запускается в workflow `.github/workflows/check.yml` на каждый PR (и локально
`bun run check:changelog`). Сравнивает ветку с `origin/main` и **роняет
сборку**, если для любого пакета:

- код пакета изменился, но нет записи в changelog (releases.json + own
  changelog) — запрещает молчаливый релиз;
- запись в changelog добавлена, но код пакета не менялся;
- версия в `releases.json` не совпадает с версией в собственном changelog.

MCP-манифест проверяется по своему changelog. Сборка падает, если файлы пакета
изменились (копии манифеста тоже), а сверху `CHANGELOG.md` нет новой версии,
если версия в `CHANGELOG.md` не совпадает с `package.json` и если в
`releases.json` появилась запись о нём. Пока версии сверху `CHANGELOG.md` нет в
npm, правки пакета входят в неё без новой записи: проверка спрашивает npm, а
если спросить не удалось, сборка падает.

«Код пакета» — любой файл в директории пакета, кроме самих changelog-файлов. У
MCP-манифеста не считается и `package.json`, в котором поменялась только версия.

### 2. Публикация — `scripts/check-release.mjs`

Запускается в publish-workflow (`sdk.yml` для CLI и SDK, `n8n.yml`,
`generator.yml`, `mcp-manifest.yml`) на `push` в `main`. Пакет публикуется,
только если **все** условия выполнены для версии из `releases.json` (у
MCP-манифеста — из его `package.json`, флаг `--package-dir`):

1. **Формат** — CLI ровно `ГГГГ.М.патч`, остальные `X.Y.Z`.
2. **Точный следующий шаг** относительно **`latest` dist-tag в npm** (не semver-max,
   не просто «больше»): semver `патч+1` / `минор+1.0` / `мажор+1.0.0`; CalVer `патч+1`
   в том же месяце или `.0` в новом месяце. Перепрыг (`1.1.4 → 1.1.6`) запрещён.
3. **Номер не занят в npm** — идемпотентность: уже опубликованную версию (даже
   не-`latest`) не переиздаёт.
4. **Версия есть в собственном changelog** (CLI, n8n, MCP-манифест).
5. **Пакет уже есть в npm.** Trusted publishing не создаёт пакет, поэтому пока
   его нет, gate пропускает публикацию с `first_publish=true`, а прогон
   остаётся зелёным. Первая версия выходит по разделу «Новый пакет в npm».

Правка кода пакета в самом push условием не является: объявленную версию,
которой ещё нет в npm, допубликует следующий прогон workflow (см. «Если
публикация упала»).

Если версия не проходит шаг (2), gate печатает допустимые варианты, например:
`generator: version "1.1.6" is not a valid next step after npm 1.1.4.
Allowed: 1.1.5 (patch), 1.2.0 (minor), 2.0.0 (major)`.

Шаг считается **от `latest` dist-tag в npm**, а не от `releases.json` и не от
semver-max. Если баг прошлого занял номера (generator latest `1.1.4` при
портале `1.1.2`), следующий релиз = `1.1.5`. Лишние «брошенные» старшие версии
(как SDK `3.0.0` при latest `1.0.19`) на базу шага не влияют — берётся `latest`.

## Какой шаг выбирать

`check-release` проверяет только, что версия — **ровно один** шаг от `latest`, и
принимает патч, минор и мажор одинаково. Какой из трёх взять — решение автора
релиза, и вот критерий.

### SDK

SDK генерируется из спеки, поэтому значимая ось одна: **компилируется ли после
обновления код, который уже написал потребитель**.

| Шаг       | Когда                                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **патч**  | Только добавления: новые методы, модели, поля, опциональные параметры, значения enum. Прежний код потребителя не меняется                   |
| **минор** | Меняется форма уже существующих типов: поле стало nullable, модель разделена или переименована, сервис переехал, параметр стал обязательным |
| **мажор** | Удаления и переименования: метод убран, поле снято                                                                                          |

Типовой API-аудит добавляет методы и поля, ничего не ломая, — это **патч**.
Минор на каждом аудите сжигает номер впустую: аудиты идут раз в одну-две недели,
и за год версия уходит в `1.20.x`, ничего этим не сообщая.

**Исключения в истории — не прецедент.** Релизы SDK `1.2.0` (7 августа: поле
`archived` и значения enum) и `1.3.0` (12 августа: два метода, модель,
параметры) — чистые добавления и по правилу выше должны были быть патчами. То же
у ноды: `2.1.0` (12 августа) добавила операции и фильтры, тогда как все прежние
релизы с новыми операциями — `2.0.14`, `2.0.15` — уезжали патчем.

Минор взяли, потому что правило не было записано, а рядом стоял SDK `1.1.0`, где
минор как раз заслужен: там детали аудит-события видеозвонка разъехались на три
модели, то есть форма существующих типов изменилась. Переиздать номера нельзя,
шаг считается от `latest`, — но повторять этот выбор не нужно.

### Остальные пакеты

- **n8n** — semver по тому же принципу, ось та же: продолжит ли работать уже
  собранный воркфлоу. Патч — новые операции, поля и исправления. Минор — когда
  меняется поведение уже настроенной ноды: переехал ресурс, переименована
  операция, изменился набор полей существующей.
- **generator** — патч на исправления шаблонов, минор на новый язык или новую
  возможность генерации.
- **mcp-manifest** — своя ось: загрузит ли новую версию сервер, который
  исполняет манифест, без доработки. Мажор — сменился мажор `schema_version`,
  и сервер нужно доработать, или пропал инструмент либо аргумент: клиент сервера
  теряет то, что вызывал. Минор — новые или изменённые инструменты и
  аргументы и всё остальное, что прежний сервер загрузит как есть. Патч — только
  тексты: описания, инструкции, заголовки. Версия пакета и `schema_version` —
  разные номера, мажор пакета идёт следом за мажором схемы. Правило проверяет
  `scripts/check-mcp-manifest.mjs` в `mcp-manifest.yml`: если мажор
  `schema_version` сдвинулся относительно `latest` в npm или пропал инструмент
  либо аргумент, а объявлен не мажор, проверка падает. Исключение —
  `UNUSED_RELEASES` в том же скрипте: выпуски, на которых не построен ни один
  работающий сервер. Сейчас там только 1.0.0: его сменила 1.1.0 раньше, чем на
  нём построили работающий сервер.
- **CLI** — CalVer, выбора нет: `патч+1` в том же месяце, `.0` в новом.

## Как выпустить релиз

1. Внеси изменения в код пакета (или в `typespec.tsp` для SDK). MCP-манифест
   собирается из спеки и `packages/spec/mcp-*.ts`: копии в
   `packages/mcp-manifest` обновляет `npx turbo build`, и любая правка
   манифеста — это правка пакета.
2. Узнай текущую (`latest`) версию в npm: `npm view <pkg> version`
   (CLI `@pachca/cli`, n8n `n8n-nodes-pachca`, generator `@pachca/generator`,
   SDK `@pachca/sdk`, MCP-манифест `@pachca/mcp-manifest`). Шаг считается
   именно от неё.
3. Вычисли следующую версию: разряд — по разделу «Какой шаг выбирать», сам шаг — по проверке (2).
4. Добавь запись в `apps/docs/data/releases.json` (новая запись сверху, формат
   — `docs/updates-format.md`). Для всех пакетов, включая SDK, это источник
   версии. Исключение — MCP-манифест: вместо записи в `releases.json` добавь
   сверху `packages/mcp-manifest/CHANGELOG.md` заголовок `## X.Y.Z (дата)` со
   списком изменений на английском и ту же версию в поле `version` его
   `package.json` и `server.json` в корне репозитория.
5. Для CLI добавь ту же версию в `packages/cli/src/data/changelog.json`, для
   n8n — заголовок `## X.Y.Z (дата)` в `integrations/n8n/CHANGELOG.md`.
   Версии обязаны совпадать с `releases.json`.
6. Открой PR. `check.yml` проверит синхронность код↔changelog.
7. После merge в `main` publish-workflow опубликует ровно объявленную версию
   (один раз; повторные push не переиздают).
8. MCP-манифест: сервер `mcp.pachca.com` исполняет собственную копию манифеста
   и новую версию сам не подхватывает. После публикации передай её команде
   бэкенда. Пока копию не обновили, сервер отдаёт прежние инструменты и
   инструкции, поэтому страницы доки о новых инструментах выкладывай вместе с
   обновлением сервера. Новый `server.json` выложи в каталог по разделу
   [MCP Registry](#mcp-registry).

Локально перед PR: `bun run check:changelog`.

## Если публикация упала

Gate не смотрит, менялся ли код пакета в самом push: он публикует версию из
`releases.json` (у MCP-манифеста — из `package.json`), которой ещё нет в npm.
Поэтому упавший релиз допубликует следующий прогон того же workflow. `sdk.yml`
(CLI и SDK) запускается на каждый push в `main`, а `generator.yml`, `n8n.yml`
и `mcp-manifest.yml` — только на push, который трогает их пути.

Чтобы не ждать такого push, перезапусти упавший прогон:

```bash
gh run list --branch main --limit 10          # найти прогон и его id
gh run rerun <id> --failed                    # перезапустить только упавшие джобы
```

Флаг `--failed` берёт лишь упавшие джобы и переиспользует результаты
успешных. Полный перезапуск гоняет заново и `generate-and-build`, а у него
шаги с коммитом регенерации, тегами и пушем в `main` — без нужды это лучше не
повторять.

Смена секрета в настройках репозитория сама по себе ничего не запускает:
прогоны стартуют от событий, а не от изменения настроек.

Как читать причину падения:

- `npm error code E404` и `Not Found - PUT https://registry.npmjs.org/<pkg>` —
  публикация без прав: npm отвечает на неё 404, а не 401. Пакеты в npm
  публикуются через trusted publishing (OIDC), без токена. Проверить trusted
  publisher пакета на npmjs.com: владелец `pachca`, репозиторий `openapi`, имя
  файла workflow. У пакета, который только что создан заглушкой, 404 значит,
  что trusted publisher ещё не добавлен или истёк за 48 часов: см. «Новый пакет
  в npm».
- `Version ... already published, skipping` — норма, идемпотентность из условия (3).

После зелёного прогона версия в реестре появляется не мгновенно: в логе шага
публикации видно `+ <pkg>@<version>` и примечание, что пакет обрабатывается.
Пару минут `npm view <pkg> version` может отдавать прежний номер — правду
показывает `https://registry.npmjs.org/<pkg>`, поле `dist-tags.latest`.

## Новый пакет в npm

Первую версию нового пакета workflow выпустить не может: npm настраивает
trusted publisher только у пакета, который уже есть в реестре. Новая настройка
к тому же истекает, если за 48 часов через неё ничего не опубликовали, поэтому
шаги 2 и 3 ниже делаются подряд. Пока пакета в npm нет, `check-release`
пропускает публикацию и прогон остаётся зелёным, поэтому PR с новым пакетом можно
влить в любой момент.

Workflow нового пакета устроен как `mcp-manifest.yml`: у него есть
`workflow_dispatch`, проверка и публикация идут только с `main`, а пока пакета нет
в npm, публикация пропускается с подсказкой.

Порядок одинаковый для любого нового пакета. Выполняет владелец пакетов
`@pachca` в npm:

1. Создать пакет в npm со своего аккаунта, npm спросит второй фактор:

   ```bash
   npm login
   node scripts/npm-bootstrap.mjs packages/<пакет>
   ```

   Скрипт публикует из временной папки заглушку `0.0.0` под именем пакета и не
   трогает файлы репозитория. Если пакет уже есть в npm, скрипт откажется.
   Проверить без публикации можно с флагом `--dry-run`.

2. Добавить trusted publisher в настройках пакета на npmjs.com: GitHub Actions,
   владелец `pachca`, репозиторий `openapi`, файл workflow пакета (у
   MCP-манифеста это `mcp-manifest.yml`), environment пустой. Скрипт печатает
   эти значения и ссылку на страницу настроек.
3. В течение 48 часов запустить workflow на `main`: кнопкой Run workflow на
   вкладке Actions или командой `gh workflow run <workflow>.yml --ref main`. Он
   опубликует версию, объявленную для пакета: `1.0.0` после заглушки `0.0.0` —
   допустимый мажорный шаг.

После первой публикации настройка больше не истекает, и каждый следующий релиз
выходит сам, как у остальных пакетов. Если 48 часов прошли раньше, удалить
настройку, добавить её заново и повторить шаг 3. Пометить заглушку устаревшей
командой `npm deprecate <пакет>@0.0.0 "Bootstrap placeholder"` можно по желанию,
на публикацию это не влияет.

## MCP Registry

MCP-сервер `mcp.pachca.com` описан для официального каталога
registry.modelcontextprotocol.io файлом `server.json` в корне репозитория.
Workflow его не публикует: файл выкладывают вручную утилитой `mcp-publisher`.

- **Имя.** Сервер называется `com.pachca/mcp`. Право на пространство имён
  `com.pachca` подтверждает файл `https://pachca.com/.well-known/mcp-registry-auth`
  со строкой `v=MCPv1; k=ed25519; p=<открытый ключ в base64>`. Строку печатает
  вторая команда из блока ниже. Файл размещает команда сайта, закрытый ключ
  хранит тот, кто публикует. Каталог запрашивает файл со своих серверов и не
  идёт по редиректам, поэтому адрес должен сразу отвечать `200` с этой строкой.
- **Версия.** Каждой публикации нужна новая версия: опубликованную нельзя ни
  повторить, ни изменить. В поле `version` ставится версия
  `@pachca/mcp-manifest` из `packages/mcp-manifest/package.json`. Выпуск
  манифеста поднимает `version` в `server.json` в том же PR, а после
  публикации пакета `server.json` выкладывают в каталог заново. Правка одного
  `server.json` выходит со следующим выпуском манифеста: предварительная версия
  вида `1.4.0-1` после `1.4.0` в каталоге последней не станет, и каталог
  продолжит показывать прежнее описание.
- **Адрес.** Каталог не проверяет, что адрес из `remotes` принадлежит владельцу
  имени. Один адрес может быть только у одного имени сервера: если адрес уже
  занят, публикация не пройдёт.

Ключ создают и читают в OpenSSL 3: системный LibreSSL в macOS ключ Ed25519 не
создаёт. Блок `priv:` OpenSSL печатает парами через двоеточие в несколько
строк, а `mcp-publisher` принимает hex без разделителей, поэтому третья команда
их убирает.

```bash
# Ключ Ed25519
openssl genpkey -algorithm Ed25519 -out key.pem
# Строка для файла на pachca.com: открытый ключ в base64
echo "v=MCPv1; k=ed25519; p=$(openssl pkey -in key.pem -pubout -outform DER | tail -c 32 | base64)"
# Закрытый ключ в hex для входа
openssl pkey -in key.pem -noout -text | grep -A3 "priv:" | tail -n +2 | tr -d ' :\n'
```

Публикация из корня репозитория, `<hex>` — вывод третьей команды:

```bash
mcp-publisher login http --domain pachca.com --private-key <hex>
mcp-publisher publish
```

## Чего НЕ делать

- Не публиковать руками `npm publish` — только через workflow. Исключение —
  заглушка `0.0.0` нового пакета, её публикует `scripts/npm-bootstrap.mjs`.
- Не вписывать произвольную версию: gate требует точный следующий шаг от
  `latest` dist-tag в npm. Кривую/перепрыгнутую версию он отклонит.
- Не менять код пакета без записи в changelog (и наоборот) — сборка упадёт.
- Не добавлять MCP-манифест в `releases.json`: он на портал не выходит, его
  история — в `packages/mcp-manifest/CHANGELOG.md`.
- Не редактировать `packages/cli/CHANGELOG.md` руками — он генерируется из
  `changelog.json` при сборке CLI.
- `@pachca/generator` `1.1.3/1.1.4` и `@pachca/cli` `2026.5.5` — артефакты
  старого авто-инкремента (до этих проверок). Не пытаться «переиздать» их.
