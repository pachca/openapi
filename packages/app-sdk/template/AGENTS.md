# AGENTS.md

Приложение Пачки: сервер (схема, функции) выполняет платформа приложений, фронт открывается в окне Пачки. SDK и команды
разработки в пакете `@pachca/app-sdk` (`npx pachca-app …` из этой папки), хуки React в `@pachca/app-react`.

## Команды

    npx pachca-app check                          # типы, скоупы, хосты, импорты; запускайте до ship
    npx pachca-app ship                           # проверка, сборка, создание приложения (первый раз), загрузка
    npx pachca-app logs                           # журнал: ошибки функций, сеть, API Пачки, нарушения фронта

`ship` и другие сетевые команды работают через CLI Пачки и его вход: `npm install -g @pachca/cli`, затем
`pachca auth login` (владелец или администратор пространства). Если входа нет, команда так и скажет: попросите человека
войти, сами токены не ищите и не создавайте. Не читайте и не правьте `_generated/` и `dist/`: это результат `check`/`build`.

`ship`, `check` и `build` работают только на последней версии SDK. Если версия устарела, они предлагают обновить
`@pachca/app-sdk` и `@pachca/app-react` (без терминала печатают команду): обновите и повторите.

## Версии и загрузка

- Загрузка сразу становится текущей версией, черновиков и отката нет: ошибку исправляют следующей версией.
- `.pachca-app.json` в папке хранит id приложения и номер версии, от которой сделана папка. Не правьте его руками.
- `version_conflict`: приложение загрузили из другой папки. Не загружайте поверх. Скачайте текущую версию в новую папку
  (`npx pachca-app pull ../<имя>-new --app <id>`), перенесите туда свои изменения, проверьте (`check`) и загрузите
  оттуда. `--force` затирает чужие изменения: только если человек сам об этом попросил.
- Изменились права, хосты или события: `ship` без терминала ничего не загружает и печатает список изменений. Покажите его
  человеку и добавьте `--approve-consent-screen` только после его согласия.
- `--mode staging` собирает с `.env.staging` и загружает в отдельное приложение этого режима (первый раз создаёт его). В коде
  `import.meta.env.VITE_*` и `import.meta.env.MODE`, на фронте и на сервере. Значения попадают в сборку: ключи туда не кладите,
  для них `secret set`. Режим нужен, только если человек хочет проверочную копию приложения.
- Удаляет приложение только человек: `npx pachca-app delete` спрашивает id приложения в его терминале, без терминала
  ничего не удаляет. Сами её не запускайте: если приложение нужно удалить, скажите человеку эту команду.

## Структура папки приложения

    manifest.ts     права и сеть (defineManifest)
    schema.ts       таблицы и индексы (defineSchema, defineTable, v)
    server/*.ts     функции query / mutation / action; имя файла = модуль (api.<модуль>.<функция>)
    index.html      единственная точка входа фронта (<script type="module" src="/src/main.tsx">), обязателен
    src/            фронт на React: main.tsx, router.tsx (TanStack Router), экраны; хуки из @pachca/app-react
    vite.config.ts  необязательный: свои плагины Vite (build и ship собирают фронт через Vite)
    public/         остальная статика как есть (картинки, шрифты)

Приложению без интерфейса (бот, вебхуки, задания) вместо фронта хватает `public/index.html` с заглушкой.

## Схема (`schema.ts`)

    export default defineSchema({
      notes: defineTable({ text: v.string(), note: v.optional(v.string()), owner: v.string() }).index("by_owner", ["owner"]),
    });

- Один язык `v` для схемы, аргументов и результатов функций: `v.string()`, `v.number()`, `v.boolean()`, `v.id("таблица")`
  (ссылка на документ, тип `Id<"таблица">`), `v.optional(...)`. Для аргументов и результатов есть ещё `v.object({...})` и `v.array(тип)` (в таблицах их нет: поля таблиц скалярные). Вариантов (union) пока нет.
  `v` строит описание, а не проверку: данные проверяет платформа, кода проверки в сборке нет. Типы выводятся из описания.
- Проверяемая ссылка `v.ref("таблица")`: тип тот же `Id<"таблица">`, но платформа следит, чтобы документ существовал.
  `insert`/`patch` с несуществующим документом отказывают кодом `ref_missing` (422), `delete` документа, на который ссылается
  поле `v.ref`, отказывает кодом `ref_in_use` (409): сначала удалите или поменяйте ссылающиеся документы той же мутацией.
  `v.id` существование не проверяет. В аргументах функций `v.ref` проверяется как `v.id`. Ссылаться на `_scheduled` нельзя.
- Служебные поля `_id` (тип `Id<"таблица">`) и `_creationTime` добавляет платформа.
- Индекс: `.index("имя", ["поле1", "поле2"])`. Запрос с индексом принимает равенства по началу списка полей.
- Платформа проверяет каждую запись (`insert`, `patch`) по схеме: неверный тип, нет обязательного поля или лишнее поле это ошибка.
- SQL писать нельзя и не нужно: платформа строит запросы по схеме.

### Менять схему, когда данные уже есть

При загрузке версии платформа проверяет все существующие документы по новой схеме. Если хоть один не подходит, версия
отклоняется целиком, ничего не меняется, а ответ перечисляет проблемы:

    tasks: 50 документов без обязательного поля priority (например id 81, 82, 90)
    notes: поле text у 3 документов number, ожидается string (например id 4, 7, 9)

- Новые таблицы, необязательные поля и индексы добавляются в любой момент.
- Поле можно убрать, а таблицу удалить, только когда в них нет данных (очистите значения мутацией, потом уберите).
- Тип поля можно менять, если все значения подходят под новый (например, `v.number()` в `v.id("tasks")` при целых от 1).
  `v.id` → `v.ref` проходит, только если все ссылки целы (иначе `comments: поле task у 2 документов ссылается на несуществующий
  документ таблицы tasks (например id 4, 7)`: удалите или поправьте их мутацией), `v.ref` → `v.id` проходит всегда.
- Ломающее изменение делайте в несколько версий. Например, обязательное поле `priority`:
  1. Добавьте `priority: v.optional(v.number())`, загрузите версию. Код пишет поле, читает его с учётом `undefined`.
  2. Мутацией заполните поле у всех старых документов (`ctx.db.patch`), загрузите версию, в которой она есть.
  3. Сделайте поле обязательным (`priority: v.number()`) и загрузите версию: платформа проверит данные и пропустит её.
  Так же с переименованием: новое поле необязательное, перенос значений мутацией, потом убрать старое.

## Функции (`server/<модуль>.ts`)

Импорт строителей: `import { query, mutation, action } from "../_generated/server"` (файл появляется после `check`/`build`).
Аргументы описываются через `v` (`import { v } from "@pachca/app-sdk/server"`): `args: { text: v.string(), note: v.optional(v.string()) }`,
результат необязателен: `returns: v.id("tasks")`. Функция должна быть именованным экспортом вида
`export const имя = query({ ... })`: другие объявления CLI не находит.

- Платформа проверяет вызов до запуска обработчика: неверный тип, нет обязательного поля или лишнее поле дают
  `invalid_args` с путём к полю (`text: ожидается string, получено number`), функция не запускается. Это же верно для `ctx.runMutation`
  и заданий. Если задан `returns`, платформа проверяет и результат: несовпадение это ошибка автора (500 в журнале, мутация откатывается).
- Ограничения по значению (длина, диапазон, набор допустимых значений) в типах пока не выразить: проверяйте в обработчике и бросайте
  `AppError`.

- `query`: только чтение, `ctx.db.query(table).withIndex(name, q => q.eq(field, v)).order("desc").collect()|take(n)|first()`,
  `ctx.db.get(table, id)`. Фронт держит его живым (`useQuery`), платформа перезапускает при изменении данных.
- `mutation`: одна транзакция, дольше 2 секунд нельзя. `ctx.db.insert`, `patch`, `delete` и чтение. Ошибка откатывает всё.
  Мутации идут параллельно: если за время мутации данные поменяла другая, платформа откатывает её и выполняет функцию заново
  (до 8 попыток, потом клиент получит `conflict`). Поэтому мутация зависит только от аргументов и базы: `Date.now()` и `new Date()`
  в ней дают время начала попытки (одно на всю мутацию, с ним же пишется `_creationTime`), `Math.random()` годится для простых
  случайных значений, а `crypto.getRandomValues` и `crypto.randomUUID` бросают `nondeterministic`: ключ или токен создайте в
  действии и передайте мутации аргументом. Ловить ошибку конфликта бессмысленно: попытка всё равно перезапустится.
- `action`: нет доступа к базе. Есть `ctx.fetch` (только хосты из `manifest.fetch`, https), `ctx.pachca.bot` и `ctx.pachca.user`
  (API Пачки, см. ниже), `ctx.runQuery`, `ctx.runMutation`.
- `ctx.pachca.bot` от бота приложения, `ctx.pachca.user` от имени пользователя после его согласия. Методы и типы приходят из
  установленного `@pachca/app-sdk` (открытая спецификация API Пачки той же версии), сеть для них не нужна.
  Имена как в `@pachca/sdk`: `ctx.pachca.<раздел>.<метод>`, у каждого JSDoc с описанием и скоупом. Аргументы как в API, один объект
  `{ path, query, body }`, поля в camelCase (SDK переводит в snake_case и обратно). Ответ `{ data }` приходит как `data`,
  списки целиком (`{ data, meta }`, курсор в `meta.paginate.nextPage`). Пустой ответ это `undefined`.
  ```ts
  await ctx.pachca.bot.messages.createMessage({ body: { message: { entityId: chatId, content: "Готово" } } });
  const { data } = await ctx.pachca.user.chats.listChats({ query: { limit: 50 } });
  ```
  Метод, чьего скоупа нет в `manifest.pachca.<сторона>`, не компилируется: ошибка говорит, что добавить. Обход типов не поможет:
  платформа проверяет скоуп каждого вызова и отвечает `scope_missing`. Методы только для бота
  (`roles: bot` в спецификации) у `user` отсутствуют. В `job`, `internalAction` и `webhook` есть только `ctx.pachca.bot`.
  Отказ Пачки это `PachcaError` из `@pachca/app-sdk/server` (`e.status`, `e.code`: `insufficient_scope`, `not_found`…).
  Файлы: поле формы (`image` у загрузки аватара) принимает uuid файла приложения или `{ data, name, contentType? }` (байты, `Blob`,
  поток); `files.downloadFile` отдаёт `{ name, contentType, size, body, arrayBuffer(), text() }` потоком. Без методов API:
  `ctx.pachca.<сторона>.uploadFile(файл)` (скоуп `uploads:write`) загружает файл в Пачку и даёт `{ key, name, size, fileType }`
  для `files` сообщения, `ctx.pachca.<сторона>.saveFile({ id, target? })` (скоуп `files:read`) кладёт вложение Пачки сразу в файлы
  приложения и даёт `{ id, name, size, contentType }` (`id` для `v.file()`). Файл через `ctx.pachca` до 32 МБ, отказ это `file_too_large`.
- `job`: внешний вызов, который что-то меняет (письмо, платёж, запись в CRM). Берите `job` вместо `action`, если повтор небезопасен
  или клиенту нужно знать исход; `action` оставьте для поиска и других вызовов, повтор которых безвреден. Обработчик как у `action`
  (`ctx.fetch`, `ctx.runQuery`, `ctx.runMutation`), но без пользователя (`ctx.actor` равен `null`) и напрямую его не вызвать: клиент
  запускает задание, сразу получает его номер, а платформа выполняет его не больше одного раза, без автоповторов (повтор делает
  пользователь новым запуском). Запуск работает как мутация: по порядку сессии и ровно один раз при обрыве связи, аргументы проверяются до
  постановки. Результат (`returns`, JSON до 1 МБ) хранится в `_scheduled.result`. `throw new AppError("текст", { code })` доходит до
  клиента кодом и текстом, любая другая ошибка получает код `job_failed` без подробностей (они в журнале).
  ```ts
  export const send = job({
    args: { to: v.string(), text: v.string() },
    handler: async (ctx, { to, text }) => {
      const res = await ctx.fetch("https://api.mail.example/send", { method: "POST", body: JSON.stringify({ to, text }) });
      if (!res.ok) throw new AppError("Почта не приняла письмо", { code: "mail_rejected" });
      return { id: ((await res.json()) as { id: string }).id };
    },
  });
  ```
  Фронт запускает задание хуком `useJob(api.mail.send)` (см. «Фронт»): `start(args)`, живой `state` (`starting`, `pending`,
  `running`, `success`, `failed`, `canceled`), `result`, `error` (`{ code, message }`) и `cancel()`. Видит и отменяет задание только
  тот, кто его запустил. Начавшееся задание отменить нельзя. Номер хук помнит в `localStorage`: после перезагрузки iframe статус и
  результат снова видны до `reset()` или нового `start` (несколько мест запуска одного задания: `useJob(ref, { key: "send:" + id })`). Своя функция автора может читать `_scheduled` всех пользователей
  (экран «все отправки»). `ctx.scheduler.runAfter` и `runAt` принимают и `job`, номер такого задания фронт показывает `useJobStatus(id)`.
- Ключи внешних сервисов в код не кладите и в запросе не пишите. Подключение объявляется в манифесте: хост из `fetch` и место ключа,
  `secrets: { NAME: { host: "api.example.com", header: "Authorization", prefix: "Bearer " } }` или `{ host, query: "api_key" }`.
  Ключ вводит человек: `npx pachca-app secret set NAME`. Платформа сама добавляет его в каждый `ctx.fetch` к этому хосту
  (заголовок или параметр с тем же именем от кода заменяется), на другие хосты ключ не уходит, в ответе его значение маскируется,
  а ключ в адресе редиректа даёт отказ. Смена хоста подключения в новой версии сбрасывает ключ: после публикации его задают заново.
  Имя `[A-Z][A-Z0-9_]*`.
- Мутация выполняется ровно один раз даже при обрыве связи, мутации идут в порядке вызовов. Действие не больше одного раза:
  при обрыве придёт `connection_lost`. Поэтому внешнее, что нельзя повторять (письмо, платёж), делайте `job`, а не прямым вызовом действия.
- По расписанию: `ctx.scheduler.runAfter(мс, internal.<модуль>.<функция>, args)` из мутации или действия (`runAt` по метке времени,
  `cancel(id)`). Вызываемую функцию объявляйте `internalMutation`/`internalAction` (клиенту она не видна), ссылка `internal` лежит
  в `_generated/api`. Обработчик, который сам зовёт `internal.*`, типизируйте по результату (`(ctx, args): Promise<void> =>`).
  В задании `ctx.actor` всегда `null`, `ctx.pachca.user` недоступен, пишите от бота; id пользователя передавайте в аргументах. Всегда проверяйте `ctx.actor` на `null` перед использованием (`ctx.actor?.id`) и не выводите права из `ctx.actor`: в заданиях и вебхуках его нет, и код, который это не учитывает, может принять работу платформы за действие человека.
  Мутация по расписанию выполняется один раз, действие не больше одного, автоповторов нет. Состояние заданий читайте запросом
  `ctx.db.query("_scheduled")` (поля `fn`, `state`, `result`, `error`, `errorCode`, `runAt`). Повторяющееся задание ставит себя заново в конце.
- Ожидаемый отказ (не найдено, уже занято, нельзя) бросайте как `throw new AppError("текст", { code: "taken", status: 409 })`
  из `@pachca/app-sdk/server`: клиент получает код 4xx с `code` и `message`, в журнале приложения это не 500, мутация
  откатывается. `status` только 400-499 (по умолчанию 400). Обычный `throw new Error(...)` остаётся 500.
- `ctx.app` это `{ id, url }` приложения, в котором выполняется функция (есть везде, включая задания и вебхуки): id в Пачке и
  ссылка, которая его открывает (кнопка в сообщении бота). Одна сборка работает и в тестовом приложении, и в рабочем, поэтому
  id и ссылку в код не пишите, берите из `ctx.app`.
- `ctx.actor` это `{ id, role }` пользователя Пачки (`role`: `owner`, `admin`, `user`, `multi_guest`, `guest`) или `null`. Данные пользователя храните с `owner: ctx.actor.id` и
  проверяйте владельца в `mutation`, иначе один пользователь увидит и изменит чужое.

## Файлы (`v.file()`, `ctx.files`)

Картинки и документы пользователей хранит платформа (внешний S3), приложению своё хранилище не нужно. 

- Поле таблицы или аргумент `v.file()` содержит uuid файла (`FileId`). Запись документа с ним проверяет платформа: файл подтверждён, принадлежит этому приложению и загружен этим же пользователем.
- Фронт: `const id = await pachca.files.upload(file, { signal, onProgress, createSession? })`, затем мутация с `id`. Для своих правил (только картинки, роли) напишите `action`, который проверяет `ctx.actor` и зовёт `ctx.files.generateUploadUrl({ filename, size, contentType })`, и передайте его в `createSession`.
- Показ: `await ctx.files.url(id)` даёт адрес `/_files/…` на 10–20 минут, кладите его в `<img src>`; в документе храните uuid, а не адрес. Картинки отдаются inline, остальное как attachment; SVG и HTML исполняться не будут.
- `ctx.files.delete(id)` при удалении документа: платформа не считает ссылки, а файлы занимают квоту компании (по умолчанию 256 МБ, файл до 10 МБ).
- Ошибки: `file_too_large` 413, `quota_exceeded` 422, `rate_limited` 429, `file_invalid` 422, `bad_filename` 422, `files_disabled` 503 (хранилище не настроено).

## Фронт (`src/`)

Одностраничное приложение на React, Vite и TanStack Router, как в этой заготовке. Данные только через хуки `@pachca/app-react`
(они работают поверх моста, который платформа подставляет сама, импортировать его не нужно):

```tsx
import { isFunctionError, useAction, useJob, useMutation, usePachca, useQuery } from "@pachca/app-react";
import { api } from "../_generated/api";

const tasks = useQuery(api.tasks.list);                 // живое значение, undefined пока грузится
const task = useQuery(api.tasks.get, id ? { id } : "skip");
const add = useMutation(api.tasks.add).withOptimisticUpdate((store, { text }) => {
  const list = store.getQuery(api.tasks.list, {});      // ожидаемый результат сразу, сервер подтвердит или откатит
  if (list) store.setQuery(api.tasks.list, {}, [...list, { ...черновик, text }]);
});
await add({ text });                                    // отказ: isFunctionError(e), e.code из AppError, e.message
const search = useAction(api.tasks.search);             // повтор безвреден: поиск, чтение
const send = useJob(api.mail.send);                     // нельзя повторять: письмо, платёж
<button disabled={send.isRunning} onClick={() => send.start({ to, text })}>Отправить</button>
{send.state === "success" && send.result?.id} {send.error?.message}
const { theme } = usePachca();                          // "light" | "dark", меняется на лету
```

- Ошибка `useQuery` бросается при рендере: ловите её `errorComponent` роута (или своим Error Boundary). `start` у `useJob` не
  бросает: отказ запуска и падение задания приходят в `error`.
- Экраны меняет только роутер (`<Link to="/tasks/$id">`, `useNavigate`, параметры поиска `validateSearch`). `<a href="/tasks/2">`
  без роутера или `location.href` на свой адрес Пачка отменит, документ в iframe один.
- Ссылки наружу только тегом `<a href="https://…">`: адрес Пачки (`https://app.pachca.com/chats/<id>`) открывается переходом в
  Пачке, остальные Пачка покажет с адресом и откроет в браузере. Открывает их только клик человека: `location.href = …`,
  `window.open`, `a.click()` из скрипта, `<meta refresh>` и отправка формы на другой адрес отменяются.
- Кто пользователь и что ему можно, решает сервер по `ctx.actor`: на фронте пользователя нет, а проверка на фронте ничего не защищает.

Сборка помнит версию протокола (одна на фронт и бэк), на которой её собрал CLI. Когда выходит новая версия протокола, начинается
переход: сборка прежней версии ещё работает целиком, а `ship`, `logs` (вид «платформа») и консоль браузера предупреждают, до какого
срока. После срока Пачка показывает вместо приложения заглушку «Приложение устарело», а платформа не принимает загрузку старой
сборки и не выполняет её функции (задания, вебхуки, события получают `outdated`). Увидели предупреждение: обновите
`@pachca/app-sdk`, пересоберите и загрузите заново (`ship`). После публикации новой версии открытый документ устаревает: статус
подписки `outdated`, вызовы падают с кодом `version_changed`, а Пачка предлагает человеку перезагрузить приложение. Введённое
человеком, которое жалко потерять, приложение может держать в `localStorage`. Типы приходят из схемы и функций, `any` не нужен. Файлы в `public/`
с сегментом пути на `_` платформа не примет: эти пути её (`/_pachca/sdk.js`, `/_ws`).

## Манифест (`manifest.ts`)

    export default defineManifest({
      description: "Что делает приложение",
      db: true,                                   // нужна своя база; `build` ставит сам, если есть таблицы
      fetch: ["api.example.com"],                 // точные хосты для ctx.fetch, без wildcard
      browser: ["*.basemaps.cartocdn.com"],       // хосты, куда фронт ходит из браузера (тайлы, шрифты, картинки)
      pachca: { bot: ["messages:create"], user: ["messages:read"] },
    });

- Права бота и пользователя: любые разрешения API Пачки (`область:действие`, например `messages:create`, `threads:create`).
  Платформа проверяет формат и скоуп каждого вызова по манифесту, Пачка ещё раз по скоупам токена; у пользователя `profile:read` добавляется
  сам, если есть любые права пользователя.
- Доступ к приложению (`private` только автор, `link` по ссылке, `public` ещё и в обзоре) в манифесте не задаётся: его меняет человек
  или токен с `apps:write` в Пачке без новой версии (`npx pachca-app edit --visibility link|public|private`). Не расширяйте доступ сами: если он нужен, скажите человеку, кто его получит.
  Права внутри приложения (кто что видит и правит) строит код: `ctx.actor.id`, `ctx.actor.role` плюс API Пачки; платформа ограничивает
  только вход в приложение.
- Вебхук внешнего сервиса: `manifest.webhooks.<имя>` (нужна хотя бы одна проверка: `signature: { header, secret }` и/или `allow`; без подписи `allow` не может быть `/0`) и функция
  `export const <имя> = webhook({ handler: async (ctx, req): Promise<void> => … })`; адрес `/_hooks/<имя>` на хосте приложения. Секрет
  подписи (если он есть) ставит человек (`secret set`), его имя не может совпадать с ключом из `secrets`. Обработчик без пользователя (`ctx.actor` пуст), идемпотентный, пишет в базу через
  `ctx.runMutation`. Нужна база (`db: true`).
  Чтобы платформа сама проверила тело, задайте его на языке `v`: `webhook({ body: v.object({ order_id: v.string() }), handler: async (ctx, req) => … })`.
  Платформа разбирает JSON, при ошибке отвечает 400 без запуска обработчика, а `req.body` приходит уже объектом (лишние поля допускаются).
  Без `body` тело строкой, как раньше. Если у сервиса есть идентификатор события, укажите, где он лежит:
  `webhooks: { crm: { signature: …, id: { header: "X-Event-Id" } } }` или `id: { json: "data.event.id" }`: повтор отбрасывается по нему, а не
  по хэшу тела (два одинаковых законных заказа не склеиваются). Идентификатор в теле подписан, заголовок нет. Сервисы, которые при
  подключении проверяют адрес и ждут эхо (`url_verification` у Slack, `hub.challenge` у Meta), обслуживает `verify: (req) => …`: синхронная чистая
  функция (без ctx, базы и сети, две секунды), вернула `{ status?, body }`, платформа отвечает так сразу, вернула `undefined`, запрос обычный.
- События Пачки (бот приложения): в манифесте `pachca: { bot: ["messages:create"], events: ["message.new", "button.click", "view.submit"] }`,
  на каждое событие ровно один обработчик `export const onMessage = pachcaEvent("message.new", { handler: async (ctx, event) => … })`
  (`event` типизирован по схеме Пачки). Обработчик это действие без пользователя, как у вебхука: ответ в чат пишите через `ctx.pachca.bot`,
  данные через `ctx.runMutation`, он идемпотентный и не повторяется при падении. Платформа сама проверяет, что событие пришло из Пачки,
  и отбрасывает повторную доставку. События собственного бота приложению не приходят (бот не отвечает сам себе). Форма (`view.submit`)
  закрывается сразу: показать ошибки полей из обработчика нельзя. Нужна база (`db: true`). Подписку человек видит в списке прав при загрузке.
  Пример: `server/bot.ts`.
- Новые права и хосты требуют подтверждения человеком: без `--approve-consent-screen` (или ответа в терминале) `ship` ничего
  не загрузит. Не добавляйте права «на всякий случай»: подтверждает их человек, чем меньше, тем лучше.
- Чтение данных Пачки вместе с внешней сетью помечается в списке изменений прав как опасная комбинация.

## Сеть фронта

Фронт ходит на свой origin и на хосты `manifest.browser`: `fetch`, картинки, шрифты, стили и медиа одним списком, точный хост или
маска поддомена `*.example.com`, можно с портом (голая `*`, `*.com`, схема и путь не проходят). Скрипты только свои: библиотеки
кладите в сборку, а не грузите с CDN. Новый хост `browser` человек подтверждает, как новый хост `fetch`.

- `browser`: тайлы, стили и глифы карт (MapLibre), шрифты и картинки с CDN, публичные API без ключа.
- Серверное действие с `fetch`: всё с ключом (ключ добавляет серверный egress, в браузер его не передать), запись во внешние
  системы, ответ, которого человеку видеть не нужно.

Воркеры из своего файла и из `blob:` работают (MapLibre, pdf.js), сервис-воркеры нет. WebRTC (`RTCPeerConnection`, PeerJS,
y-webrtc) закрыт: вызов бросает `NotAllowedError`, живые данные между пользователями идут через подписки (`useQuery`). Нельзя inline-скрипты и `onclick=`
(стили inline можно), `eval`, вложенные iframe, `<form action>` (форму обрабатывайте в JS с `preventDefault`), OAuth во фронте
(права пользователя даёт `manifest.pachca.user`). В iframe открывается только `index.html`: переходы между экранами делайте
роутером, другие `.html` и SVG как страницы получат 403. Приложению без интерфейса (бот, вебхуки, задания) всё равно нужен
`public/index.html`: заглушка, которая объясняет, что делает приложение. Нарушения видны в `npx pachca-app logs` (вид «фронт»).

## Тема

Хост Пачки передаёт тему окна в адресе (`?theme=light|dark`), а платформа сама ставит её на `<html data-pachca-theme="…">`
и добавляет `<meta name="color-scheme">` в отдаваемый `index.html`. Приложению достаточно стилей:
`:root[data-pachca-theme="dark"] { … }`, плюс `@media (prefers-color-scheme: dark)` для `:root:not([data-pachca-theme])`
как запасной вариант. Если тема нужна коду (графики, canvas), её даёт `usePachca().theme`.

## Проверка и отладка

- `npx pachca-app check` гоняет `tsc`: неверные аргументы, несуществующий индекс или функция,
  запись из `query`, доступ к базе из `action` и метод Пачки без скоупа не компилируются. Ещё он сверяет скоупы манифеста со списком
  API Пачки (неизвестный скоуп, скоуп, который боту или пользователю не выдаётся). Ещё он отказывает на импортах, которых нет в рантайме функций (workerd без модулей Node: `node:fs`, `path`). Запускайте до `ship`.
  Фронт проверяется так же: аргументы `useQuery`, `useMutation`, `useJob.start` и поля результата выводятся из функций сервера.
- Ошибки `ship` печатаются под шагом, который упал. Токен не печатайте и не коммитьте.
- Права и лимиты платформы жёсткие (память, CPU, время запроса, размер сборки 16 МБ): большие вычисления не для этого рантайма.
