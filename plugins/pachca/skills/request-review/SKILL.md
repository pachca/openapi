# Request a code review in Pachca

Ask for a review of the merge request or pull request the user gave, or of the current branch's, in the chat where the team asks for reviews, mentioning the reviewers. With «напомни» or "remind" instead, remind about the user's open MRs or PRs that still wait for a review (step 5). Follow the `pachca-messaging` skill for writing, mentions and editing, its «Writing to colleagues» section included.

1. What to review. Take the MR or PR the user named, or the current branch's, through the tools this session already has: `glab mr view` for GitLab, `gh pr view` for GitHub (`git remote -v` tells which), or the code host's MCP server. Note its title, link, the size of the diff and whether it is a draft: a draft is not ready for review, so say so and ask. Take the task from the tracker key in the branch name or the title, with its link, through the tracker's tools this session has. Do not invent a link, number or status you did not read, and say what you could not check. With no MR or PR for the branch, say so: opening one is the user's call.
2. Where and whom. The review chat and the reviewers may be written down in the project's instructions for agents (`AGENTS.md`, `CLAUDE.md` or the program's own rules): they come first, and a chat or reviewers named with the command replace them for this run. Otherwise find the chat the user named with `pachca_search_chats`. With no name, look for the user's earlier review requests (`pachca_search_messages` with your own id in `user_ids` and «ревью» or "review" in `query`) and offer the chat they went to. Reviewers are the people the user named. With none, take the people the user mentioned in their recent requests in that chat, and when they are more than one request needs, show them and ask whom to call. Never mention the user. Resolve each reviewer to a `user_id` with `pachca_search_users`, never a nickname made up from a name: an earlier request keeps a mention only as text in `content` (`@Имя Фамилия` when typed in the app, `@nickname` when sent through the API), with no id. Mention them as the `pachca-messaging` skill says, whatever form the earlier requests show. Check each reviewer's status (`pachca_get_user_status`): name anyone who is away, and the user may pick someone else.
3. Text. First search the chat for the MR or PR link (`pachca_search_messages` with the link in `query` and the chat in `chat_ids`): if the user already asked for this review there, offer a short reply in that request's thread with what changed since, rather than a new request. Otherwise read the latest page of the chat (`pachca_list_chat_messages`), above all the user's own review requests, and follow their shape: where the mentions go, the first line, which links they keep (the task, the MR or PR), whether they give the size or what to look at. With no earlier requests, write the mentions, then «Запрос на код-ревью» or the same in the chat's language, the title as a link to the MR or PR, the task as a link, the size of the diff, and a line or two on what changed and where to look. Keep it to a few short lines in Pachca's formatting, without markdown lists. If the chat asks for reviews in threads, do the same.
4. Send. Show the chat, who will be mentioned and the text, and send after a yes: a mention notifies at once, and an edit takes no notification back. Send without showing only when the user said «отправь» with the command, or the instructions for agents say review requests go out without showing, and then mention only the reviewers named with the command or in those instructions, never ones taken from earlier requests. Give the user the message link and offer the `watch-thread` command on its thread to hear about comments.
5. Remind. Collect the user's open MRs or PRs that wait for a review (`glab mr list --author=@me`, `gh pr list --author @me`, or the code host's MCP server), leaving out drafts and the ones the user excluded. For each, find its review request in the chat (`pachca_search_messages` for its link with the chat in `chat_ids`) and the reviewers who have not approved it yet. Write one message to the chat: a short line per MR or PR with its link and a link to its review request, mentioning only the reviewers who still owe a review. One message notifies once, while a reply under each review request notifies each time. If the user reminded in the threads of the review requests before, do that instead. Show the text and send after a yes, as in step 4.

Corrections the user makes to the chat, the reviewers or the text are rules for this project: when it keeps such rules in its instructions for agents, offer to add them there, so the next request asks nothing.
